# Observables for Using Socket with Angular

Здесь наконец сходятся обзерверы из 6.0–6.1 и сокеты из 6.3: событие сокета оборачивают в `Observable`, чтобы получить операторы RxJS. Логика лекции правильная, но код в слайдах написан на API двухлетней давности и содержит утечку обработчиков. Разберу по порядку.

### Логика лекции, которая верна и важна

  - Сокеты дают двусторонний канал: сервер может **сам** пушить сообщения всем подключённым клиентам, не дожидаясь запроса.
  - Работу с сокетом надо держать в **сервисе**, а не в компоненте. Слайд говорит про MVC-разделение, но практическая причина важнее: сервис с `providedIn: 'root'` существует в единственном экземпляре, поэтому соединение будет одно, а не по одному на каждый компонент. Плюс сервисом могут пользоваться другие компоненты без копипасты.
  - Сервису нужны три метода: инициализировать соединение, отправлять сообщения, принимать сообщения.
  - Ключевое наблюдение из слайда 7: когда сервис принимает колбэк (`getMessage(next)`) и вызывает его на каждое сообщение, это **уже** паттерн Observer, написанный руками. Observable — то же самое, только со стандартным интерфейсом, отменой и операторами.
  
### Устаревший код в слайдах

**Импорт клиента.** В слайдах написано `import * as io from 'socket.io-client'` — это стиль v2. В v3/v4 правильно так:

    ```ts
    import { io } from "socket.io-client"; // v3/v4
    const socket = io("http://localhost:3000");
    ```

Со старым вариантом в v4 ты получишь ошибку вида «This expression is not callable», потому что `io` окажется объектом модуля, а не функцией.

**Создание Observable.** Слайд показывает два варианта и говорит, что это одно и то же:

    ```ts
    Observable.create((observer) => { ... });   // устарело в RxJS 7
    new Observable((observer) => { ... });      // так правильно
    ```

По результату они действительно одинаковы, но `Observable.create` объявлен deprecated и в v8 будет удалён. Пиши `new Observable(...)`. Ну и импорт в v6+ идёт из `'rxjs'`, а не из `'rxjs/Observable'`, как в слайде.

### Главная проблема кода из лекции: нет очистки

Вот код из слайда 9 как есть:

    ```ts
    getMessages() {
        return new Observable((observer) => {
            this.socket.on('new-message', (message) => {
                observer.next(message);
            });
        });                     // ← ничего не возвращаем
    }
    ```

Функция внутри `new Observable` выполняется **на каждую подписку**, и то, что она вернёт, RxJS вызовет при отписке (teardown). Здесь не возвращается ничего, и отсюда два бага.

Первый: `unsubscribe()` не убирает обработчик с сокета. Компонент уничтожен, а `socket.on` продолжает висеть и дёргать мёртвый `observer` — утечка памяти.

Второй, более коварный: Observable холодный, поэтому **каждая новая подписка навешивает ещё один `socket.on`**. Два компонента подписались — обработчиков два, и одно пришедшее сообщение попадёт в список дважды. В чате это выглядит как дублирующиеся сообщения, и причину обычно ищут на сервере, хотя она здесь.

Правильная версия с очисткой и типами:

    ```ts
    getMessages(): Observable<string> {
        return new Observable<string>((observer) => {
            const handler = (message: string) => observer.next(message);
            this.socket.on('new-message', handler);

            return () => this.socket.off('new-message', handler);  // вызовется при unsubscribe
        });
    }
    ```

### Как правильнее для нескольких подписчиков

Если сообщения нужны в нескольких местах приложения (список чата, счётчик непрочитанных, звук), холодный Observable плохо подходит — обработчик будет заводиться на каждую подписку. Тогда в сервисе держат один `Subject`, а сокет пишет в него один раз:

    ```ts
    @Injectable({ providedIn: "root" })
    export class SocketService {
        private socket = io(environment.socketUrl);
        private messages$ = new Subject<string>();

        constructor() {
            this.socket.on("new-message", (m: string) => this.messages$.next(m));
        }

        getMessages(): Observable<string> {
            return this.messages$.asObservable(); // наружу отдаём только Observable
        }

        send(message: string): void {
            this.socket.emit("message", message);
        }
    }
    ```

Здесь обработчик сокета ровно один, а подписчиков может быть сколько угодно — это тот самый «горячий» multicast из 6.1. `asObservable()` нужен, чтобы снаружи нельзя было вызвать `next()` и подделать сообщение от сервера. Если новому подписчику нужна вся история сообщений, а не только будущие, вместо `Subject` берут `BehaviorSubject` с массивом или `ReplaySubject`.

### Подписка на стороне компонента

    ```ts
    export class ChatComponent implements OnInit, OnDestroy {
        messages: string[] = [];
        private sub?: Subscription;

        constructor(private socketService: SocketService) {}

        ngOnInit(): void {
            this.sub = this.socketService
                .getMessages()
                .subscribe((m) => this.messages.push(m));
        }

        ngOnDestroy(): void {
            this.sub?.unsubscribe(); // без этого — утечка, о которой лекция молчит
        }
    }
    ```

В слайде подписка есть, а отписки нет вообще. Для сокета это критично: HTTP-запрос завершается сам и подписка умирает вместе с ним, а поток сообщений из сокета бесконечен и сам никогда не закончится.

### Зачем вообще Observable, если колбэк работал

Слайд 11 задаёт этот вопрос честно и отвечает верно: RxJS даёт операторы, а они возвращают **новый** Observable, не меняя исходный (это и называется «pure operation»). На практике выигрыш выглядит так:

```ts
this.socketService
    .getMessages()
    .pipe(
        filter((m) => m.channelId === this.currentChannel), // только текущий канал
        map((m) => ({ ...m, text: m.text.trim() })), // привести к нужной форме
        takeUntil(this.destroy$), // автоматически отписаться
    )
    .subscribe((m) => this.messages.push(m));
```

С сырым `socket.on` всё это пришлось бы писать вручную внутри обработчика: сам проверяй канал, сам преобразуй, сам снимай обработчик. Тут же добавляются вещи, которые руками писать больно: `debounceTime` для индикатора «печатает…», `scan` для накопления счётчика, `merge` для объединения нескольких событий сокета в один поток.

### Связки с другими лекциями
  - **6.1:** `socket.on` — это Subject внутри библиотеки, а твой колбэк — Observer. Обёртка в `new Observable` просто переводит это на стандартный интерфейс RxJS.
  - **6.2:** промис здесь принципиально не подходит — сообщений много, промис срабатывает один раз.
  - **6.3:** сервер рассылает через `io.emit` (всем, включая отправителя) или `socket.broadcast.emit` (всем, кроме него) — от этого зависит, надо ли компоненту добавлять своё сообщение локально.
  - **week5:** origin `http://localhost:4200` должен быть разрешён в опциях `new Server(server, { cors: ... })` на сервере, иначе соединение не встанет.
  
### Проверь себя
  1. Почему `new Observable(observer => socket.on(...))` без возврата функции течёт?
  2. Что произойдёт, если на такой Observable подпишутся три компонента?
  3. Зачем в сервисе отдавать `subject.asObservable()`, а не сам `subject`?
  4. Почему для сокета отписка в `ngOnDestroy` обязательна, а для HTTP-запроса не так критична?
  5. Чем `new Observable` лучше, чем просто передать колбэк в сервис?
