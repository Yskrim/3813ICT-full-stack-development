# 03 — Promise, async/await, параллельность

Конспект: `6-2-Promises-and-async-functions.md`.

Зачем это на практике: половина серверного кода ассайнмента — это асинхронные обращения к файлам и базе. Здесь тренируются три вещи, на которых обычно теряют время: превращение колбэчного API в промис, корректная обработка ошибок в цепочке и умение не делать три независимых запроса последовательно.

Запуск: `node 03-promises/task-1-promisify.ts`

## Задание 1 — обернуть колбэк в промис

Файл: `task-1-promisify.ts`

В файле дан колбэчный API `findUser(id, callback)` — так выглядят старые библиотеки и почти весь низкоуровневый Node. Твоя задача обернуть его в промис, как в лекции обернули `XMLHttpRequest`.

Что сделать:

- написать `findUserAsync(id): Promise<User>` через `new Promise`;
- ошибку отклонять объектом `Error`, а не строкой;
- получить пользователя через `await` и напечатать результат;
- поймать ошибку для `id === 0` через `try/catch`;
- посмотреть на строки `[api] пошёл искать...` и понять, в какой момент реально стартует работа.

**Критерии**

- В выводе видно, что микрозадача (`2`) печатается после всего синхронного кода — это порядок `1, 3, 2` из конспекта.
- `findUserAsync(0)` попадает именно в `catch`, а не роняет процесс.
- В `catch` у ошибки есть `message` и стек, потому что отклоняли через `new Error(...)`.
- Ты можешь объяснить, почему строка `[api] пошёл искать` печатается **до** `await`, а не в момент `.then`.

**Ожидаемый вывод**

```
1
3
2
[api] пошёл искать пользователя 7
[ok] user-7
[api] пошёл искать пользователя 0
[fail] пользователь не найден
```

## Задание 2 — цепочка против async/await и обработка ошибок

Файл: `task-2-chain-vs-async.ts`

Два способа написать одно и то же, чтобы увидеть их эквивалентность, плюс самая частая ошибка новичка.

Что сделать:

- `withThen()` — получить канал, затем его сообщения через цепочку `.then`, добавить `.catch` и `.finally`;
- `withAsync()` — то же самое через `async/await` с `try/catch/finally`;
- `brokenChain()` — намеренно забыть `return` в `.then` и напечатать, что придёт в следующий `.then`;
- прогнать `withAsync()` на несуществующем канале и убедиться, что ошибка ловится, а `finally` всё равно срабатывает.

**Критерии**

- Оба варианта дают одинаковый результат — это разный синтаксис, а не разная механика.
- В `brokenChain()` следующий `.then` получает `undefined`, и понятно почему.
- `finally` выполняется и при успехе, и при ошибке (в реальном коде там выключают спиннер загрузки).
- Ошибка обрабатывается **один раз**: нет ситуации, когда её ловит и `catch`, и внешний код.

**Ожидаемый вывод**

```
[then] канал general, сообщений 2
[then] finally: спиннер выключен
[async] канал general, сообщений 2
[async] finally: спиннер выключен
[broken] что пришло в следующий then: undefined
[error] канал не найден
[error] finally: спиннер выключен
```

## Задание 3 — последовательно против параллельно

Файл: `task-3-parallel.ts`

Это то, чего нет в лекции, но что важнее всего на практике: не заставлять пользователя ждать сумму всех задержек.

Что сделать:

- загрузить три независимых ресурса последовательно через три `await` и замерить время;
- загрузить их же одновременно через `Promise.all` и замерить время;
- показать, что `Promise.all` падает целиком, если упал хоть один промис;
- сделать то же через `Promise.allSettled` и напечатать статусы всех трёх.

**Критерии**

- Последовательный вариант занимает примерно сумму задержек, параллельный — примерно максимальную из них.
- Ты можешь объяснить, почему `Promise.all` вообще способен работать параллельно (подсказка: промисы «горячие», операция уже идёт).
- В варианте с `Promise.all` и ошибкой результат остальных промисов теряется, а в `allSettled` — нет.
- Понятно, в каком случае в реальном коде нужен `allSettled`, а не `all`.

**Ожидаемый вывод**

```
последовательно: ~500 мс
параллельно: ~300 мс
Promise.all упал целиком: сервер недоступен
allSettled: fulfilled, rejected, fulfilled
```
