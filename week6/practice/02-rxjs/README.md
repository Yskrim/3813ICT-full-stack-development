# 02 — RxJS: Subject, BehaviorSubject, контракт потока

Конспекты: `6-1-observables.md`, `6-1-Observables-explained.md`.

Зачем это на практике: это ровно тот код, который ты будешь писать в Angular-сервисах. Здесь же ловятся два бага, на которые все наступают: «поздний подписчик увидел пустоту» и «после ошибки поток умер, а я жду сообщений».

Запуск: `node 02-rxjs/task-1-contract.ts`

## Задание 1 — три способа подписки и контракт потока

Файл: `task-1-contract.ts`

Что сделать:

- подписаться на `Subject<string>` тремя способами: одной функцией, объектом с частью колбэков и классом, который `implements Observer<string>`;
- отправить значение, затем вызвать `complete()`, затем отправить ещё одно;
- на отдельном `Subject` показать, что происходит после `error()`;
- подписаться на уже завершённый `Subject` и посмотреть, что получит такой подписчик.

**Критерии**

- Понятно, почему у класса пришлось реализовать все три метода, а у объекта — только нужные (подсказка: `Observer<T>` против `Partial<Observer<T>>`).
- После `complete()` ни один `next` не доходит ни до кого.
- После `error()` не приходит ни `next`, ни `complete`: завершающее событие только одно.
- Подписка на уже завершённый Subject получает `complete` немедленно и ни одного значения.
- Ошибка передана как `new Error(...)`, а не строкой.

**Ожидаемый вывод**

```
[fn] первое
[obj] первое
[class] первое
[obj] поток закрыт
[class] поток закрыт
[late] подписался после complete → сразу complete
[err] next: до ошибки
[err] error: сокет отвалился
```

Порядок строк зависит от порядка твоих вызовов — сверяй по смыслу, а не побуквенно. Важно, чего в выводе **нет**: значения после `complete`, значения после `error` и `complete` после `error`.

## Задание 2 — сервис-хранилище состояния

Файл: `task-2-state-service.ts`

Напиши `ChatStore` — то, что в Angular станет сервисом с `@Injectable({ providedIn: 'root' })`. Он хранит список сообщений текущего канала и раздаёт его всем желающим.

Что сделать:

- внутри `private messages$ = new BehaviorSubject<Message[]>([])`;
- наружу метод `getMessages(): Observable<Message[]>`, отдающий `asObservable()`;
- метод `addMessage(message)` — добавляет сообщение и рассылает **новый** массив (не мутирует прежний: в Angular от этого зависит обновление шаблона);
- метод `getCurrent(): Message[]` через `getValue()`;
- два «компонента»-подписчика: первый подписывается сразу, второй — после того как пришло два сообщения.

**Критерии**

- Снаружи нельзя вызвать `next()` у `messages$` — наружу уходит только `Observable`.
- Второй подписчик сразу при подписке получает уже накопленные два сообщения, а не пустой массив.
- `addMessage` не мутирует предыдущий массив: старая ссылка остаётся прежней длины.
- Оба подписчика получают одно и то же значение при следующем `addMessage` — поток общий.

**Ожидаемый вывод**

```
[список] сообщений: 0
[список] сообщений: 1
[список] сообщений: 2
[сайдбар] сообщений: 2
[список] сообщений: 3
[сайдбар] сообщений: 3
старая ссылка не изменилась: true
```

## Задание 3 — отписка, утечка и правильное завершение

Файл: `task-3-unsubscribe.ts`

Самое важное задание темы: здесь исправляется ошибка из слайдов лекции, где предлагалось `subject.unsubscribe(observer)`.

Что сделать:

- создать `Subject<string>`, подписать двух подписчиков `[A]` и `[B]`;
- отписать только `[A]` и убедиться, что `[B]` продолжает получать;
- вызвать `stream$.unsubscribe()` (без аргументов!) и в `try/catch` попробовать отправить значение — напечатать имя поймавшейся ошибки;
- на отдельном `Subject` показать правильное завершение через `complete()`: подписчики получают `complete`, дальнейшие `next` просто игнорируются без исключений;
- написать класс `FakeComponent` с методами `init()` и `destroy()` — аналог `ngOnInit`/`ngOnDestroy`, где `destroy()` отписывается, и показать, что после `destroy()` сообщения не обрабатываются.

**Критерии**

- Отписка одного подписчика не задевает остальных.
- Ты можешь своими словами объяснить, чем `subscription.unsubscribe()` отличается от `subject.unsubscribe()`.
- После `subject.unsubscribe()` вызов `next` бросает `ObjectUnsubscribedError` — и понятно, почему в прикладном коде так делать не надо.
- После `complete()` вызовы `next` безопасны и просто ничего не делают.
- `FakeComponent.destroy()` действительно останавливает обработку: счётчик обработанных сообщений после destroy не растёт.

**Ожидаемый вывод**

```
[A] первое
[B] первое
[B] второе
поймали: ObjectUnsubscribedError
[C] next: перед завершением
[C] complete
компонент обработал до destroy: 2
компонент обработал после destroy: 2
```
