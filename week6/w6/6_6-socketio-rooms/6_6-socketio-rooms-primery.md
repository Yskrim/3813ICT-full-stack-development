## Пример 1. Namespace и room решают разные задачи

Представь сервер учебной платформы. Namespace `/admin` отделяет административные события приложения. Внутри обычного `/` комнаты `course-3813` и `study-group-a` выбирают разные группы участников.

```text
Socket.IO сервер
├── namespace /
│   ├── room course-3813
│   └── room study-group-a
└── namespace /admin
```

В [6.5](6_5-sockets-coding-konspekt.md#s1) мы отправляли сообщение всем. Здесь добавляем адресную группу, чтобы ограничить аудиторию.

## Пример 2. Вступление после проверки

Упрощённая схема обработчика:

```js
io.on('connection', (socket) => {
  socket.on('join-room', async ({ roomId }, acknowledge) => {
    const allowed = await canJoinRoom(socket.data.user, roomId);
    if (!allowed) {
      acknowledge?.({ ok: false, error: 'forbidden' });
      return;
    }

    await socket.join(roomId);
    acknowledge?.({ ok: true });
  });
});
```

`canJoinRoom` здесь обозначает проверку приложения. Её нужно реализовать по собственной модели пользователей и комнат; Socket.IO не знает сам по себе, кому разрешено вступать.

## Пример 3. Рассылка участникам комнаты

```js
// Включает отправителя, если тот является участником комнаты
io.to(roomId).emit('new-message', message);

// Исключает текущий socket
socket.to(roomId).emit('new-message', message);
```

Перед рассылкой также проверь, что отправитель действительно состоит в комнате и имеет право писать. Имена событий должны соответствовать тому, что клиент слушает через `socket.on`.

## Пример 4. Переподключение и socket.id

Пользователь подключился: `socket.id = "abc"`. Сеть оборвалась, клиент подключился заново: новое соединение может получить другой id, например `"xyz"`. Поэтому для восстановления пользовательской сессии используй проверенную идентичность приложения (например, пользователя из auth middleware), а не сохраняй `socket.id` как постоянный user ID. ⚠ [П-4](6_6-socketio-rooms-popravki.md#p-4)
