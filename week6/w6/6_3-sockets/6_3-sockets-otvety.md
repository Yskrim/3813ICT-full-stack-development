## Понимание понятий

1. **Сокет** — программная точка взаимодействия с сетевым соединением. Для TCP-сервера один сокет может слушать подключения, а принятый сокет представляет соединение с конкретным клиентом.
2. IP-адрес указывает на сетевой интерфейс узла, а порт помогает системе выбрать приложение. Для TCP endpoint обычно записывают вместе IP и порт.
3. Слушающий сокет ждёт новые подключения. Принятый сокет используется для обмена с одним подключившимся клиентом. Поэтому сервер может одновременно продолжать принимать других клиентов.
4. ОС назначает клиенту временный свободный порт. Приложению обычно важно знать адрес и порт сервера, куда подключаться, а не вручную резервировать клиентский порт.
5. Двунаправленный обмен означает, что каждая сторона может отправлять данные другой стороне. В постоянном соединении сервер может отправить событие без ожидания нового запроса от браузера.

## Связь между уровнями

6. Это разные уровни. TCP доставляет поток данных между endpoint; `chat:message` — понятное приложению событие, которое библиотека передаёт через сетевой протокол.
7. Observable из 6.1 — модель уведомлений и подписки в приложении. TCP-сокет — механизм сетевого соединения. Observable может представлять события, которые поступили через сокет, но сам сокет не становится RxJS Observable автоматически.
8. Promise подходит, когда операция возвращает один итог, например Promise установления соединения или Promise подтверждения одного запроса (если конкретный API так устроен). Для непрерывных входящих сообщений удобнее потоковая модель вроде Observable или обработчики событий.
9. При открытом соединении сервер может передать новое событие сразу. Клиенту не нужно регулярно отправлять запросы только ради проверки, появилось ли обновление.
10. Socket.IO имеет собственный протокол и API событий, а WebSocket — транспортный протокол. Socket.IO может использовать WebSocket, но обычный WebSocket-клиент не разговаривает с Socket.IO-сервером напрямую.

## Применение

11. Обычно приложение-сервер заранее выбирает порт `4000` и начинает его слушать. Клиентский порт часто временный и назначается системой.
12. Принятое соединение обслуживает этого клиента отдельно. Слушающий сокет остаётся нужен, чтобы принимать новые подключения на том же адресе сервера.
13. Интерфейс отправителя вызывает клиентскую библиотеку; та кодирует и передаёт данные по выбранному транспорту серверу. Сервер обрабатывает событие и отправляет его нужному клиенту или группе, после чего обработчик интерфейса получателя обновляет экран.
14. Пока синхронная работа не отдаёт управление, цикл событий не может обработать другие ожидающие callback-и. Поэтому соседние подключения могут получить задержку. Сам факт использования sockets не устраняет блокирующую работу.
15. Нет. Socket.IO может использовать HTTP long-polling, если WebSocket недоступен. Конкретное поведение зависит от конфигурации и доступных транспортов.

Например: **TCP** — канал доставки данных между двумя сетевыми endpoint; **WebSocket** — способ обмениваться сообщениями в обе стороны через открытое соединение; **Socket.IO** — библиотека событий, которая добавляет свой протокол и удобства, например переподключение, и может выбирать транспорт.
