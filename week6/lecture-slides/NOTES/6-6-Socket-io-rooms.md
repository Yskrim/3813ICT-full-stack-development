# Socket.IO — Namespaces и Rooms

Лекция на 4 слайда, и она про то, как разделить один сокет-сервер на логические каналы. Для ассайнмента это самая практичная часть недели: группы и каналы в чате делаются именно комнатами. Содержание слайдов верное, но неполное, и ссылка в них ведёт на документацию v2 — актуальные разделы это `socket.io/docs/v4/rooms/` и `socket.io/docs/v4/namespaces/`.

### Namespaces (слайд 2)

Namespace — это разные «пути» (endpoints) на одном и том же сокет-сервере. По умолчанию используется namespace `/`, и именно его слушает сервер, если ты ничего не настраивал.

    ```js
    const nsp = io.of('/new-namespace');

    nsp.on('connection', (socket) => {   // у каждого namespace своё событие connection
        console.log('подключился в /new-namespace');
    });
    ```

Клиент подключается к namespace через путь в URL:

    ```ts
    const socket = io('http://localhost:3000/new-namespace');
    ```

Важное, чего в слайде нет: несколько namespace **не создают несколько TCP-соединений**. Они мультиплексируются по одному физическому соединению, так что это дешёвое разделение. И набор событий у каждого namespace свой — `nsp.on('message')` и `io.on('message')` живут независимо.

### Rooms (слайд 3)

Внутри любого namespace, включая дефолтный, сокеты можно раскладывать по произвольным каналам — это и есть комнаты.

  - Каждое подключение получает случайный уникальный `socket.id`.
  - Вход и выход из комнаты делаются **только на сервере**. Клиент может лишь попросить событием.
  - Дальше сервер, получая сообщение, обязан сначала понять, в какой комнате находится этот сокет, и разослать только в неё.

    ```js
    socket.join('room1');                              // добавить в комнату
    socket.leave('room1');                             // выйти
    socket.to('room1').emit('someEvent', 'message');   // всем в комнате, КРОМЕ отправителя
    io.to('room1').emit('someEvent', 'message');       // всем в комнате, включая отправителя
    ```

Вот это различие в слайде не проговорено, а оно ровно то же, что в 6.3: `socket.to(...)` исключает отправителя, `io.to(...)` — нет. Для чата с локальным добавлением своего сообщения нужен `socket.to`, иначе автор увидит дубль.

Комнату не надо создавать заранее: она появляется при первом `join` и исчезает, когда её покинул последний сокет. Имя комнаты — просто строка. Можно войти сразу в несколько:

    ```js
    socket.join(['room1', 'room2']);
    ```

### Три вещи про комнаты, которых в лекции нет

**1. Каждый сокет автоматически лежит в комнате со своим `socket.id`.**

    ```js
    io.on('connection', (socket) => {
        console.log(socket.rooms);   // Set { <socket.id> }
        socket.join('room1');
        console.log(socket.rooms);   // Set { <socket.id>, 'room1' }
    });
    ```

`socket.rooms` — это `Set`. А следствие полезное: личные сообщения не требуют никакого отдельного механизма, достаточно отправить в комнату с идентификатором нужного сокета:

    ```js
    socket.on('say to someone', (id, msg) => {
        socket.to(id).emit('my message', msg);   // личное сообщение конкретному клиенту
    });
    ```

**2. Комнаты не сохраняются между подключениями.** Всё членство хранится в памяти адаптера (две карты: `sids` — сокет к его комнатам, и `rooms` — комната к её сокетам). Поэтому при реконнекте клиент получает **новый** `socket.id` и оказывается вне всех комнат: заново заходить в комнату обязан сервер, обычно по событию от клиента после переподключения. То же при рестарте сервера — членство теряется полностью, а вот сами сообщения должны лежать в БД, иначе исчезнут.

**3. Есть два события выхода, и они не равнозначны.** В момент `disconnecting` комнаты ещё доступны, а в `disconnect` их уже нет:

    ```js
    socket.on('disconnecting', () => {
        console.log(socket.rooms);            // ещё содержит комнаты — можно уведомить их
        socket.rooms.forEach((room) => socket.to(room).emit('user-left', socket.id));
    });

    socket.on('disconnect', () => {
        // socket.rooms.size === 0 — уведомлять уже некого
    });
    ```

Если хочешь показывать «пользователь вышел из канала», делать это надо в `disconnecting`.

### Workflow из слайда 4, с добавленной проверкой прав

Порядок в лекции описан правильно: соединение создаёт `socket.id`, клиент присылает событие с именем комнаты, сервер запоминает, кто в какой комнате, дальше сообщения расходятся только по нужной комнате. Но в слайдах пропущен ключевой шаг: сервер обязан **проверить, имеет ли пользователь право** на этот канал. Иначе любой клиент отправит `join` с чужим `roomId` и будет читать переписку, куда его не приглашали.

    ```js
    io.on('connection', (socket) => {
        socket.on('join-channel', async (channelId) => {
            const userId = socket.data.userId;                       // положили при аутентификации

            if (!(await userCanAccess(userId, channelId))) {         // проверка на сервере
                socket.emit('join-denied', channelId);
                return;
            }

            socket.join(channelId);
            socket.data.channelId = channelId;                       // помним текущий канал
            socket.to(channelId).emit('user-joined', userId);
        });

        socket.on('message', async (text) => {
            const channelId = socket.data.channelId;                 // берём с СЕРВЕРА, не из сообщения
            if (!channelId) return;

            const message = await saveMessage(channelId, socket.data.userId, text);
            io.to(channelId).emit('new-message', message);
        });
    });
    ```

Два принципа, которые стоит запомнить из этого кода. Первый: никогда не бери `roomId` из присланного сообщения — бери из состояния сокета на сервере, иначе клиент сможет писать в любой канал. Второй: `socket.data` — штатное место для своих данных, привязанных к соединению (в v4 это официальное поле), и именно там держат `userId` после проверки на handshake.

Аутентификация ставится в middleware, до `connection`:

    ```js
    io.use((socket, next) => {
        const token = socket.handshake.auth.token;
        const user = verifyToken(token);
        if (!user) return next(new Error('unauthorized'));
        socket.data.userId = user.id;
        next();
    });
    ```

### Namespaces или rooms — что выбрать

Для чата с группами и каналами нужны **комнаты**, а не namespace. Разница в природе: комнаты динамические, их создаёт и раздаёт сервер во время работы, вход и выход происходят постоянно. Namespace задаются кодом заранее и разделяют целые куски приложения — например `/chat` и `/admin`, где вообще разный набор событий и своя логика подключения. Создавать namespace на каждый канал чата — плохая идея: их нельзя удобно перечислять и создавать на ходу.

И ещё одно, если дойдёт до нескольких процессов Node (`cluster` или несколько инстансов): комнаты живут в памяти **одного** процесса, поэтому клиенты на разных инстансах друг друга не увидят. Лечится это адаптером, обычно Redis-адаптером, который синхронизирует рассылку между процессами.
