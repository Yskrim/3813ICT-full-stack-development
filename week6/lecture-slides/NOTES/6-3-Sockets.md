# Sockets

Лекция короткая (7 слайдов) и очень поверхностная: рассказывает про TCP-сокеты, называет это WebSockets, а socket.io упоминает одним слайдом без единой строчки кода. Ниже: что верно, что перепутано, и то, чего в ней нет, но без чего чат в ассайнменте не написать.

### Почему Node хорош для realtime (слайд 2)

Что в лекции верно:

- Node крутит один event loop вместо «поток на каждый запрос», поэтому нет переключения контекста и огромных стеков в памяти.
- Node не простаивает в ожидании I/O (БД, файлы, сеть) — отдал запрос и пошёл обслуживать следующий.
- WebSockets в Node реализуются очень просто, отсюда и realtime.

Что упрощено:

- «Single thread» относится к **твоему JS-коду**. Под капотом libuv держит пул потоков (по умолчанию 4) для файловой системы, DNS и crypto, плюс существуют `worker_threads` и `cluster`.
- Сравнение с Apache «поток на запрос» устарело (у Apache есть event MPM, а типовой конкурент сейчас nginx), но сама идея верна.

Практический вывод, которого в лекции нет: раз поток один, то **один тяжёлый синхронный участок кода блокирует всех клиентов сразу**. Большой цикл, `JSON.parse` на десятки мегабайт, синхронный bcrypt — и чат «завис» у всех одновременно, а не только у того, кто это вызвал.

### Что такое сокет (слайды 3–5)

- Сокет — это один конец двусторонней связи между двумя программами по сети.
- Endpoint = IP-адрес + номер порта. TCP-соединение однозначно определяется **парой** endpoints, поэтому с одним и тем же сервером можно держать много соединений одновременно.
- Механика установки: сервер делает bind на порт и слушает (`listen`), клиент подключается к паре хост+порт, свой локальный порт ему обычно выдаёт ОС автоматически (ephemeral port).
- Сервер принимает соединение (`accept`) и получает **новый** сокет под этого клиента, а слушающий сокет продолжает висеть на том же порту и ждать следующих. Это ответ на вопрос со слайда 5 «зачем нужен новый сокет»: чтобы обслуживать подключённого и одновременно слышать новых.

### Путаница №1: WebSocket — это не TCP-сокет

Слайды 3–5 озаглавлены «WebSockets», но описывают обычные TCP-сокеты (Berkeley sockets API). Это разные уровни, и путать их нельзя.

WebSocket — это **протокол поверх HTTP и TCP**. Соединение начинается как обычный HTTP-запрос со специальными заголовками:

    ```http
    GET /socket HTTP/1.1
    Host: localhost:3000
    Upgrade: websocket
    Connection: Upgrade
    Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
    ```

Сервер отвечает `101 Switching Protocols`, и после этого **то же самое** TCP-соединение перестаёт быть «запрос-ответ» и становится двусторонним каналом сообщений. Схемы адресов — `ws://` и `wss://` (второй через TLS, как `https`).

Почему это важно на практике:

- Из браузера **нельзя** открыть произвольный TCP-сокет. Доступен только WebSocket (ну и WebRTC/WebTransport). Так что «сокеты» в веб-разработке всегда означают WebSocket.
- Отличие от обычного HTTP: в HTTP сервер не может заговорить первым, он только отвечает на запросы. В WebSocket соединение живёт, и сервер пушит данные сам, когда захочет. Именно это даёт realtime.
- Альтернатива без сокетов — опрос (`setInterval` + запрос каждую секунду). Это и задержка, и мусорный трафик, и нагрузка на сервер на пустом месте.

### Путаница №2: Socket.IO — это не WebSocket

Слайд 6 называет socket.io «самым используемым websocket-пакетом», и это формулировка, из которой вырастают часы отладки. В документации socket.io написано прямым текстом: **Socket.IO не является реализацией WebSocket**. Он использует WebSocket как транспорт, когда может, но добавляет к сообщениям свои метаданные и свой протокол handshake.

Три следствия, которые надо запомнить:

1. `socket.io-client` **не подключится** к «чистому» WebSocket-серверу — даже если явно указать `transports: ['websocket']`.
2. Браузерный `new WebSocket('ws://localhost:3000')` **не подключится** к socket.io-серверу.
3. Версии клиента и сервера должны быть совместимы: socket.io v2 и v3/v4 между собой не разговаривают. Классическая причина «ничего не работает, а код правильный».

Что socket.io даёт сверх сырого WebSocket (по официальной документации): fallback на HTTP long-polling, если WebSocket недоступен; автоматический реконнект; acknowledgements (подтверждение доставки); broadcast сразу многим; масштабирование на несколько инстансов сервера; восстановление состояния после короткого разрыва. По умолчанию соединение стартует long-polling-ом и потом апгрейдится до WebSocket (опция `upgrade` включена).

### Чего в лекции нет: минимальный рабочий код

Сервер, socket.io v4:

    ```js
    const express = require('express');
    const { createServer } = require('node:http');
    const { Server } = require('socket.io');

    const app = express();
    const server = createServer(app);              // socket.io цепляется к http-серверу, а не к app
    const io = new Server(server, {
        cors: { origin: 'http://localhost:4200' }  // Angular dev-server: тот же CORS, что в week5
    });

    io.on('connection', (socket) => {              // событие на каждое новое подключение
        console.log('подключился', socket.id);

        socket.on('chat message', (msg) => {       // слушаем событие от этого клиента
            io.emit('chat message', msg);          // рассылаем всем подключённым
        });

        socket.on('disconnect', (reason) => {
            console.log('ушёл', socket.id, reason);
        });
    });

    server.listen(3000);
    ```

Клиент:

    ```ts
    import { io } from 'socket.io-client';   // в v4 именно так; `import * as io` из слайдов 6.4 — это стиль v2

    const socket = io('http://localhost:3000');

    socket.on('chat message', (m) => console.log('пришло:', m));
    socket.emit('chat message', 'привет');
    ```

Обрати внимание на асимметрию имён: на сервере подключение ловится через `io.on('connection', ...)`, а дальше всё общение идёт через объект `socket` конкретного клиента.

### Кто что получает при emit

Самое частое место ошибок: сообщение либо дублируется у автора, либо наоборот до него не доходит.

| Вызов                         | Кому уйдёт                             |
| ----------------------------- | -------------------------------------- |
| `socket.emit(...)`            | только этому одному клиенту            |
| `io.emit(...)`                | всем подключённым, включая отправителя |
| `socket.broadcast.emit(...)`  | всем, кроме отправителя                |
| `io.to('room').emit(...)`     | всем в комнате                         |
| `socket.to('room').emit(...)` | всем в комнате, кроме отправителя      |

Для чата, где отправитель сам добавляет своё сообщение в список локально, нужен `socket.broadcast.emit`. Если же список рисуется только из того, что вернул сервер, — нужен `io.emit`.

### Комнаты (rooms)

Для каналов и групп в ассайнменте:

    ```js
    socket.join("channel-42"); // добавить сокет в комнату
    io.to("channel-42").emit("chat message", msg); // отправить только в неё
    socket.leave("channel-42");
    ```

Комната — это просто строковый идентификатор, отдельно создавать её не надо, она возникает при первом `join`. Управление комнатами живёт **только на сервере**, клиент про них ничего не знает и сам себя в комнату добавить не может (и это правильно с точки зрения безопасности).

### Что помнить про состояние и надёжность

  - `socket.id` меняется при каждом переподключении, поэтому он **не** идентификатор пользователя. Держи своё соответствие «userId ↔ socket» на сервере.
  - Соединение и все комнаты живут в памяти процесса: при рестарте сервера они теряются. Сообщения обязаны лежать в БД, иначе история исчезает — в официальном туториале socket.io ровно для этого прикручивают sqlite.
  - Доставка не гарантирована: при разрыве часть событий может пропасть. В v4 есть `connectionStateRecovery`, но по умолчанию он выключен.
  - Аутентификация делается на handshake: клиент передаёт `auth` при подключении, сервер проверяет в middleware `io.use((socket, next) => ...)`. В лекции про это ни слова, а в ассайнменте пользователи есть, и без проверки любой сможет слушать чужие каналы.
  
### Как это стыкуется с предыдущими лекциями

  - **6.0/6.1 (обзерверы).** `socket.on('event', handler)` — это готовый паттерн Observer внутри библиотеки: сокет — Subject, твой колбэк — Observer. В лекции 6.4 его завернут в `Observable`, чтобы получить операторы RxJS.
  - **6.2 (промисы).** Промис здесь принципиально не подходит: он срабатывает один раз, а сообщений будет много. Поэтому сокет — всегда Observable или колбэк, но не Promise.
  - **week5 (CORS).** Тот же самый барьер origin, но настраивается отдельно — в опциях `new Server(server, { cors: ... })`, а не через `app.use(cors())` в Express. Легко забыть и полчаса смотреть на ошибку в консоли браузера.
  
  Заодно про устаревший код в слайдах 6.4: там написано `import * as io from 'socket.io-client'` и `Observable.create(...)`. В актуальных версиях правильно `import { io } from 'socket.io-client'` и `new Observable(...)` — `Observable.create` объявлен устаревшим.
