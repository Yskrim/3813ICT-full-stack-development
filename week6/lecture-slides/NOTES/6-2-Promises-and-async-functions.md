# Promises and async functions

### Promises

- другой популярный подход к вопросу асинк ивентов.

Promise — это объект-обещание одного результата. Именно поэтому в слайдах написано «a Promise is treated as a value» — с ним работают как со значением, которого пока нет, но оно будет.

У промиса три состояния:

1. pending (ждём),
2. fulfilled (получилось, значение отдано через resolve) и
3. rejected (не получилось, причина отдана через reject).

Переход происходит ровно один раз и навсегда — после этого промис заморожен, его результат не изменится и заново он не запустится. Отсюда и фраза из лекции «can't be used after that».

И вот главное отличие от Observable, которое надо забить в голову сразу: Promise запускается немедленно, в момент создания. Посмотри на пример из слайдов:

```ts
function openURL(url) {
    return new Promise((resolve, reject) => {
        const xhr = new XMLHttpRequest();
        xhr.open("GET", url);
        xhr.onload = () => resolve(xhr.responseText);
        xhr.onerror = () => reject(xhr.statusText);
        xhr.send(); // запрос уходит здесь
    });
}
const data = openURL("example.com"); // ЗАПРОС УЖЕ ПОШЁЛ, до всякого then
data.then((d) => console.log(d)); // просто говорим, что делать с результатом
```

- Функция внутри new Promise выполняется сразу и синхронно.
- then ничего не запускает — он лишь регистрирует колбэк на уже летящий результат.

Обычный Observable ведёт себя ровно наоборот: пока нет subscribe, не выполняется ничего. Это та самая «холодность» из прошлого разговора.

Второе следствие: промис нельзя отменить. У него нет unsubscribe. Раз запрос уже ушёл, ты можешь только проигнорировать результат. (Отменить сам HTTP-запрос можно через AbortController, но это механизм fetch, а не промиса.)

##### Ошибка в слайде про fetch:
В лекции написано так:

```ts
let response = fetch("example.com");
response.then((response) => {
    console.log("Data received: " + response.body); // так НЕ работает
});
```

`Response.body` — это не данные, а ReadableStream, то есть поток байтов. 
При склейке со строкой ты получишь буквально Data received: [object ReadableStream], а не JSON. Слайд сам себе противоречит: следующий слайд с чейнингом делает правильно.

Данные достают методами, каждый из которых сам возвращает промис, потому что тело ещё дочитывается из сети: 
- response.json(), 
- response.text(), 
- response.blob(). 
Отсюда и берётся цепочка из слайда 7.

Заодно две вещи, которых в лекции нет, но без них ты напишешь битый код:
  1. Первая: fetch отклоняет промис только при сетевой ошибке, а на HTTP-ответы 404 и 500 он преспокойно резолвится, потому что ответ-то получен. Проверять надо руками через response.ok.

  2. Вторая: fetch("example.com") без схемы — это относительный путь, а не домен; нужно https://example.com.

Правильный вариант целиком:
  ```ts
  const response = await fetch("https://example.com/movies.json");
  if (!response.ok) {
      throw new Error("HTTP " + response.status); // 404 и 500 сами по себе НЕ ошибка для fetch
  }
  const movies = await response.json();
  ```

### Как работает чейнинг
Механика в одном правиле: то, что ты вернул из .then, определяет, что получит следующий .then.
  - Вернул обычное значение — оно автоматически завернётся в промис и придёт дальше как есть.

  - Вернул промис — цепочка дождётся его и передаст дальше уже развёрнутый результат. На этом и держится пример из слайдов:

  ```ts
  fetch("http://example.com/movies.json")
      .then((response) => response.json()) // вернули ПРОМИС → следующий then ждёт его
      .then((myJson) => console.log(myJson)); // здесь уже готовый объект, а не промис
  ```

Самая частая ошибка новичка здесь — забыть `return`. 
Если написать `.then((response) => { response.json(); })`, то из колбэка вернётся `undefined`, следующий `.then` получит `undefined`, и ты полчаса будешь искать, куда делись данные.

Про ошибки:
  - одного .catch() в конце цепочки достаточно на все шаги — исключение или reject на любом этапе пролетает мимо всех then прямо в catch.
  
  - Есть ещё .finally(), который выполнится в любом случае (удобно гасить спиннер загрузки).
  
  - В слайдах показан только вариант с двумя колбэками в then — он работает, но в реальном коде пишут .catch(), потому что он ловит ещё и ошибки, брошенные внутри самого then.

Мелочь по стилю из примера с XHR:
  `reject(xhr.statusText)` лучше писать как `reject(new Error(xhr.statusText))` — отклонять промис принято объектом `Error`, чтобы был стек вызовов.

### async/await
  - async/await — это тот же промис, просто читаемее
    
    Тут лекция права: await разворачивает промис, а код становится похож на последовательный. Две вещи из слайдов, которые стоит уточнить.

  - «await можно использовать только внутри async-функции» — это уже устарело.

    В ES-модулях работает top-level await, то есть await прямо на верхнем уровне файла, без обёртки. В Angular-компонентах ты всё равно будешь внутри методов, так что практической разницы мало, но знать полезно.

  - «async-функция может возвращать только промис» — верно, и это важно понимать буквально: если ты написал `return true`, наружу уйдёт Promise<boolean>, а не boolean. 
  Поэтому вызов такой функции тоже требует await.

  - Ошибки в async/await ловятся обычным try/catch, и это, пожалуй, главный выигрыш в читаемости:

  ```ts
  async function loadMovies() {
      try {
          const response = await fetch("/api/movies");
          if (!response.ok) throw new Error("HTTP " + response.status);
          return await response.json();
      } catch (err) {
          console.error("Не смогли загрузить:", err);
          return [];
      } finally {
          this.loading = false;
      }
  }
  ```

Чего в лекции нет: 
  - последовательно против параллельно
  
  Посмотри на пример из слайда 11 внимательно:
  ```ts
  const slow = await resolveAfter2Seconds();
  const fast = await resolveAfter1Seconds();
  ```
  Это займёт три секунды, а не две. Потому что await буквально останавливает функцию: второй запрос даже не начнётся, пока не завершится первый. Если запросы друг от друга не зависят, так делать нельзя — это самая распространённая проблема производительности в коде на async/await.

  Когда операции независимы, их запускают все сразу и ждут вместе:
  ```ts
  const [slow, fast] = await Promise.all([
      resolveAfter2Seconds(),
      resolveAfter1Seconds(),
  ]);
  // две секунды: оба промиса стартовали одновременно
  ```

  Работает это именно потому, что промисы «горячие»:
    - вызов функции уже запустил операцию, а Promise.all только дожидается результатов.
    - Рядом живут Promise.allSettled (дождаться всех, даже если часть упала),
    - Promise.race (первый закончившийся) и
    - Promise.any (первый успешный).
    - Promise.all, кстати, падает целиком, если упал хоть один из промисов.

  Маленькая деталь, которая объясняет порядок вывода:

  - Колбэки then всегда выполняются асинхронно, даже если промис уже разрешён. Они складываются в очередь микрозадач и запускаются только после того, как текущий синхронный код добежал до конца:

  ```ts
  console.log("1");
  Promise.resolve().then(() => console.log("2"));
  console.log("3"); // выведет 1, 3, 2
  ```

Знание этого избавляет от вопроса «почему мой console.log печатается раньше данных».

### Promise <=> Observable
  Последний слайд показывает превращение промиса в Observable через from:

  ```ts
  import { from } from "rxjs";
  const data = from(fetch("/api/endpoint"));
  data.subscribe({
      next: (response) => console.log(response),
      error: (err) => console.error("Error: " + err),
      complete: () => console.log("Completed"),
  });
  ```

Полученный Observable отдаст ровно одно значение и сразу вызовет complete — потому что у промиса больше нечего отдавать.

Два подвоха, о которых лекция молчит.

  1. Первый: fetch внутри from(...) запустился в момент этой строки, ещё до subscribe, так что настоящей ленивости здесь нет; если она нужна, берут defer(() => fetch(...)).
  2. Второй: unsubscribe() у такого Observable не отменит запрос — отменять нечего, промис неотменяем.

  Обратное превращение тебе понадобится не реже: чтобы применить await к Observable из Angular, в RxJS 7 есть firstValueFrom и lastValueFrom (старый toPromise() объявлен устаревшим):
  
  ```ts
  const user = await firstValueFrom(this.http.get<User>("/api/user"));
  ```

  Важно понимать, что при этом ты теряешь: 
    - остаётся одно значение вместо потока, 
    - пропадает возможность отменить и пропадают операторы. 
    - Для одиночного HTTP-запроса это нормальная и часто более читаемая сделка.

Сводка отличий, которую стоит держать в голове:

|                   | Promise            | Observable               |
| ----------------- | ------------------ | ------------------------ |
| Сколько значений  | ровно одно         | от нуля до бесконечности |
| Когда запускается | сразу при создании | при subscribe            |
| Отмена            | нет                | unsubscribe()            |
| Нужна библиотека  | нет, встроен в JS  | да, RxJS                 |
| Преобразования    | then-цепочки       | 100+ операторов в pipe   |

Практический вывод для твоего курса:
  - Одиночный HTTP-запрос — годится и то, и другое, и async/await часто читается лучше.
  - Сокеты, события форм, любой поток во времени — только Observable, промис там физически не подходит, потому что умеет сработать один раз.
  - А в Angular HttpClient всё равно отдаёт Observable, так что выбор сводится к тому, подписываешься ты через subscribe или разворачиваешь в await через firstValueFrom.
