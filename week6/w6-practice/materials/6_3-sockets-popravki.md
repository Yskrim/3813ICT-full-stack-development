## П-1. Почему Node.js быстрый 🟡

### Как в материале

Перечислены причины быстроты Node.js: он работает в одном потоке, в отличие от серверов вроде Apache, которые создают поток на каждый запрос, — это избавляет от переключения контекста процессора и больших стеков в памяти; цикл событий даёт очередь для быстрого доступа к запросам; Node не теряет время процессора на ожидание ввода-вывода. Самое главное, что даёт Node ответы в реальном времени, — он «очень хорошо использует WebSockets» и их легко реализовать.

### Пример из материала

Кода нет.

### В чём несоответствие

Суть (цикл событий, неблокирующий ввод-вывод) передана верно, но упрощения создают неверные ожидания:

1. **«Один поток» — только для JavaScript.** Код приложения выполняется в одном потоке, но Node.js использует внутренний пул потоков (libuv) для части операций: работы с файлами, криптографии, сжатия. Поэтому «Node однопоточный» — неполная картина.
2. **Обратная сторона не названа.** Раз JavaScript выполняется в одном потоке, долгое синхронное вычисление в обработчике **блокирует цикл событий**: пока оно идёт, сервер не отвечает никому. Официальное руководство Node.js посвящено этому отдельно: «не блокируйте цикл событий».
3. **WebSocket — не особенность Node.js.** WebSocket — протокол, его поддерживают серверы на любых платформах. В самом Node.js WebSocket-сервера нет; его делают библиотеками (`ws`, Socket.IO). Сила Node для реального времени — именно в модели цикла событий, которая дёшево держит много ожидающих соединений.
4. Сравнение с Apache упрощено: современные конфигурации Apache (модуль `event`) тоже не держат поток на каждое простаивающее соединение.

### Как правильно

JavaScript в Node.js выполняется в одном потоке, цикл событий вызывает обработчики, ввод-вывод неблокирующий; поэтому ожидающие соединения дёшевы, а тяжёлые синхронные вычисления вредны.

### Пример

```js
const express = require('express');
const app = express();

// ❌ Блокирует цикл событий: пока цикл крутится, сервер не отвечает НИКОМУ
app.get('/api/slow', (req, res) => {
  const end = Date.now() + 5000;
  while (Date.now() < end) {}          // 5 секунд занятого потока
  res.json({ done: true });
});

// ✅ Не блокирует: ожидание отдано системе, сервер обслуживает других
app.get('/api/wait', async (req, res) => {
  await new Promise((r) => setTimeout(r, 5000));
  res.json({ done: true });
});

app.get('/api/ping', (req, res) => res.json({ pong: true }));
app.listen(3000);

// Проверка: открой /api/slow, затем сразу /api/ping — ping ответит только через 5 с.
// С /api/wait вместо /api/slow ping ответит мгновенно.
```

**Источник:** [Node.js — Don't Block the Event Loop (or the Worker Pool)](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop) · [Node.js — The Node.js Event Loop](https://nodejs.org/en/learn/asynchronous-work/event-loop-timers-and-nexttick)

## П-2. Определение WebSocket 🟡

### Как в материале

Под заголовком «WebSockets» дано определение: сокет — одна из конечных точек двусторонней связи двух программ в сети, привязан к номеру порта, чтобы уровень TCP знал, какому приложению доставлять данные; конечная точка — комбинация IP-адреса и порта, и каждое TCP-соединение однозначно определяется двумя конечными точками. Дальше описано, как сервер слушает порт, клиент подключается, а сервер при принятии получает новый сокет.

### Пример из материала

Кода нет (схема «сервер слушает порт — клиент подключается»).

### В чём несоответствие

Это определение **TCP-сокета** — сетевого механизма операционной системы. Оно полезно как основа, но **WebSocket** — другое: это протокол прикладного уровня поверх TCP (RFC 6455), созданный для браузеров. Отличия, которых в материале нет:

- соединение WebSocket **начинается как HTTP-запрос** с заголовками `Upgrade: websocket` и `Connection: Upgrade`; сервер отвечает `101 Switching Protocols`, и дальше по тому же TCP-соединению идут сообщения WebSocket;
- обмен идёт **сообщениями**, а не потоком байтов, как у TCP;
- адреса имеют схему `ws://` или `wss://`;
- в браузере есть API `new WebSocket(url)` — а к TCP-сокетам JavaScript в браузере доступа не имеет.

Смешение понятий приводит к следующей ошибке — считать Socket.IO реализацией WebSocket ([П-3](#p-3)).

### Как правильно

TCP-сокет — конечная точка сетевого соединения (IP + порт). WebSocket — протокол поверх TCP для постоянного двустороннего обмена сообщениями между браузером и сервером; начинается с HTTP-рукопожатия `Upgrade`.

### Пример

```
Рукопожатие WebSocket (упрощённо):

→ GET /chat HTTP/1.1
  Host: example.com
  Upgrade: websocket
  Connection: Upgrade
  Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

← HTTP/1.1 101 Switching Protocols
  Upgrade: websocket
  Connection: Upgrade
  Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Дальше по этому же TCP-соединению — сообщения в обе стороны.
```

```js
// Браузерный API WebSocket
const ws = new WebSocket('wss://example.com/chat');
ws.onopen = () => ws.send('Привет');
ws.onmessage = (event) => console.log('пришло:', event.data);
```

**Источник:** [MDN — The WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API) · [MDN — Protocol upgrade mechanism](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Protocol_upgrade_mechanism) · [RFC 6455 — The WebSocket Protocol](https://datatracker.ietf.org/doc/html/rfc6455)

## П-3. «Socket.IO — пакет WebSocket» 🔴

### Как в материале

Socket.IO назван самым распространённым пакетом WebSocket для Node.js; перечислены компании, которые его используют; сказано, что это открытый проект и что на нём можно написать чат в несколько строк. Дальше слайды «Using WebSockets» переходят к коду Socket.IO, как будто это одно и то же.

### Пример из материала

Кода нет.

### В чём несоответствие

Официальная документация Socket.IO прямо говорит: **Socket.IO — не реализация WebSocket.** Он использует WebSocket как транспорт, когда может, но добавляет к каждому пакету свои метаданные (тип пакета, пространство имён, идентификатор подтверждения). Из-за этого:

- обычный WebSocket-клиент (`new WebSocket(...)`) **не сможет** подключиться к серверу Socket.IO;
- клиент Socket.IO **не сможет** подключиться к обычному WebSocket-серверу.

Это практически важно: с сервером Socket.IO в Angular работают только через пакет `socket.io-client`, а не через браузерный `WebSocket`. Кроме того, соединение Socket.IO по умолчанию начинается с HTTP long-polling и затем переходит на WebSocket.

Если нужен именно «чистый» WebSocket-сервер, документация Socket.IO рекомендует библиотеки `ws` или `uWebSockets.js`.

### Как правильно

Socket.IO — библиотека событий реального времени с собственным протоколом поверх Engine.IO; транспорты — HTTP long-polling и WebSocket (и WebTransport); обе стороны должны использовать Socket.IO.

### Пример

```ts
// ✅ Клиент Socket.IO к серверу Socket.IO
import { io } from 'socket.io-client';
const socket = io('http://localhost:3000');
socket.on('connect', () => console.log('подключено, транспорт:', socket.io.engine.transport.name));
// обычно сначала 'polling', после апгрейда — 'websocket'

// ❌ Браузерный WebSocket к серверу Socket.IO — не подключится
// const ws = new WebSocket('ws://localhost:3000');

// ❌ Клиент Socket.IO к обычному WebSocket-серверу — тоже не подключится
// io('ws://echo.websocket.org');
```
