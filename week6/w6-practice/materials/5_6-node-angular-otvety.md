## A. Структура проекта

<a id="a-1"></a>

### 1. Один репозиторий

**Ответ:** создать Angular-проект, а внутри его папки — папку `server/` с `server.js`, маршрутами и данными. Один `git push`, одна ссылка для сдачи, один `git clone` для проверяющего.

**Подробнее:** [Конспект §2](5_6-node-angular-konspekt.md#s2) · [Структура и запуск](5_6-node-angular-primery.md#run) · [← вопрос](5_6-node-angular-voprosy.md#q-1)

<a id="a-2"></a>

### 2. Общий `package.json`

**Ответ:** плюс — одна команда `npm install` ставит всё, скрипты в одном месте. Минус — зависимости клиента и сервера смешаны. `nodemon` — инструмент разработки, место ему в `devDependencies` (`npm install -D nodemon`), либо вместо него `node --watch`.

**Подробнее:** [Конспект §2](5_6-node-angular-konspekt.md#s2) · [П-1](5_6-node-angular-popravki.md#p-1) · [← вопрос](5_6-node-angular-voprosy.md#q-2)

<a id="a-3"></a>

### 3. Что устарело

**Ответ:** `@angular/http` — старый HTTP-модуль, удалён в Angular 8; сейчас `HttpClient` из `@angular/common/http`. `nodemon` стоит в `dependencies`, а должен в `devDependencies`. Сам скриншот — из Angular 6.

**Подробнее:** [П-1](5_6-node-angular-popravki.md#p-1) · [← вопрос](5_6-node-angular-voprosy.md#q-3)

## B. Сервер

<a id="a-4"></a>

### 4. Проблемы `server.js`

**Ответ:**

1. путь без `browser` — с Angular 17 `index.html` лежит в `dist/my-app/browser/`;
2. путь склеен строкой — надёжнее `path.join(__dirname, ...)`;
3. `body-parser` не нужен — есть `express.json()`;
4. маршрут без префикса `/api` — легко пересечься с маршрутами Angular, не работает прокси.

И ещё: нет fallback для F5 на маршрутах Angular.

**Подробнее:** [Конспект §3](5_6-node-angular-konspekt.md#s3) · [П-2](5_6-node-angular-popravki.md#p-2) · [← вопрос](5_6-node-angular-voprosy.md#q-4)

<a id="a-5"></a>

### 5. Обработчик в отдельном файле

**Ответ:** модуль экспортирует функцию-обработчик `(req, res)`, и она передаётся вторым аргументом в `app.post`. `express.Router()` — отдельное мини-приложение с несколькими маршрутами, которое монтируют на префикс (`app.use('/api/users', router)`); удобнее для группы связанных маршрутов.

**Подробнее:** [Конспект §4](5_6-node-angular-konspekt.md#s4) · [← вопрос](5_6-node-angular-voprosy.md#q-5)

<a id="a-6"></a>

### 6. `c = u + p`

**Ответ:**

1. `c` без `let`/`const` — глобальная переменная, общая для всех запросов (в строгом режиме — `ReferenceError`);
2. в консоль сервера выводятся имя и **пароль** — в логах паролей быть не должно.

**Подробнее:** [Конспект §4.1](5_6-node-angular-konspekt.md#s4-1) · [П-3](5_6-node-angular-popravki.md#p-3) · [← вопрос](5_6-node-angular-voprosy.md#q-6)

<a id="a-7"></a>

### 7. `throw` в колбэке

**Ответ:** исключение в асинхронном колбэке никто не перехватит — процесс Node упадёт, и сервер перестанет работать для всех. Правильно — `fs/promises` с `await` внутри `try/catch` и ответ клиенту `500`.

**Подробнее:** [Конспект §4.1](5_6-node-angular-konspekt.md#s4-1) · [П-3](5_6-node-angular-popravki.md#p-3) · [← вопрос](5_6-node-angular-voprosy.md#q-7)

<a id="a-8"></a>

### 8. Путь к файлу данных

**Ответ:** от папки, из которой запущен `node` (`process.cwd()`). Сломается, если запустить сервер из другой папки, например из `server/`. Надёжно: `path.join(__dirname, '../data/users.json')` — от папки самого файла.

**Подробнее:** [Конспект §4.3](5_6-node-angular-konspekt.md#s4-3) · [5_3 §3.6](5_3-node-hosting-konspekt.md#s3-6) · [← вопрос](5_6-node-angular-voprosy.md#q-8)

<a id="a-9"></a>

### 9. `200 { ok: false }` или `401`

**Ответ:** с `401` `HttpClient` сам передаст неудачу в `error`, а в `next` будут только успешные входы. Клиент перестаёт проверять `data.ok` и различает причины по `err.status`: `401` — неверный пароль, `400` — пустые поля, `500`/`0` — проблемы сервера.

**Подробнее:** [П-3](5_6-node-angular-popravki.md#p-3) · [Конспект §5.2](5_6-node-angular-konspekt.md#s5-2) · [← вопрос](5_6-node-angular-voprosy.md#q-9)

<a id="a-10"></a>

### 10. Что вернуть при входе

**Ответ:** профиль пользователя (id, имя, роль, дата рождения, возраст) — **без пароля**: `const { pwd, ...profile } = user`. Объект как есть содержит пароль, который окажется в браузере, в DevTools и в хранилище.

**Подробнее:** [Конспект §4.1](5_6-node-angular-konspekt.md#s4-1) · [← вопрос](5_6-node-angular-voprosy.md#q-10)

<a id="a-11"></a>

### 11. Проблемы `postLoginafter`

**Ответ:**

1. `push` при каждом входе добавляет **копию** пользователя — дубли;
2. ответ содержит **всех** пользователей — утечка данных;
3. сервер верит любым присланным данным, включая чужой `id`.

Плюс глобальная `uArrayjson` и `throw` в колбэках. Правильно — `PATCH` существующей записи по `id` с проверкой данных и ответом только этим профилем.

**Подробнее:** [Конспект §4.2](5_6-node-angular-konspekt.md#s4-2) · [П-4](5_6-node-angular-popravki.md#p-4) · [← вопрос](5_6-node-angular-voprosy.md#q-11)

<a id="a-12"></a>

### 12. Одновременная запись

**Ответ:** оба прочитают старый файл, и второй при записи затрёт изменения первого — данные потеряются. Решение — выполнять операции «прочитать → изменить → записать» по очереди (цепочка промисов), а в будущем — база данных (MongoDB, неделя 8).

**Подробнее:** [Пример 2, очередь записи](5_6-node-angular-primery.md#ex-2) · [← вопрос](5_6-node-angular-voprosy.md#q-12)

## C. Клиент

<a id="a-13"></a>

### 13. Проблемы `LoginComponent`

**Ответ:**

- **учётные данные в коде** попадают в репозиторий и собранное приложение;
- **пароль в `alert`** виден на экране;
- **запрос в компоненте** — работа с сервером должна жить в сервисе, иначе её не переиспользовать и не подменить;
- **подписка внутри подписки** — трудно читать, ошибки второго запроса не обработаны; для зависимых запросов есть `switchMap`;
- **нет `error`** — при недоступном сервере пользователь ничего не увидит.

**Подробнее:** [Конспект §5.1](5_6-node-angular-konspekt.md#s5-1) · [П-5](5_6-node-angular-popravki.md#p-5) · [← вопрос](5_6-node-angular-voprosy.md#q-13)

<a id="a-14"></a>

### 14. `setItem` с `null`

**Ответ:** в TypeScript — ошибка компиляции: `null` нельзя передать туда, где ожидается `string`. В JavaScript сохранится строка `"null"`, и при чтении получится не `null`, а непустая строка.

**Подробнее:** [П-5](5_6-node-angular-popravki.md#p-5) · [5_1 П-2](5_1-data-persistence-popravki.md#p-2) · [← вопрос](5_6-node-angular-voprosy.md#q-14)

<a id="a-15"></a>

### 15. Одна запись или четыре ключа

**Ответ:** одна запись сохраняет типы (число остаётся числом после `JSON.parse`), читается и удаляется одной операцией, не может оказаться «наполовину обновлённой». С четырьмя ключами всё становится строками, и при выходе легко забыть удалить один из них.

**Подробнее:** [П-6](5_6-node-angular-popravki.md#p-6) · [5_1 §3.4](5_1-data-persistence-konspekt.md#s3-4) · [← вопрос](5_6-node-angular-voprosy.md#q-15)

<a id="a-16"></a>

### 16. Откуда брать профиль

**Ответ:** источник правды о пользователе — сервер. Данные из формы входа — это то, что ввёл человек, а не то, что хранится; `userid: 1` вообще одинаков для всех. Сервер после проверки пароля знает настоящий профиль и должен вернуть его в ответе.

**Подробнее:** [П-5](5_6-node-angular-popravki.md#p-5) · [Конспект §5.2](5_6-node-angular-konspekt.md#s5-2) · [← вопрос](5_6-node-angular-voprosy.md#q-16)

<a id="a-17"></a>

### 17. `httpOptions` с `Content-Type`

**Ответ:** нет. Когда тело — объект, `HttpClient` сам ставит `Content-Type: application/json`.

**Подробнее:** [5_4 §8](5_4-http-requests-konspekt.md#s8) · [← вопрос](5_6-node-angular-voprosy.md#q-17)

## D. Другая страница и весь поток

<a id="a-18"></a>

### 18. `Page2Component`

**Ответ:** значения — строки или `null` (возраст не число); компонент сам знает, как устроено хранилище; нет проверки, вошёл ли пользователь. Лучше: сервис хранит пользователя одной записью и отдаёт сигнал, страница читает `auth.currentUser()`, доступ закрыт гардом.

**Подробнее:** [Конспект §6](5_6-node-angular-konspekt.md#s6) · [П-6](5_6-node-angular-popravki.md#p-6) · [← вопрос](5_6-node-angular-voprosy.md#q-18)

<a id="a-19"></a>

### 19. Новая вкладка

**Ответ:** у каждой вкладки свой sessionStorage, в новой он пуст. Варианты: оставить так (вход живёт в одной вкладке — осознанный выбор), перейти на localStorage (общий для вкладок, переживает закрытие браузера) или хранить сессию на сервере в HttpOnly-куке и спрашивать `GET /api/me`.

**Подробнее:** [П-6](5_6-node-angular-popravki.md#p-6) · [5_1 §4](5_1-data-persistence-konspekt.md#s4) · [5_1, пример 3](5_1-data-persistence-primery.md#ex-3) · [← вопрос](5_6-node-angular-voprosy.md#q-19)

<a id="a-20"></a>

### 20. Весь поток

**Ответ:**

1. `LoginComponent` вызывает `auth.login(username, pwd)`;
2. `AuthService` отправляет `POST /api/login`;
3. обработчик читает `users.json`, ищет пользователя;
4. не найден — `401`, компонент показывает ошибку;
5. найден — ответ с профилем без пароля;
6. сервис сохраняет профиль одной записью в sessionStorage и в сигнал;
7. компонент переходит на `/account`, гард пропускает;
8. `AccountComponent` читает профиль из сервиса и показывает его.

**Подробнее:** [Конспект §7, диаграмма](5_6-node-angular-konspekt.md#s7) · [Пример 1](5_6-node-angular-primery.md#ex-1) · [← вопрос](5_6-node-angular-voprosy.md#q-20)

<a id="a-21"></a>

### 21. Роль на сервере

**Ответ:** всё, что присылает клиент, можно подделать — в DevTools или через Postman. Если сервер поверит роли из запроса, любой назовётся суперадмином. Сервер определяет, кто прислал запрос, и берёт его роль из своих данных; только по ней решает — `403` или разрешить.

**Подробнее:** [Пример 2, requireRole](5_6-node-angular-primery.md#ex-2) · [5_1 §7.3](5_1-data-persistence-konspekt.md#s7-3) · [← вопрос](5_6-node-angular-voprosy.md#q-21)
