## П-1. Имена методов Web Storage 🔴

### Как в материале

На слайдах с методами localStorage и sessionStorage перечислены операции: добавить элемент, прочитать, изменить, удалить и очистить всё хранилище. Методы добавления, чтения и удаления записаны со строчной буквой `i` в слове `item`. На слайде sessionStorage в имени объекта опечатка — лишняя буква `r`. Строки взяты в типографские «кривые» кавычки. При этом на слайде с Angular-примером те же методы написаны правильно, через `setItem` и `getItem`, так что материал противоречит сам себе.

### Пример из материала

```js
localStorage.setitem(“key”,”value”);
let myvar = localStorage.getitem(“key”);
localStorage.removeitem(“key”);
localStorage.clear();

sessionStrorage.setitem(“key”,”value”);
let myvar = sessionStrorage.getitem(“key”);
```

### В чём несоответствие

- JavaScript чувствителен к регистру. У хранилища есть методы `setItem`, `getItem` и `removeItem`, с заглавной `I`. Метода `setitem` не существует, и вызов падает с ошибкой `TypeError: localStorage.setitem is not a function`.
- Опечатка в имени объекта даёт `ReferenceError: sessionStrorage is not defined`.
- Типографские кавычки `“ ”` для JavaScript не кавычки. Скопированная со слайда строка даст `SyntaxError: Invalid or unexpected token`.
- `clear()` записан верно.
- Не упомянуты два полезных члена API: свойство `length` (сколько записей) и метод `key(index)` (имя ключа по номеру). Без них нельзя перебрать содержимое хранилища.

### Как правильно

API одинаковый для localStorage и sessionStorage: `setItem(key, value)`, `getItem(key)` (возвращает строку или `null`), `removeItem(key)`, `clear()`, `length` и `key(index)`. Код со слайдов PDF не копировать, а набирать руками: вместе с ним копируются неправильные кавычки.

### Пример

```js
// Запись. Тот же метод перезаписывает существующее значение
localStorage.setItem('theme', 'dark');
localStorage.setItem('theme', 'light'); // 'dark' заменено на 'light'

// Чтение: строка, если ключ есть, и null, если нет
const theme = localStorage.getItem('theme');  // 'light'
const nothing = localStorage.getItem('nope'); // null

// Удаление одного ключа
localStorage.removeItem('theme');

// Полная очистка. Удаляет ВСЁ, что этот origin хранил в localStorage
localStorage.clear();

// Перебор всех записей через length и key(i)
for (let i = 0; i < localStorage.length; i++) {
  const key = localStorage.key(i);
  console.log(key, '→', localStorage.getItem(key));
}

// sessionStorage — ровно тот же набор методов
sessionStorage.setItem('draft:1', 'Привет');
sessionStorage.getItem('draft:1'); // 'Привет'
```

**Пояснения:**

- «Изменить» и «добавить» — одна операция `setItem`: хранилище не различает, был ключ раньше или нет.
- `clear()` удаляет данные только своего origin, чужие сайты не затрагивает. Но внутри своего origin — всё, включая то, что сохранили другие части приложения. В реальном коде обычно удаляют конкретные ключи через `removeItem`.

## П-2. «Ключ и значение должны быть строками» 🔴

### Как в материале

В начале файла сказано, что все клиентские хранилища сохраняют пары «ключ → значение» в виде строк. В пояснении к Angular-примеру добавлено, что ключ и значение, передаваемые в `setItem`, должны быть строками. Что делать с объектами, числами или массивами, не объясняется. В примере сохраняется только одна строка — фамилия `Smith`.

### Пример из материала

```ts
localStorage.setItem("lastname","Smith");
console.log(localStorage.getItem("lastname"));
```

### В чём несоответствие

Формулировка «должны быть строками» звучит так, будто иначе будет ошибка. На деле всё зависит от языка:

- **В TypeScript** ошибка действительно будет, но на этапе компиляции: `setItem` принимает только `string`, и передать объект компилятор не даст.
- **В JavaScript** (или в TypeScript с `any`) ошибки не будет. Браузер молча приведёт значение к строке, и данные испортятся без предупреждения:

| Что передали | Что сохранилось | Что вернёт `getItem` |
|---|---|---|
| `{ id: 2, username: 'anna' }` | `"[object Object]"` | `"[object Object]"` — данные потеряны |
| `42` | `"42"` | строка `"42"`, не число |
| `false` | `"false"` | строка `"false"`, которая в `if` считается **истиной** |
| `null` | `"null"` | строка `"null"`, не `null` |

Главный практический случай — пользователь чата, то есть объект с `id`, `username` и `role`. Именно его нужно хранить после логина, и материал не показывает, как это сделать. Также не сказано, что `getItem` возвращает `null` для отсутствующего ключа, а это нужно учитывать при чтении.

### Как правильно

- Объекты и массивы: при записи `JSON.stringify`, при чтении `JSON.parse`.
- При чтении проверять `null` (ключа нет) и оборачивать `JSON.parse` в `try/catch`: если строку в хранилище кто-то испортил (например, руками в DevTools), `JSON.parse` бросит исключение.
- Числа и булевы значения явно преобразовывать при чтении.

### Пример

```ts
interface User {
  id: number;
  username: string;
  role: 'superadmin' | 'groupadmin' | 'user';
}

const user: User = { id: 2, username: 'anna', role: 'groupadmin' };

// ❌ Так нельзя: в JS молча сохранится "[object Object]"
// localStorage.setItem('user', user);  // в TS — ошибка компиляции

// ✅ Запись: объект → JSON-строка
localStorage.setItem('user', JSON.stringify(user));
// в хранилище лежит: '{"id":2,"username":"anna","role":"groupadmin"}'

// ✅ Чтение с защитой от отсутствия ключа и испорченных данных
function readUser(): User | null {
  const raw = localStorage.getItem('user');
  if (raw === null) {
    return null; // пользователь не сохранён
  }
  try {
    return JSON.parse(raw) as User;
  } catch {
    localStorage.removeItem('user'); // испорченную запись удаляем
    return null;
  }
}

// ✅ Числа: сохраняем строкой, при чтении превращаем обратно
localStorage.setItem('unreadCount', String(5));
const unread = Number(localStorage.getItem('unreadCount') ?? 0); // 5 (число)

// ✅ Булевы значения: сравниваем со строкой
localStorage.setItem('muted', String(false));
const muted = localStorage.getItem('muted') === 'true'; // false

// ❌ Типичная ошибка: строка "false" непустая, поэтому условие выполнится
// if (localStorage.getItem('muted')) { ... }
```

**Пояснения:**

- `as User` не проверяет данные, а только говорит компилятору, какой тип ожидать. Если в хранилище лежит объект другой формы, TypeScript этого не заметит.
- `?? 0` подставляет `0`, если `getItem` вернул `null`: иначе `Number(null)` тоже даст `0`, но явная запись понятнее.

## П-3. Что такое origin 🟡

### Как в материале

Лимит localStorage около 5 МБ указан «на origin», и в скобках origin расшифрован как домен и протокол. В разделе про IndexedDB сказано, что каждая база уникальна для origin, и уточнено, что обычно это домен или поддомен сайта.

### Пример из материала

Кода нет.

### В чём несоответствие

Origin состоит из **трёх** частей: протокол, хост и **порт**. Порт в материале пропущен. Следующий файл курса (5_3 про хостинг Angular на Node) определяет origin правильно, с портом, так что материалы противоречат друг другу.

Для Phase 2 это важно напрямую. Во время разработки Angular запускается на `http://localhost:4200` (`ng serve`), а тот же собранный билд, отданный Express-сервером, открывается на `http://localhost:3000`. Это **два разных origin**, и у каждого свой localStorage, свой sessionStorage и своя IndexedDB. Если залогиниться на 4200, то на 3000 пользователь окажется незалогиненным, и это не баг кода.

У кук правило другое: они привязаны к домену и пути, но **не к порту**. Кука, поставленная сервером на `localhost:3000`, будет видна и странице на `localhost:4200`.

### Как правильно

Origin = протокол + хост + порт. Два адреса имеют один origin, только если совпадают все три части. Путь (`/groups`, `/api/users`) в origin не входит.

| Адрес | Тот же origin, что `https://chat.example.com`? | Почему |
|---|---|---|
| `https://chat.example.com/groups/5` | да | отличается только путь |
| `http://chat.example.com` | нет | другой протокол |
| `https://chat.example.com:8443` | нет | другой порт (у https по умолчанию 443) |
| `https://api.chat.example.com` | нет | другой хост (поддомен) |

| Адрес | Тот же origin, что `http://localhost:4200`? |
|---|---|
| `http://localhost:4200/login` | да |
| `http://localhost:3000` | нет, другой порт |
| `http://127.0.0.1:4200` | нет, другой хост: для браузера `localhost` и `127.0.0.1` — разные строки |

### Пример

```js
// Откройте две вкладки: http://localhost:4200 и http://localhost:3000.
// В консоли DevTools каждой вкладки:

console.log(location.origin);
// вкладка 1: "http://localhost:4200"
// вкладка 2: "http://localhost:3000"

// Вкладка 1 (4200)
localStorage.setItem('user', '{"username":"anna"}');

// Вкладка 2 (3000)
localStorage.getItem('user'); // null — у этого origin своё хранилище
```

**Где увидеть:** DevTools → Application → Storage → Local Storage. Слева будет отдельная строка для каждого origin, с которым работала вкладка.

## П-4. `ngOnInit` и `$(document).ready` 🟡

### Как в материале

В аннотации к Angular-примеру сказано, что `ngOnInit()` делает то же, что `$(document).ready(...)` в jQuery: ждёт готовности DOM, то есть пока страница полностью загрузится и отрисуется. Внутри `ngOnInit` пример работает с localStorage, и первой строкой выводит в консоль сообщение о проверке готовности DOM.

### Пример из материала

```ts
import { Component,OnInit } from '@angular/core';

@Component({
  selector: 'app-root',
  templateUrl: './app.component.html',
  styleUrls: ['./app.component.css']
})
export class AppComponent implements OnInit{
  title = 'datapersistence';

  ngOnInit(){
    console.log("Testing if DOM is ready");

    if (typeof(Storage) !== "undefined"){
      console.log('Storage ready');
      localStorage.setItem("lastname","Smith");
      console.log(localStorage.getItem("lastname"));
    }else{
      console.log("No storage Support");
    }
  }
}
```

### В чём несоответствие

- `$(document).ready` — событие **всего документа**: HTML разобран, DOM построен.
- `ngOnInit` — хук жизненного цикла **конкретного компонента**. Angular вызывает его один раз, после того как установил входные свойства компонента (`@Input`). В этот момент шаблон компонента **ещё не отрисован**: его элементы и дочерние компоненты недоступны.
- Элементы шаблона становятся доступны в хуке `ngAfterViewInit`, который вызывается после первой отрисовки представления компонента и его детей.
- Для localStorage готовность DOM вообще не важна: хранилище — это API браузера, а не часть страницы. Пример работает, но не по той причине, которая указана в аннотации.

Порядок вызова для компонента:

```
constructor → ngOnChanges → ngOnInit → ngDoCheck
→ ngAfterContentInit → ngAfterContentChecked
→ ngAfterViewInit → ngAfterViewChecked
```

### Как правильно

| Где | Что делать |
|---|---|
| `constructor` | только получить зависимости (сервисы) |
| `ngOnInit` | начальная загрузка данных: прочитать хранилище, запросить сервер через сервис |
| `ngAfterViewInit` | работа с элементами шаблона: фокус, размеры, сторонние библиотеки, которым нужен DOM |

### Пример

```ts
import { Component, OnInit, AfterViewInit, ElementRef, ViewChild } from '@angular/core';

@Component({
  selector: 'app-chat-input',
  template: `<input #messageInput [value]="draft" placeholder="Сообщение">`,
})
export class ChatInputComponent implements OnInit, AfterViewInit {
  // Ссылка на <input #messageInput> из шаблона
  @ViewChild('messageInput') messageInput!: ElementRef<HTMLInputElement>;

  draft = '';

  constructor() {
    // Здесь только внедрение зависимостей.
    // Шаблона ещё нет, this.messageInput — undefined.
  }

  ngOnInit(): void {
    // ✅ Начальные данные: DOM для этого не нужен
    this.draft = sessionStorage.getItem('draft:1') ?? '';

    // ❌ Здесь this.messageInput ещё undefined — шаблон не отрисован
    // this.messageInput.nativeElement.focus();
  }

  ngAfterViewInit(): void {
    // ✅ Шаблон отрисован, элемент доступен
    this.messageInput.nativeElement.focus();
  }
}
```

**Пояснения:**

- `#messageInput` в шаблоне — template reference variable (подробно в файле 5_5). `@ViewChild('messageInput')` находит этот элемент в классе.
- В новых версиях Angular (17.2+) вместо декоратора можно использовать сигнальную функцию `viewChild('messageInput')`. Правило то же: элемент появляется только после отрисовки шаблона.

## П-5. Проверка `typeof(Storage)` 🔵

### Как в материале

Перед работой с хранилищем пример проверяет, определён ли объект `Storage`. Аннотация объясняет, что так проверяется доступность localStorage и sessionStorage, потому что старые браузеры могут их не поддерживать. Если проверка не проходит, в консоль выводится сообщение об отсутствии поддержки.

### Пример из материала

```ts
if (typeof(Storage) !== "undefined"){
  console.log('Storage ready');
  localStorage.setItem("lastname","Smith");
  console.log(localStorage.getItem("lastname"));
}else{
  console.log("No storage Support");
}
```

### В чём несоответствие

Web Storage поддерживается всеми браузерами больше десяти лет. Проверка безвредна, но от реальных проблем не защищает. Реальные проблемы другие:

1. **Место закончилось.** `setItem` бросает исключение `QuotaExceededError`.
2. **Хранение запрещено.** Если пользователь заблокировал в браузере хранение данных сайтов (cookies), само обращение к `localStorage` может бросить `SecurityError`.
3. **Серверный рендеринг (SSR).** Если Angular-проект создан с SSR (`ng new` спрашивает об этом при создании), код компонентов выполняется ещё и на сервере, в Node, где браузерных API нет. Признаки такого проекта: пакет `@angular/ssr` в `package.json` и файл `server.ts`. В Angular для таких случаев принято проверять платформу через `isPlatformBrowser`.

### Как правильно

- Работу с хранилищем вынести в один сервис (об этом говорит и файл 5_2 про сервисы).
- Запись и чтение обернуть в `try/catch`.
- Если в проекте есть SSR — проверять платформу. Если SSR нет, эта проверка всегда пропускает и ничего не ломает.

### Пример

```ts
import { Injectable, PLATFORM_ID, inject } from '@angular/core';
import { isPlatformBrowser } from '@angular/common';

@Injectable({ providedIn: 'root' })
export class StorageService {
  // true в браузере, false при рендеринге на сервере
  private isBrowser = isPlatformBrowser(inject(PLATFORM_ID));

  get<T>(key: string): T | null {
    if (!this.isBrowser) return null;
    try {
      const raw = localStorage.getItem(key);
      return raw === null ? null : (JSON.parse(raw) as T);
    } catch {
      // Хранилище недоступно или JSON испорчен
      return null;
    }
  }

  set(key: string, value: unknown): boolean {
    if (!this.isBrowser) return false;
    try {
      localStorage.setItem(key, JSON.stringify(value));
      return true;
    } catch (e) {
      // QuotaExceededError — нет места, SecurityError — хранение запрещено
      console.warn('Не удалось сохранить', key, e);
      return false;
    }
  }

  remove(key: string): void {
    if (!this.isBrowser) return;
    try {
      localStorage.removeItem(key);
    } catch {
      // Хранилище недоступно — удалять нечего
    }
  }
}
```

**Пояснения:**

- `set` возвращает `true` или `false`, чтобы вызывающий код знал, сохранилось ли значение, и мог показать пользователю сообщение.
- Благодаря сервису компоненты не работают с localStorage напрямую. Если позже хранение переедет, например, в IndexedDB, поменяется один файл.

## П-6. Время жизни sessionStorage 🟡

### Как в материале

sessionStorage описан как похожий на localStorage с единственным отличием: localStorage не имеет срока, а sessionStorage очищается, когда заканчивается сессия страницы. Дальше сказано, что сессия страницы длится, пока открыт браузер, и переживает перезагрузки и восстановление. Открытие страницы в новой вкладке или окне начинает новую сессию, а закрытие вкладки очищает сессию.

### Пример из материала

Кода нет, кроме списка методов (см. [П-1](#p-1)).

### В чём несоответствие

- Две фразы противоречат друг другу: «длится, пока открыт браузер» и «закрытие вкладки очищает сессию». Верна вторая: sessionStorage привязан к **вкладке**. Браузер может оставаться открытым, но закрытая вкладка унесёт свой sessionStorage.
- Отличий от localStorage два, а не одно. Кроме срока жизни, различается **область видимости**: localStorage общий для всех вкладок одного origin, а у каждой вкладки свой sessionStorage.
- Не упомянуты крайние случаи:
  - «Дублировать вкладку» создаёт **копию** sessionStorage на момент дублирования; дальше копии живут независимо.
  - Ссылка, открытая в новой вкладке, в современных браузерах, как правило, получает новую пустую сессию.
  - При восстановлении закрытой вкладки (Ctrl+Shift+T) или сессии браузера после перезапуска данные могут вернуться.

### Как правильно

| | localStorage | sessionStorage |
|---|---|---|
| Видимость | все вкладки одного origin | только своя вкладка (и origin) |
| Перезагрузка (F5) | сохраняется | сохраняется |
| Закрытие вкладки | сохраняется | удаляется |
| Закрытие браузера | сохраняется | удаляется (если сессия не восстанавливается) |
| Новая вкладка вручную | видит данные | пустое хранилище |
| Дублирование вкладки | видит данные | копия на момент дублирования |

### Пример

```js
// ── Вкладка A (http://localhost:4200) ──
sessionStorage.setItem('draft:1', 'Привет, как дела');
localStorage.setItem('theme', 'dark');

// ── Вкладка B: открыли вручную тот же адрес ──
sessionStorage.getItem('draft:1'); // null — у вкладки B своё хранилище
localStorage.getItem('theme');     // 'dark' — localStorage общий

// ── Вкладка A: нажали F5 ──
sessionStorage.getItem('draft:1'); // 'Привет, как дела' — пережило перезагрузку

// ── Вкладку A продублировали → вкладка C ──
sessionStorage.getItem('draft:1'); // 'Привет, как дела' — копия
sessionStorage.setItem('draft:1', 'Другой текст');
// во вкладке A по-прежнему 'Привет, как дела' — копии независимы

// ── Вкладку A закрыли, браузер открыт ──
// черновик вкладки A потерян, localStorage 'theme' на месте
```

## П-7. Время жизни session cookie 🔴

### Как в материале

В разделе атрибутов сказано, что кука без даты истечения — сессионная и удаляется в конце текущей сессии. В скобках пояснено, что это до закрытия вкладки или окна браузера. Кука с датой истечения названа постоянной.

### Пример из материала

Кода нет.

### В чём несоответствие

- Сессионная кука живёт до конца **сеанса браузера**, то есть до закрытия браузера целиком, а не вкладки. Закрытие вкладки её не удаляет: если открыть сайт в новой вкладке, кука на месте и уходит на сервер.
- Когда именно заканчивается сеанс, решает браузер. Если включено «Продолжить с того же места», браузер может сохранять сессионные куки даже между перезапусками.
- Путаница опасна тем, что у sessionStorage всё ровно наоборот: он как раз привязан к вкладке (см. [П-6](#p-6)). Формулировка материала переносит поведение sessionStorage на куки.
- Кроме того, куки общие для всех вкладок — изоляции по вкладкам у них нет вообще.

### Как правильно

Слово «session» в двух названиях означает разное:

| | sessionStorage | Сессионная кука |
|---|---|---|
| Что такое «сессия» | жизнь вкладки | сеанс браузера |
| Закрыли вкладку | удалено | **осталась** |
| Закрыли браузер | удалено | удалена (если сеанс не восстанавливается) |
| Видна другим вкладкам | нет | да |
| Уходит на сервер | нет | да, с каждым запросом |

### Пример

```js
// ── Вкладка A ──
document.cookie = 'lang=ru; path=/';                       // сессионная кука (без срока)
sessionStorage.setItem('tabNote', 'только эта вкладка');

// ── Закрыли вкладку A, открыли тот же сайт во вкладке B (браузер не закрывали) ──
document.cookie;                   // "lang=ru" — кука жива
sessionStorage.getItem('tabNote'); // null — sessionStorage вкладки A исчез

// ── Закрыли браузер полностью и запустили снова (без восстановления сессии) ──
document.cookie;                   // "" — сессионная кука удалена
```

## П-8. Размер и хранение cookie 🟡

### Как в материале

Куки описаны как данные, которые отправляет сервер и которые хранятся на компьютере пользователя в маленьких текстовых файлах размером около 2 КБ. Браузер может сохранить куку и отправить её обратно на сервер со следующим запросом.

### Пример из материала

Кода нет.

### В чём несоответствие

1. **Размер.** Лимит — около **4 КБ (4096 байт) на одну куку**: имя, значение и атрибуты вместе. Стандарт (RFC 6265) требует от браузеров поддерживать минимум 4096 байт на куку и минимум 50 кук на домен; реальные лимиты на количество у браузеров выше и различаются. Цифра 2 КБ неверна.
2. **«Текстовые файлы».** Так было в старых браузерах (например, Internet Explorer). Современные хранят куки во внутренней базе данных профиля. Для разработчика это деталь, но формулировка устарела.
3. **«Отправляет сервер».** Не только: куку может создать и JavaScript на странице через `document.cookie`, что видно на следующих слайдах того же файла. Сервер может запретить JS доступ к своей куке атрибутом `HttpOnly` (см. [П-10](#p-10)).
4. **Не сказано главное следствие.** Куки прикладываются к **каждому** запросу на подходящий домен и путь: к API, картинкам, стилям. Поэтому они должны быть маленькими, а крупные данные хранят в localStorage или IndexedDB.

### Как правильно

Кука — до ~4 КБ, ставится сервером или JS, хранится браузером и отправляется с каждым подходящим запросом. Слишком большая кука не сохраняется, и ошибки при этом нет.

### Пример

```js
// Кука больше лимита молча отбрасывается — без ошибки
document.cookie = 'big=' + 'x'.repeat(5000) + '; path=/';
document.cookie.includes('big=');   // false — браузер её не сохранил

// Кука нормального размера сохраняется
document.cookie = 'small=' + 'x'.repeat(100) + '; path=/';
document.cookie.includes('small='); // true

// Каждая кука увеличивает КАЖДЫЙ запрос на сайт.
// В DevTools → Network → любой запрос → Headers → Request Headers → Cookie
// видно, что уходит на сервер.
```

## П-9. JS-примеры cookie 🔵

### Как в материале

Приведены четыре примера установки куки через `document.cookie`. Первый — сессионная кука: только имя и значение. Второй — постоянная: то же плюс дата истечения в конце 2020 года. Третий — истёкшая: дата 1 января 1970 года. Четвёртый — безопасная: та же дата 1970 года плюс атрибут `Secure`. Все строки в типографских кавычках, в конце дана ссылка на MDN.

### Пример из материала

```js
document.cookie = “best_fruit=banana”;
document.cookie=“best_fruit=banana; expires=Fri, 31 Dec 2020 23:59:59 GMT”
document.cookie=“best_fruit=banana; expires=Thu, 01 Jan 1970 00:00:00 GMT”
document.cookie=“best_fruit=banana; expires=Thu, 01 Jan 1970 00:00:00 GMT; Secure”
```

### В чём несоответствие

1. **«Постоянная» кука уже истекла.** Дата в конце 2020 года сейчас в прошлом. Браузер воспринимает такую куку как истёкшую: не создаст её, а если кука с этим именем была — удалит. Сегодня второй пример работает так же, как третий.
2. **Не объяснено, зачем нужна истёкшая кука.** Это стандартный способ **удалить** куку. Удаление сработает, только если `path` (и `domain`, если был указан) совпадают с теми, с которыми кука создавалась. В примерах `path` не указан.
3. **«Безопасная» кука одновременно истёкшая.** Пример показывает `Secure` на куке, которая тут же удаляется, — наглядности это не добавляет. Кроме того, на странице, открытой по http, браузер Secure-куку не примет (localhost некоторые браузеры считают исключением).
4. **Типографские кавычки** при копировании дают `SyntaxError`.
5. **Не показано чтение.** `document.cookie` при чтении возвращает одну строку со всеми доступными куками вида `"a=1; b=2"`, без атрибутов. Её нужно разбирать вручную.
6. **Не сказано, что присваивание не перезаписывает все куки.** Каждое присваивание `document.cookie = ...` добавляет или обновляет **одну** куку.
7. **Не показаны современные варианты**: `max-age` (срок в секундах, проще даты) и `SameSite` (см. [П-10](#p-10)).
8. **Не сказано про кодирование.** Пробелы, `;`, `=` и кириллица в значении ломают строку куки. Значение нужно кодировать через `encodeURIComponent`.

### Как правильно

- Срок задавать через `max-age` в секундах или через дату, вычисленную в коде.
- Всегда указывать `path=/`, если кука нужна на всём сайте: иначе она привяжется к пути текущей страницы.
- Удалять через `max-age=0` с тем же `path`.
- Значения кодировать, при чтении декодировать.

### Пример

```js
// ── Сессионная кука: без срока, удалится при закрытии браузера ──
document.cookie = 'lang=ru; path=/';

// ── Постоянная кука на 7 дней через max-age (в секундах) ──
document.cookie = `theme=dark; max-age=${60 * 60 * 24 * 7}; path=/; SameSite=Lax`;

// ── То же через expires: дату вычисляем, а не пишем руками ──
const expires = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000).toUTCString();
document.cookie = `theme=dark; expires=${expires}; path=/; SameSite=Lax`;

// ── Значение со спецсимволами: кодируем ──
document.cookie = `nick=${encodeURIComponent('Антон; admin')}; path=/`;

// ── Безопасная кука: только на странице, открытой по https ──
document.cookie = 'pref=compact; path=/; Secure; SameSite=Lax';

// ── Удаление: max-age=0 и ТОТ ЖЕ path, что при создании ──
document.cookie = 'theme=; max-age=0; path=/';

// ── Чтение: разбираем строку "lang=ru; nick=%D0%90..." ──
function getCookie(name) {
  const pair = document.cookie
    .split('; ')                               // ["lang=ru", "nick=..."]
    .find(row => row.startsWith(name + '='));  // нужная пара или undefined
  return pair ? decodeURIComponent(pair.slice(name.length + 1)) : null;
}

getCookie('lang'); // 'ru'
getCookie('nick'); // 'Антон; admin'
getCookie('nope'); // null
```

**Пояснения:**

- `pair.slice(name.length + 1)` отрезает `имя=` и оставляет значение.
- Кук с `HttpOnly` в строке `document.cookie` не будет: JS их не видит.

## П-10. Атрибуты cookie 🔵

### Как в материале

Перечислены пять атрибутов: `Secure`, `Domain`, `Path`, `HttpOnly` и `Expires`. Общее пояснение: каждый атрибут ограничивает область действия куки и повышает её безопасность. Дальше отдельно объяснены: отсутствие `Expires` делает куку сессионной, наличие — постоянной; `Secure` разрешает передачу только по HTTPS; `Domain` задаёт хосты, которые получают куку, а без него используется хост текущего документа без поддоменов; `Path` задаёт путь, который должен присутствовать в URL запроса, чтобы кука отправилась.

### Пример из материала

Кода нет, кроме JS-примеров из П-9.

### В чём несоответствие

1. **Нет `SameSite`** — ключевого атрибута современной безопасности кук. Он определяет, уходит ли кука с запросами, которые инициировал **другой сайт**, и служит главной защитой от CSRF (см. [П-11](#p-11)):
   - `Strict` — кука уходит только с запросами, инициированными этим же сайтом;
   - `Lax` — плюс обычный переход по ссылке на сайт с чужой страницы;
   - `None` — уходит всегда, в том числе с запросами с чужих сайтов; обязательно вместе с `Secure`.
   Chrome и Edge с 2020 года считают куку без `SameSite` как `Lax`. В других браузерах поведение по умолчанию может отличаться, поэтому атрибут лучше указывать явно.
2. **Нет `Max-Age`** — срока жизни в секундах. Если указаны оба, `Max-Age` важнее `Expires`. Браузеры ограничивают максимальный срок: например, Chrome — 400 днями.
3. **`Domain` не сужает, а расширяет область.** Без `Domain` кука уходит только на тот хост, который её поставил. С `Domain=example.com` — на `example.com` **и все его поддомены**. Указать чужой домен нельзя.
4. **`HttpOnly` упомянут, но не объяснён.** Кука с `HttpOnly` недоступна JavaScript: `document.cookie` её не показывает, поэтому её нельзя украсть через XSS. Ставится только сервером.
5. **`Path` сопоставляется по началу пути.** `Path=/api` отправит куку на `/api` и `/api/users`, но не на `/apix` и не на `/`.
6. **Порт в области куки не участвует** (см. [П-3](#p-3)).

### Как правильно

| Атрибут | Что делает | Кто может поставить |
|---|---|---|
| `Expires` | дата удаления | сервер и JS |
| `Max-Age` | срок в секундах, важнее `Expires` | сервер и JS |
| `Secure` | только HTTPS | сервер и JS (на https-странице) |
| `HttpOnly` | невидима для JS | **только сервер** |
| `Domain` | расширяет область на поддомены | сервер и JS |
| `Path` | ограничивает путь по префиксу | сервер и JS |
| `SameSite` | `Strict` / `Lax` / `None`, защита от CSRF | сервер и JS |

### Пример: кука на Express-сервере

Для Phase 2 полезнее всего увидеть, как куку ставит сервер. На курсе авторизация в чате может быть устроена без кук, так что пример — для понимания механизма.

```js
const express = require('express');
const cookieParser = require('cookie-parser'); // npm install cookie-parser
const app = express();

app.use(express.json());
app.use(cookieParser()); // разбирает заголовок Cookie в объект req.cookies

// Сервер ставит куку в ответе → браузер получает заголовок Set-Cookie
app.post('/api/login', (req, res) => {
  // ... проверка логина и пароля ...
  res.cookie('sessionId', 'abc123', {
    httpOnly: true,          // JS в браузере куку не увидит
    secure: true,            // только по HTTPS
    sameSite: 'lax',         // не уходит с большинства запросов с чужих сайтов
    maxAge: 1000 * 60 * 60,  // ⚠ в Express maxAge задаётся в МИЛЛИсекундах: здесь 1 час
    path: '/',
  });
  res.json({ ok: true });
});
// Заголовок ответа будет примерно таким:
// Set-Cookie: sessionId=abc123; Max-Age=3600; Path=/; Expires=...; HttpOnly; Secure; SameSite=Lax

// Браузер сам прислал куку в заголовке Cookie → читаем её
app.get('/api/me', (req, res) => {
  const sessionId = req.cookies.sessionId; // undefined, если куки нет
  if (!sessionId) {
    return res.status(401).json({ error: 'Not logged in' });
  }
  res.json({ sessionId });
});

// Удаление: сервер присылает ту же куку с истёкшим сроком
app.post('/api/logout', (req, res) => {
  res.clearCookie('sessionId', { path: '/' });
  res.json({ ok: true });
});

app.listen(3000);
```

**Пояснения:**

- В атрибуте `Max-Age` самой куки срок в **секундах**, а в опции `maxAge` у Express — в **миллисекундах**. Express сам переводит одно в другое. Частая ошибка — передать секунды и получить куку, живущую в 1000 раз меньше.
- При разработке по `http://localhost` опция `secure: true` может помешать: некоторые браузеры не примут такую куку. Для локальной разработки её иногда временно выключают.

## П-11. Угрозы безопасности 🟡

### Как в материале

В последнем разделе сказано, что не стоит хранить большие объёмы чувствительной информации в браузере. У кук и веб-хранилища есть уязвимости, из-за которых сохранённые данные могут быть использованы или украдены другими сайтами, которые посещает пользователь. Поэтому никогда не нужно хранить там пароли, чувствительные данные пользователя или данные из базы. Ранее в разделе localStorage тоже сказано, что он небезопасен для чувствительной информации.

### Пример из материала

Кода нет.

### В чём несоответствие

Вывод верный — пароли в браузере не хранят. Но механизм угрозы описан неточно, а без правильного механизма непонятно, как защищаться.

- **Другие сайты не могут напрямую прочитать** localStorage, sessionStorage или куки твоего origin. Это запрещает same-origin policy браузера.
- **XSS (межсайтовый скриптинг)** — реальная угроза для всех хранилищ. Чужой скрипт выполняется **внутри твоего** origin и поэтому видит всё: localStorage, sessionStorage и куки без `HttpOnly`, после чего может отправить их куда угодно. Типичные пути: пользовательский ввод (например, сообщение в чате), вставленный на страницу как HTML, или скомпрометированная сторонняя библиотека.
- **CSRF (межсайтовая подделка запроса)** касается только кук. Чужой сайт не читает твои куки, но может заставить браузер **отправить** запрос на твой сервер, и браузер сам приложит к нему куки. Защита — `SameSite` (см. [П-10](#p-10)) и CSRF-токены.
- **Общий компьютер.** Содержимое хранилищ открыто видно в DevTools любому, кто сядет за этот браузер.
- **«Большие объёмы» не при чём.** Опасен даже один ценный токен; дело не в объёме, а в чувствительности.

### Как правильно

1. Пароль не хранить в браузере нигде: ни в localStorage, ни в sessionStorage, ни в куках.
2. После логина хранить только то, что не страшно показать: `id`, `username`, `role`.
3. Роль в браузере — только для отображения интерфейса (показать или скрыть кнопки). Пользователь может отредактировать localStorage в DevTools, поэтому права проверяет **сервер** при каждом запросе.
4. Пользовательский текст выводить через интерполяцию, а не как HTML.
5. Токены сессии, если они есть, хранить в куке с `HttpOnly`, `Secure` и `SameSite`.

### Пример

```ts
// ✅ Что можно хранить после логина
const safeUser = { id: 2, username: 'anna', role: 'groupadmin' };
localStorage.setItem('user', JSON.stringify(safeUser));

// ❌ Никогда: пароль в браузере
```

## П-12. Терминология и IndexedDB 🟡

### Как в материале

В начале файла сказано, что HTML5 предоставляет набор вариантов клиентского Web Storage, и в этот список включены local storage, session storage, cookies и IndexedDB. Затем — что каждый из вариантов хранит пары «ключ → значение» из строк. В разделе про IndexedDB она описана как низкоуровневый API для хранения больших объёмов структурированных данных, объектно-ориентированное NoSQL-хранилище на JavaScript, где объекты сохраняются и читаются по ключу; база уникальна для origin. Подробно IndexedDB на курсе не рассматривается, достаточно знать, что она существует.

### Пример из материала

Кода нет.

### В чём несоответствие

1. **Web Storage API — это только localStorage и sessionStorage.** Cookies — механизм протокола HTTP, появившийся задолго до HTML5. IndexedDB — отдельный API. Все четыре — клиентские хранилища, но не «Web Storage». Это важно при чтении документации: MDN описывает их в разных разделах.
2. **«Все хранят строки» противоречит разделу IndexedDB** того же файла. IndexedDB хранит **объекты как есть**: массивы, даты, файлы, без `JSON.stringify`.
3. **Не сказано ключевое отличие IndexedDB:** она **асинхронная** и не блокирует страницу, в отличие от синхронного localStorage. Поддерживает транзакции и индексы для поиска, а объём ограничен в основном свободным местом на диске (сотни мегабайт и больше).

### Как правильно

| Группа | Что входит |
|---|---|
| Web Storage API | localStorage, sessionStorage |
| HTTP cookies | куки (`document.cookie`, заголовки `Set-Cookie` / `Cookie`) |
| IndexedDB API | IndexedDB |
| Общее название всех четырёх | клиентское хранение данных (client-side storage) |

### Пример (для понимания, на курсе не требуется)

```js
// Открываем (или создаём) базу "chat" версии 1
const request = indexedDB.open('chat', 1);

// Срабатывает при создании базы или повышении версии — здесь создаём «таблицы»
request.onupgradeneeded = () => {
  const db = request.result;
  db.createObjectStore('messages', { keyPath: 'id' }); // ключ — поле id объекта
};

request.onsuccess = () => {
  const db = request.result;

  // Запись — внутри транзакции. Объект кладём как есть, без JSON
  const tx = db.transaction('messages', 'readwrite');
  tx.objectStore('messages').put({
    id: 1,
    channelId: 3,
    text: 'Привет',
    sentAt: new Date(),
  });

  // Когда транзакция завершилась — читаем
  tx.oncomplete = () => {
    const getRequest = db.transaction('messages').objectStore('messages').get(1);
    getRequest.onsuccess = () => {
      const message = getRequest.result;
      console.log(message.text);                // 'Привет'
      console.log(message.sentAt instanceof Date); // true — тип Date сохранился
    };
  };
};

request.onerror = () => console.error('Не удалось открыть базу', request.error);
```

**Пояснения:**

- Всё асинхронно: результат приходит в обработчиках `onsuccess`, а не возвращается сразу, как у `localStorage.getItem`.
- `keyPath: 'id'` означает, что ключом записи служит поле `id` самого объекта.
- Сравнение с localStorage: там пришлось бы делать `JSON.stringify`, а дата вернулась бы строкой.
