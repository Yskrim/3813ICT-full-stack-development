## Шаг 0 — контракт API (15 мин)

Результат: заполненная таблица ниже. Это тот слой планирования, которого не хватало между схемой базы и страницами. Сервер и клиент дальше пишутся под неё, а не наугад.

Первая строка заполнена как образец. Остальные заполни сам прямо в этой таблице:

| Метод | Путь                  | Тело запроса | Успешный ответ   | Ошибки            |
| ----- | --------------------- | ------------ | ---------------- | ----------------- |
| GET   | /api/books            | —            | 200, массив книг | 500 — сервер упал |
| GET   | /api/books/:id        | -            | 200, одна книга  | 500, 404          |
| POST  | /api/books/:id/borrow | -            | 200, успешно     | 500, 400          |
| POST  | /api/books/:id/return | -            | 200, успешно     | 500, 400          |

1. Для каждого эндпоинта реши: что приходит в теле запроса и что сервер возвращает при успехе — всю книгу, сообщение или ничего?
2. Для «Взять» продумай минимум три ошибки: книги с таким id нет, id в неправильном формате, экземпляров не осталось. Какой код ответа подходит к каждой? Посмотри на коды 400, 404 и 409.
   1. 404 - не найдено - подходит если айди книги нет в списке
   2. 400 - не правильный запрос - если не правильное тело для эндпоинта, в целом не особо применимо, разве что если вдруг у записи книги не будет каких-то полей для вызова апи
   3. 409 - конфликт. Наверное подойдет если два клиента одновременно попытаются взять последнюю книжку. Первому придет успех, второму 409.
3. Пропиши, какие страницы Angular какими эндпоинтами пользуются. Одной строкой на страницу, под таблицей.
   1. Главная - get api/books
   2. Страница отдельной книги - get api/books/:id
   3. Кнопка "взять" на странице дашборда - POST /api/books/:id/borrow
   4. Кнопка 'вернуть' на странице дашборда - POST /api/books/:id/return

**Подумай:** почему «взять книгу» — это `POST /borrow`, а не `PUT /api/books/:id` с новым значением `copies`, которое посчитал клиент?

- потому что PUT перезапишет существующую запись о книге, просто перезапишется количество доступных копий, а запись о займе книги не появится.

## Шаг 1 — Node + Express отдельно (45 мин)

Результат: сервер на порту 3000, который отвечает по контракту из шага 0. Данные пока хранятся в массиве в памяти, базы нет. Так ты отлаживаешь только Express, без второго источника ошибок.

1. Создай папку `server`, инициализируй npm-проект, поставь `express` и `cors`. Один файл `index.js`, как ты и хотел.
2. Заведи массив из 4–5 книг. Дай им строковые `id` вида `"b1"`, `"b2"` и поле `copies`.
3. Подключи встроенный middleware для разбора JSON и `cors`.
4. **Свой middleware:** логгер, который печатает метод, путь и сколько миллисекунд занял запрос. Подумай, как узнать время, если ответ отправляется уже *после* твоего middleware.
5. Реализуй эндпоинты из контракта по очереди. После каждого проверь его в Postman, Thunder Client или через `curl`, прежде чем писать следующий.
6. «Взять» должен уменьшать `copies` и возвращать коды ошибок, которые ты выбрал в шаге 0.
7. Добавь обработчик для несуществующих путей, чтобы отвечать JSON с 404, а не HTML-страницей Express.
8. Коммит.

**Проверь себя:** вызови «Взять» для книги с `copies: 1` два раза подряд. Второй ответ должен быть ошибкой с твоим кодом, а не `copies: -1`.

**Подумай:** почему порядок `app.use` и роутов в файле важен? Что сломается, если поставить разбор JSON в самый конец?

## Шаг 2 — Express + MongoDB (45 мин)

Результат: тот же API, но данные берутся из коллекции `books` базы `library`. Контракт не меняется — клиент вообще не заметит подмены. В этом и смысл контракта.

1. Поставь официальный драйвер `mongodb`. Его синтаксис почти совпадает с mongosh, так что всё из лабораторной переносится напрямую. Если на курсе 3813 используется Mongoose, можешь взять его, но тогда запиши в парковку вопрос, чем он отличается.
2. Подключись к базе **один раз** при старте сервера, а не в каждом запросе. Сервер должен начинать слушать порт только после успешного подключения.
3. Перепиши `GET /api/books` и `GET /api/books/:id`. Учти, что `:id` приходит строкой, а `_id` в базе — ObjectId. Что будет, если прислать id неправильного формата? Это ошибка 400 из твоего контракта.
4. Перепиши «Взять». **Главное задание вечера:** сделай так, чтобы `copies` не мог уйти в минус даже при двух одновременных запросах. Без отдельного `findOne` перед обновлением — одной операцией. Это и есть ответ на вопрос про гонку, который ты вчера отложил.
5. По результату этой одной операции определи, что вернуть: 200, 404 или 409.
6. Проверь в Compass, что `copies` действительно меняется.
7. Коммит. Дальше — длинный перерыв.

**Подумай:**

- Почему вариант «прочитать книгу → проверить `copies > 0` → обновить» ломается, когда два пользователя нажимают кнопку одновременно?
- Перенеси на столики: какое условие в фильтре не даст забронировать уже занятый стол?

## Шаг 3 — Angular отдельно (45 мин)

Результат: приложение из трёх частей (список, страница книги, шапка) на моковых данных, без сервера. Цель шага — закрыть главный пробел: разницу между снимком значения сигнала и живым чтением.

1. **Разминка (10 мин):** эксперимент с `temperature` и `snapshot` из нашего чата. Выведи оба в шаблон, добавь кнопку со случайной температурой. Запиши в одну фразу, что увидел.
2. Создай новый проект Angular в папке `client`. Посмотри, есть ли в нём `app.module.ts`, — так ты ответишь и на вопрос про standalone.
3. Создай `BookService`. Список книг из шага 1 храни в нём как сигнал. Сделай так, чтобы снаружи сигнал можно было только читать, а менять — только через методы сервиса.
4. Добавь в сервис метод `borrow(id)`, который пока локально уменьшает `copies` нужной книги. Важно: новый массив и новый объект книги, а не изменение старого. Подумай, почему сигнал этого требует.
5. Создай `CartService` с сигналом взятых книг и `computed`-счётчиком.
6. Сделай два маршрута: `/books` (список) и `/books/:id` (страница книги с кнопкой «Взять»). Шапка показывает счётчик и видна на обеих страницах.
7. **Контрольный тест:** открой книгу, нажми «Взять», вернись к списку. `copies` в списке и счётчик в шапке должны обновиться без перезагрузки. Если список не обновился — это и есть снимок вместо живого чтения, ищи скобки.
8. Коммит.

**Подумай:**

- Кто сейчас вызывает `CartService`, когда пользователь берёт книгу: компонент страницы или `BookService`? Что изменится, если кнопка «Взять» появится ещё и на карточке в списке?
- Если бы сигнал в `BookService` был публичным и изменяемым, что мог бы сделать любой компонент?

## Шаг 4 — всё вместе (60 мин)

Результат: Angular-клиент работает с твоим Express-сервером и базой. Компоненты почти не меняются — меняется только то, откуда сервис берёт данные. Если это так, значит, в шаге 3 ты правильно разделил ответственность.

1. Подключи HttpClient в конфигурации приложения.
2. **Загрузка списка.** Метод сервиса запрашивает `GET /api/books` и кладёт результат в сигнал. Рядом с данными в сервисе храни сигналы «загружается» и «ошибка» — это общие данные, их может показывать любая страница.
3. Флаг «загружается» должен сбрасываться и при успехе, и при ошибке. Сделай это в одном месте, а не в двух.
4. Список показывает три состояния: «Загрузка…», сообщение об ошибке и сами книги. Проверь ошибку честно: останови сервер и обнови страницу.
5. **«Взять» через сервер.** Метод `borrow(id)` в сервисе отправляет POST. После успеха, **внутри pipe сервиса**, перезапроси список и обнови корзину. Компонент только подписывается и решает, что показать на своей странице.
6. На странице книги храни флаг «отправляется» для кнопки: пока запрос идёт, кнопка заблокирована. Это состояние одной кнопки, поэтому оно живёт в компоненте.
7. При ответе 409 покажи «Экземпляров не осталось», а не общий текст «Ошибка».
8. **Финальная проверка:** возьми книгу, у которой остался один экземпляр, в двух вкладках по очереди. Во второй вкладке должна появиться твоя ошибка 409, а в Compass `copies` должен остаться 0.
9. Коммит. Всё, на сегодня хватит.

**Подумай перед созвоном:**

- Где в твоём коде живёт правда о количестве экземпляров? А где только её отображение?
- Что из сегодняшнего ты бы сделал так же для столиков, а что пришлось бы поменять?

## Подсказки

Открывай, только если застрял дольше 10 минут. Здесь направления и названия, команды собираешь сам по документации.

**Шаг 0**

- 400 — запрос составлен неправильно, 404 — такого ресурса нет, 409 — запрос правильный, но конфликтует с текущим состоянием данных.

**Шаг 1**

- Разбор JSON: `express.json()`.
- Время запроса: запомни `Date.now()` в начале middleware и подпишись на событие `finish` у объекта `res`.
- Обработчик 404 — это `app.use` без пути, который стоит **после** всех роутов.

**Шаг 2**

- Подключение: `MongoClient` и `connect()`, затем `app.listen` — в такой последовательности, через `await` или `.then`.
- Проверка формата id: `ObjectId.isValid()`, затем `new ObjectId(id)`.
- Атомарность: условие можно поставить прямо в **фильтр** обновления, рядом с `_id`. Тогда документ обновится, только если подходит под всё условие. Нужны `$gt` и `$inc`.
- Результат `updateOne` содержит `matchedCount`. А `findOneAndUpdate` может вернуть сам обновлённый документ — поищи опцию `returnDocument`.
- Если ничего не обновилось, причины две: книги нет или экземпляров не осталось. Подумай, как их различить, чтобы вернуть 404 или 409.

**Шаг 3**

- Только чтение снаружи: приватный изменяемый сигнал и публичный через `asReadonly()`.
- Новый массив: `update()` у сигнала, внутри — `map` и spread-оператор для изменённой книги.
- Маршруты: `app.routes.ts`, `<router-outlet>`, `routerLink`. Параметр `:id` — через `ActivatedRoute` или через `input()`, если включён `withComponentInputBinding()`.

**Шаг 4**

- HttpClient: `provideHttpClient()` в `app.config.ts`.
- Действие без изменения данных — `tap`. Следующий запрос после первого — `switchMap`. Сброс при успехе и ошибке — `finalize`.
- Код ответа при ошибке лежит в `status` у `HttpErrorResponse` — его получает `error` подписки.
- Тот, кто подписывается, запускает запрос. Если в шаге 4 ничего не уходит на сервер, проверь, есть ли `subscribe`.
