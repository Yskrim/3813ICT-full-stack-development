# MongoDB Setup and CLI

Самая большая лекция недели (41 слайд): установка, оболочка, CRUD и шпаргалка по операторам. Содержательно она полезная, но команд, которые **удалены** из современной MongoDB, там штук пять, а в финальной шпаргалке перепутаны AND и OR. Разбираю по порядку и в конце даю исправленную шпаргалку — ей и пользуйся.

### Варианты запуска (слайды 2–3)

- **Atlas** — MongoDB как облачный сервис, есть бесплатный уровень для учёбы.
- **Community Edition** — бесплатная локальная установка под свою платформу или в Docker.
- **Compass** — графический клиент для просмотра и правки данных. Очень выручает при отладке: видно, что реально лежит в базе, а не что ты думаешь, что лежит.
- Установка даёт две вещи: серверный демон и клиент командной строки. Для доступа из Node нужен отдельный npm-пакет `mongodb` — драйвер.

### Установка: инструкция в слайдах устарела

В лекции написано `brew install mongodb`. Такой формулы больше нет, установка сломается. Актуальный способ на macOS:

```bash
brew tap mongodb/brew
brew install mongodb-community
brew services start mongodb-community     # запустить как сервис
brew services list                        # проверить, что запущен
```

Заодно два шага из слайдов делать **не нужно**: создавать `/data/db` и раздавать права через `sudo chown`. При установке через brew данные лежат в `/opt/homebrew/var/mongodb` (Apple Silicon) или `/usr/local/var/mongodb` (Intel), и права уже настроены. Команды `chown` из слайдов вообще написаны под путь `/usr/local`, которого на Apple Silicon нет.

### Оболочка: `mongo` больше не существует

Слайды местами говорят `mongo`, местами `mongosh`. Правильно только `mongosh`: старая оболочка `mongo` объявлена устаревшей в версии 5.0 и **удалена** в 6.0. То же касается строчки из шпаргалки `mongo --host <hostname> --port <port>` — сейчас это:

```bash
mongosh                                        # локально, порт по умолчанию 27017
mongosh "mongodb://localhost:27017"
mongosh "mongodb+srv://cluster.mongodb.net/"   # Atlas
```

Сервер по-прежнему запускается бинарником `mongod`, тут лекция верна.

### Документ (слайд 9)

Запись в MongoDB называется документом и состоит из пар «поле — значение». Значением может быть другой документ, массив или массив документов:

```js
{
    id: 1,
    name: 'the best of databases',
    status: 'active',
    categories: ['database', 'programming']
}
```

Уточнение к лекции: документ **похож** на JSON, но хранится в BSON — бинарном формате, где есть типы, которых в JSON нет: `ObjectId`, `Date`, 32- и 64-битные целые, бинарные данные. Практическое следствие: дата в базе — это настоящий тип `Date`, по ней работают `$gt` и сортировка, поэтому даты не надо хранить строками.

### Базы и коллекции (слайды 10–13)

```js
use shopdb                      // переключиться на базу
db.dropDatabase()               // удалить текущую
db.createCollection('products') // создать коллекцию
show collections                // список коллекций
show dbs                        // список баз
db                              // какая база текущая
```

Уточнение: слайд говорит, что `use` создаёт базу, если её нет. На самом деле и база, и коллекция создаются **лениво** — только в момент первой записи. Пока ты ничего не вставил, `show dbs` твою базу не покажет. Из этого же следует, что `createCollection` в обычной работе не обязателен: первый `insertOne` создаст коллекцию сам. Явно создавать её нужно, когда задаёшь особые параметры — например валидацию схемы или capped-коллекцию.

### Вставка (слайды 14–15)

```js
db.products.insertOne({ id: 1, name: 'клавиатура', price: 50 })
db.products.insertMany([{ id: 2, name: 'мышь' }, { id: 3, name: 'монитор' }])
```

В заголовке слайда 15 перевёрнуты слова («Inserting Multiple Collections Into a Document»). Вставляют, разумеется, несколько **документов в коллекцию**.

### Удаление и обновление: команд из лекции больше нет

Это главная практическая ошибка лекции. `remove()` и `update()` объявлены устаревшими давно и **удалены** из `mongosh` и из драйверов начиная с 4.0. Слайды 16, 17 и шпаргалка используют именно их.

Как надо сейчас:

```js
// вместо db.products.remove(<query>)
db.products.deleteOne({ id: 1 })          // удалить первый подходящий
db.products.deleteMany({ status: 'old' }) // удалить все подходящие
db.products.deleteMany({})                // очистить коллекцию

// вместо db.products.update(<query>, { $set: {...} })
db.products.updateOne({ id: 1 }, { $set: { price: 60 } })
db.products.updateMany({ status: 'new' }, { $set: { status: 'active' } })
db.products.replaceOne({ id: 1 }, { id: 1, name: 'другая клавиатура' })
db.products.findOneAndUpdate({ id: 1 }, { $set: { price: 70 } })  // вернёт документ
```

Про `$set` важно помнить: **без него** документ будет заменён целиком, и все поля, которых нет в переданном объекте, исчезнут. `updateOne` без `$set` в новых версиях вообще выдаст ошибку, а вот `replaceOne` заменяет намеренно.

### Поиск (слайды 18–29)

```js
db.products.find()                                  // все документы
db.products.find({ status: 'active' })              // where status = 'active'
db.products.find({ status: 'active', price: 50 })   // это И, а не ИЛИ
db.products.find({}, { name: 1, price: 1, _id: 0 }) // проекция: только нужные поля
db.products.findOne({ id: 1 })                      // первый подходящий документ
```

Проекция — это не косметика: она уменьшает объём данных, который бежит между базой и приложением. Обрати внимание на `_id: 0` — `_id` возвращается всегда, пока его явно не выключить.

Операторы сравнения работают со строками, числами и датами:

```js
db.products.find({ price: { $gt: 50 } })            // строго больше
db.products.find({ price: { $gte: 50, $lte: 100 } }) // диапазон
db.products.find({ $or: [{ price: { $lt: 20 } }, { status: 'sale' }] })
```

Курсорные методы и постраничный вывод:

```js
db.products.find().limit(10)
db.products.find().skip(20)
db.products.find().sort({ price: 1 })    // 1 по возрастанию, -1 по убыванию
db.products.find().skip(pageSize * pageNumber).limit(pageSize)   // пагинация
db.products.countDocuments()             // сколько документов
```

Две поправки. В шпаргалке слайда 39 написано `find().count` — во-первых, без скобок это вообще не вызов, во-вторых, `count()` объявлен устаревшим: сейчас `countDocuments()` для точного числа и `estimatedDocumentCount()` для быстрой оценки. И о пагинации: `skip` на больших коллекциях медленный, потому что база честно проматывает все пропускаемые документы. Для учебного проекта это неважно, но знать стоит.

### Вложенные документы и связи (слайды 30–34)

Вложенный документ — это просто объект в поле:

```js
db.users.insertOne({
    name: 'anton',
    address: { city: 'Gold Coast', zip: '4215' }
})

db.users.find({ 'address.city': 'Gold Coast' })   // точечная нотация, кавычки обязательны
```

Ссылка на документ другой коллекции — это хранение его `_id`. Так получается аналог «один ко многим» или «один к одному». `_id` генерируется MongoDB автоматически и используется для индексации и ссылок.

Полезная деталь, которой нет в лекции: если поле — массив, запрос по нему пишется как по обычному полю. `db.products.find({ categories: 'database' })` найдёт документ, у которого `categories` — массив, содержащий эту строку.

**А вот про соединения в слайде 34 написано неверно.** Там сказано, что join приходится делать рекурсивной функцией в Node, и что это «x2-проблема», которая «логарифмически замедляется». Логарифмический рост — это как раз очень медленный рост, то есть по смыслу сказано обратное задуманному. И главное: соединения в MongoDB делаются в самой базе оператором `$lookup` в агрегации, он существует с версии 3.2:

```js
db.messages.aggregate([
    { $lookup: {
        from: 'users',
        localField: 'userId',
        foreignField: '_id',
        as: 'author'
    } }
])
```

Верной в этом слайде остаётся мысль: если ты постоянно соединяешь коллекции, документная модель выбрана неудачно. Но делать это рекурсией в Node точно не надо.

### Исправленная шпаргалка

Логические операторы в слайде 41 перепутаны местами: там написано «AND → `$or`» и «OR → `$and`». Правильно так:

| Операция | Команда |
| --- | --- |
| И | `db.c.find({ $and: [<expr1>, <expr2>] })` |
| ИЛИ | `db.c.find({ $or: [<expr1>, <expr2>] })` |
| НЕ | `db.c.find({ <field>: { $not: { $eq: <value> } } })` |
| НИ ОДНО ИЗ | `db.c.find({ $nor: [<expr1>, <expr2>] })` |

Заодно про `$not`: в слайде он показан как `find({ $not: {<expression>} })` — так нельзя, это невалидный запрос. `$not` применяется **внутри поля**, к оператору: `{ price: { $not: { $gt: 100 } } }`. Если нужно отрицание целого выражения на верхнем уровне — это `$nor`.

И ещё мелочь из шпаргалки: `db.createcollection` написано со строчной `c`. Имена методов регистрозависимы, правильно `db.createCollection`.

Сводка того, что нужно заменить в конспекте лекции:

| В слайдах | Как правильно сейчас |
| --- | --- |
| `brew install mongodb` | `brew tap mongodb/brew && brew install mongodb-community` |
| `mongo` | `mongosh` (старая оболочка удалена в 6.0) |
| `db.c.remove(...)` | `deleteOne` / `deleteMany` |
| `db.c.update(...)` | `updateOne` / `updateMany` / `replaceOne` |
| `find().count` | `countDocuments()` |
| `db.createcollection` | `db.createCollection` |
| AND → `$or`, OR → `$and` | наоборот |
| `find({ $not: {...} })` | `{ field: { $not: { $eq: ... } } }` или `$nor` |
| join рекурсией в Node | `$lookup` в агрегации |

### Проверь себя

1. Почему `show dbs` не показывает базу, которую ты только что «создал» через `use`?
2. Что произойдёт с полями документа, если сделать `updateOne` и забыть `$set`?
3. Чем `countDocuments()` отличается от `estimatedDocumentCount()`?
4. Как найти документ по городу, если город лежит во вложенном объекте `address`?
5. Как правильно записать «И» и «ИЛИ», и почему шпаргалке из лекции тут верить нельзя?
6. Почему дату лучше хранить типом `Date`, а не строкой?

Ответы: потому что база создаётся лениво, только при первой записи. Документ будет заменён целиком, и все не переданные поля исчезнут (в новых версиях такой вызов вообще отклоняется). Первый честно считает документы и всегда точен, второй берёт оценку из метаданных коллекции и работает быстро, но приблизительно. Через точечную нотацию в кавычках: `{ 'address.city': 'Gold Coast' }`. И — это `$and`, ИЛИ — это `$or`; в шпаргалке слайда 41 они перепутаны. Потому что BSON хранит настоящий тип даты, и по нему корректно работают сравнения `$gt`/`$lt` и сортировка, а строки сравнивались бы лексикографически.
