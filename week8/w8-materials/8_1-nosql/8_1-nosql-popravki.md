## П-2. NoSQL, схема и согласованность 🟡

### Как в материале

На слайдах 4–5 NoSQL противопоставлен реляционным базам с заранее заданной схемой. Далее сказано, что NoSQL не подходит приложениям с высокими требованиями к согласованности данных.

### Пример из материала

Кода нет.

### В чём несоответствие

Утверждение переносит свойства отдельных систем на всё семейство. NoSQL — это разные модели и разные продукты, и гарантии у них разные:

- **схема** — у MongoDB она гибкая по умолчанию, но коллекции можно задать правила проверки ([П-4](#p-4));
- **атомарность** — в MongoDB любая операция над одним документом атомарна;
- **транзакции** — MongoDB поддерживает многодокументные ACID-транзакции: на replica set с версии 4.0, на шардированных кластерах с версии 4.2.

При этом документация MongoDB честно предупреждает, что транзакции дороже одиночных операций и не заменяют продуманную схему: часто правильное встраивание данных делает их ненужными. Поэтому правильный вопрос не «SQL или NoSQL», а «какие гарантии даёт **эта** система и какие нужны **моему** приложению».

### Как правильно

Требования к согласованности сверяют с документацией конкретной системы и её конфигурацией.

### Пример

```js
// MongoDB: удалить канал и все его сообщения — всё или ничего
// (Node.js-драйвер; нужна replica set или кластер)
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    await db.collection('groups').updateOne(
      { _id: groupId },
      { $pull: { channels: { id: channelId } } },
      { session },
    );
    await db.collection('messages').deleteMany({ channelId }, { session });
  });
} finally {
  await session.endSession();
}
```

**Источник:** [MongoDB — Transactions](https://www.mongodb.com/docs/manual/core/transactions/) · [MongoDB — Atomicity and Transactions](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/) · [MongoDB — Schema Validation](https://www.mongodb.com/docs/manual/core/schema-validation/)

## П-3. Key-value и транзакции 🟡

### Как в материале

На слайде 6 про key-value хранилища сказано, что они часто не поддерживают транзакции из-за ориентации на масштабирование и высокую скорость.

### Пример из материала

Кода нет.

### В чём несоответствие

Причинная связь «key-value → без транзакций» слишком общая. Например, Redis — одно из самых распространённых key-value хранилищ — выполняет группу команд как единую изолированную операцию через `MULTI`/`EXEC`: команды другого клиента не вклиниваются в середину. Команда `WATCH` добавляет проверку «выполнить, только если ключ не изменился». Отличие от реляционных транзакций тоже есть: Redis **не откатывает** уже выполненные команды транзакции, если одна из них завершилась ошибкой. Именно такие детали и нужно сверять по документации конкретной системы.

### Как правильно

Транзакционные гарантии key-value системы определяются её документацией, а не категорией.

### Пример

```
> SET balance:anna 100
OK
> SET balance:ben 50
OK
> MULTI                      # начало группы
OK
> DECRBY balance:anna 30
QUEUED
> INCRBY balance:ben 30
QUEUED
> EXEC                       # обе команды выполнятся подряд, без чужих команд между ними
1) (integer) 70
2) (integer) 80
```

**Источник:** [Redis — Transactions](https://redis.io/docs/latest/develop/using-commands/transactions/)

## П-4. Гибкая схема = «документы разные» 🟡

### Как в материале

На слайдах 4, 8 и 12 NoSQL описан как противоположность схемам, а про документные базы сказано, что документы в одной коллекции могут иметь различную структуру.

### Пример из материала

Кода нет.

### В чём несоответствие

То, что документы **могут** различаться, верно: по умолчанию MongoDB не требует одинаковых полей. Но из формулировки легко вывести «в NoSQL правил для данных нет», а это не так. В MongoDB коллекции можно задать **правила валидации** через `$jsonSchema`: обязательные поля, типы, диапазоны, длины строк. По умолчанию неподходящий документ отклоняется с ошибкой при вставке и обновлении. Гибкая схема описывает возможности хранения, а не призыв хранить данные как попало.

### Как правильно

Гибкая схема по умолчанию плюс валидация там, где у данных есть обязательная форма.

### Пример

```js
db.createCollection('books', {
  validator: {
    $jsonSchema: {
      bsonType: 'object',
      required: ['title', 'price'],
      properties: {
        title: { bsonType: 'string', minLength: 1 },
        price: { bsonType: ['double', 'int', 'decimal'], minimum: 0 },
      },
    },
  },
});

db.books.insertOne({ title: 'Learning Node.js', price: 42.5 });   // ✅
db.books.insertOne({ title: 'No price' });                          // ❌ Document failed validation
```

**Источник:** [MongoDB — Schema Validation](https://www.mongodb.com/docs/manual/core/schema-validation/) · [MongoDB — Specify JSON Schema Validation](https://www.mongodb.com/docs/manual/core/schema-validation/specify-json-schema/)

## П-5. Масштабирование и доступность «из коробки» 🟡

### Как в материале

На слайдах 10–11 перечислены преимущества NoSQL: производительность, горизонтальное масштабирование, высокая доступность, гибкость и глобально согласованный пользовательский опыт — как общие свойства NoSQL-систем.

### Пример из материала

Кода нет.

### В чём несоответствие

Это рекламное обобщение. Каждое из этих свойств — результат архитектуры и настройки конкретной системы, а не ярлыка:

- **горизонтальное масштабирование** в MongoDB — это шардирование. Оно распределяет данные по шардам по ключу шардирования, но добавляет сложность: неудачный ключ перегружает один шард, а запросы без ключа рассылаются на все шарды;
- **высокая доступность** — это репликация (replica set), которую нужно развернуть и обслуживать; один сервер MongoDB ничем не доступнее одного сервера PostgreSQL;
- **«глобально согласованный опыт»** — работа в нескольких регионах всегда требует выбора компромисса между задержкой, доступностью и согласованностью.

Реляционные базы тоже умеют репликацию и распределение — возможности сравнивают у конкретных продуктов.

### Как правильно

Масштабирование и доступность — свойства развёртывания, за которые платят сложностью; сначала оптимизируют запросы и индексы.

### Пример

```js
// Перед мыслями о шардировании — посмотреть, как выполняется медленный запрос
db.messages.find({ channelId: 5 }).sort({ sentAt: -1 }).limit(20).explain('executionStats');
// "COLLSCAN" в плане — перебор всей коллекции; индекс часто решает проблему:
db.messages.createIndex({ channelId: 1, sentAt: -1 });
```

**Источник:** [MongoDB — Sharding](https://www.mongodb.com/docs/manual/sharding/) · [MongoDB — Replication](https://www.mongodb.com/docs/manual/replication/) · [MongoDB — Indexes](https://www.mongodb.com/docs/manual/indexes/)

## П-6. «Неструктурированные данные», категории, «самая используемая» 🟡

### Как в материале

На слайдах 5, 8–9 и 13–14 NoSQL связывается прежде всего с неструктурированными данными; мультимодельные базы перечислены отдельной категорией рядом с key-value, документными, графовыми и wide-column; в перечне продуктов MongoDB названа самой используемой NoSQL-базой.

### Пример из материала

Кода нет.

### В чём несоответствие

1. **Документы — структурированные данные.** У документа есть поля, типы и вложенность; просто схема может быть гибкой. «Неструктурированные» — это, скорее, произвольный текст или файлы.
2. **Классификация условна.** Четыре типа — распространённая учебная группировка, а не стандарт. Мультимодельный продукт не образует отдельной «пятой модели», а сочетает несколько существующих.
3. **«Самая используемая»** — утверждение без метрики (по чему считать: скачивания, вакансии, упоминания?) и без даты. Рейтинги меняются, поэтому такое утверждение нельзя проверить и не стоит запоминать как факт.

### Как правильно

Документы — структурированные данные с гибкой схемой; категории NoSQL — учебная классификация; сравнения популярности — только с источником, метрикой и датой.

### Пример

```js
// Структурированный документ: поля, типы, вложенность
{ _id: 1, username: 'anna', role: 'groupadmin',
  profile: { birthdate: ISODate('2001-05-14'), age: 25 } }

// Неструктурированные данные — например, текст файла целиком
"Протокол встречи 24.09: обсудили дедлайн, решили..."
```

**Источник:** [MongoDB — Documents](https://www.mongodb.com/docs/manual/core/document/) · [MongoDB — BSON Types](https://www.mongodb.com/docs/manual/reference/bson-types/)

## П-7. Документы «самодостаточны» 🟡

### Как в материале

На слайде 8 документы описаны как самодостаточные единицы данных; связи между документами и способы их хранить в этом разделе не раскрыты.

### Пример из материала

Кода нет.

### В чём несоответствие

Без разговора о связях складывается ложный вывод: «если у данных есть связи, нужна SQL-база». В MongoDB связи моделируют двумя способами:

- **встраивание** — связанные данные внутри документа; подходит, когда они читаются вместе и их немного. Операция над одним документом атомарна, поэтому встраивание ещё и упрощает согласованность;
- **ссылки** — в документе хранится `_id` другого документа; подходит, когда связанных данных много, они растут без ограничений или нужны отдельно. Для соединения в запросе есть стадия агрегации `$lookup`.

Документ ограничен 16 МБ, поэтому бесконечно растущие списки (например, все сообщения канала) не встраивают.

### Как правильно

Выбор между встраиванием и ссылкой определяется тем, какие данные читаются и меняются вместе, их количеством и тем, нужны ли они отдельно.

### Пример

```js
// Встраивание: каналы внутри группы
db.groups.insertOne({ _id: 1, name: 'Study Group',
  channels: [{ id: 1, name: 'general' }, { id: 2, name: 'homework' }] });

// Ссылки: сообщение ссылается на автора
db.messages.insertOne({ channelId: 2, authorId: 3, text: 'Когда дедлайн?', sentAt: new Date() });

// $lookup: сообщения канала вместе с данными автора
db.messages.aggregate([
  { $match: { channelId: 2 } },
  { $lookup: { from: 'users', localField: 'authorId', foreignField: '_id', as: 'author' } },
]);
```

**Источник:** [MongoDB — Embedded Data](https://www.mongodb.com/docs/manual/data-modeling/embedding/) · [MongoDB — Referenced Data](https://www.mongodb.com/docs/manual/data-modeling/referencing/) · [MongoDB — $lookup](https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/) · [MongoDB — BSON Document Size Limit](https://www.mongodb.com/docs/manual/reference/limits/#mongodb-limit-BSON-Document-Size)
