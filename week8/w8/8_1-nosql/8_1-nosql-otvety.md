## A. База данных и модели

<a id="a-1"></a>

### 1. Почему не JSON-файл

**Ответ:**

1. на каждую операцию читается и перезаписывается весь файл;
2. одновременные записи затирают друг друга — очередь приходится писать самому;
3. поиск — только перебором всего массива, индексов нет;
4. нет правил для данных и защиты от испорченного файла при сбое посреди записи.

**Подробнее:** [Конспект §1.1](8_1-nosql-konspekt.md#s1-1) · [← вопрос](8_1-nosql-voprosy.md#q-1)

<a id="a-2"></a>

### 2. База данных и DBMS

**Ответ:** база данных — организованный набор данных, который хранится постоянно и из которого их можно эффективно получать и изменять. DBMS — программа, которая с базой работает. Кроме CRUD, обычно умеет: выполнять запросы, строить индексы, управлять одновременным доступом, проверять правила для данных, помогать с резервным копированием. Набор возможностей зависит от продукта.

**Подробнее:** [Конспект §1.2](8_1-nosql-konspekt.md#s1-2) · [← вопрос](8_1-nosql-voprosy.md#q-2)

<a id="a-3"></a>

### 3. Реляционная модель

**Ответ:**

- **таблица** — набор строк одинаковой структуры со столбцами заданных типов;
- **первичный ключ** — столбец, однозначно определяющий строку;
- **внешний ключ** — столбец, ссылающийся на первичный ключ другой таблицы;
- **`JOIN`** — соединение строк разных таблиц по ключам в одном запросе.

**Подробнее:** [Конспект §2.1](8_1-nosql-konspekt.md#s2-1) · [← вопрос](8_1-nosql-voprosy.md#q-3)

<a id="a-4"></a>

### 4. Что такое NoSQL

**Ответ:** обычно — *Not only SQL*. Это общее название семейства нереляционных баз с разными моделями (документы, ключ–значение, графы, широкие столбцы), разными языками запросов и разными гарантиями. Поэтому о свойствах говорят применительно к конкретной системе, а не к «NoSQL вообще».

**Подробнее:** [Конспект §2.2](8_1-nosql-konspekt.md#s2-2) · [← вопрос](8_1-nosql-voprosy.md#q-4)

## B. Модели NoSQL

<a id="a-5"></a>

### 5. Ключ–значение

**Ответ:** естественна, когда значение ищут по заранее известному ключу: сессии, кэш, счётчики, флаги. Обычно нельзя эффективно спросить по содержимому значения — например, «все сессии с ролью groupadmin»: хранилище не видит структуру значения.

**Подробнее:** [Конспект §3.1](8_1-nosql-konspekt.md#s3-1) · [Пример 1](8_1-nosql-primery.md#ex-1) · [← вопрос](8_1-nosql-voprosy.md#q-5)

<a id="a-6"></a>

### 6. Документ и значение

**Ответ:** MongoDB «видит» структуру документа: по любому полю, в том числе вложенному (`author.username`), можно искать, сортировать и строить индексы. Значение в key-value для хранилища — непрозрачный набор данных, доступный только по ключу.

**Подробнее:** [Конспект §3.2](8_1-nosql-konspekt.md#s3-2) · [← вопрос](8_1-nosql-voprosy.md#q-6)

<a id="a-7"></a>

### 7. Графы и широкие столбцы

**Ответ:** графовая модель — для запросов, которые ходят по связям: «друзья друзей», рекомендации, кратчайший путь. В базах с широкими столбцами запросы проектируют заранее под ключ раздела и порядок; произвольные соединения обычно не поддерживаются, и под новый вид запроса часто создают отдельную таблицу.

**Подробнее:** [Конспект §3.3](8_1-nosql-konspekt.md#s3-3) · [Конспект §3.4](8_1-nosql-konspekt.md#s3-4) · [← вопрос](8_1-nosql-voprosy.md#q-7)

<a id="a-8"></a>

### 8. Подбери модель

**Ответ:**

- а) ключ–значение — поиск по известному ключу-токену, часто со сроком жизни;
- б) граф — запрос проходит по связям в два шага;
- в) документы — поля, которые читаются вместе, с вложенными объектами;
- г) широкие столбцы (или специализированная база временных рядов) — огромный поток записей и запросы по ключу устройства и времени.

**Пояснение:** это типичные соответствия, а не приговор: окончательный выбор зависит от запросов и нагрузки.

**Подробнее:** [Схема выбора в примерах](8_1-nosql-primery.md#ex-0) · [← вопрос](8_1-nosql-voprosy.md#q-8)

## C. Критическое чтение материала

<a id="a-9"></a>

### 9. NoSQL и согласованность

**Ответ:** нет. Гарантии зависят от конкретной системы. MongoDB, например, атомарно выполняет операции над одним документом и поддерживает многодокументные ACID-транзакции (на replica set и шардированных кластерах). Требования к согласованности сверяют с документацией выбранной базы.

**Подробнее:** [Конспект §5.4](8_1-nosql-konspekt.md#s5-4) · [П-2](8_1-nosql-popravki.md#p-2) · [← вопрос](8_1-nosql-voprosy.md#q-9)

<a id="a-10"></a>

### 10. Key-value и транзакции

**Ответ:** нет. Например, Redis выполняет группу команд `MULTI` … `EXEC` как единую изолированную операцию, а `WATCH` позволяет выполнить её, только если ключ не изменился. При этом отката уже выполненных команд Redis не делает — такие детали и надо смотреть в документации.

**Подробнее:** [П-3](8_1-nosql-popravki.md#p-3) · [← вопрос](8_1-nosql-voprosy.md#q-10)

<a id="a-11"></a>

### 11. Гибкая схема

**Ответ:** нет. Гибкая схема значит, что база **позволяет** документам различаться. В MongoDB коллекции можно задать правила `$jsonSchema`: обязательные поля, типы, длины, диапазоны. Неподходящий документ будет отклонён.

**Подробнее:** [Конспект §5.3](8_1-nosql-konspekt.md#s5-3) · [П-4](8_1-nosql-popravki.md#p-4) · [Пример 2](8_1-nosql-primery.md#ex-2) · [← вопрос](8_1-nosql-voprosy.md#q-11)

<a id="a-12"></a>

### 12. Масштабирование «из коробки»

**Ответ:** это свойства развёртывания, а не ярлыка. Горизонтальное масштабирование в MongoDB — это шардирование, которое нужно спроектировать (ключ шардирования) и обслуживать. Доступность — это репликация, которую нужно развернуть. Реляционные базы тоже умеют репликацию и распределение. Сравнивают конкретные продукты и их цену.

**Подробнее:** [Конспект §4.1](8_1-nosql-konspekt.md#s4-1) · [П-5](8_1-nosql-popravki.md#p-5) · [← вопрос](8_1-nosql-voprosy.md#q-12)

<a id="a-13"></a>

### 13. «Неструктурированные» и «самая используемая»

**Ответ:** документы — **структурированные** данные: у них есть поля, типы и вложенность, просто схема может быть гибкой. «Самая используемая» — сравнение без метрики и даты: неясно, что считать (скачивания, вакансии, упоминания), а рейтинги меняются. Такое утверждение нельзя проверить.

**Подробнее:** [П-6](8_1-nosql-popravki.md#p-6) · [← вопрос](8_1-nosql-voprosy.md#q-13)

## D. Масштабирование

<a id="a-14"></a>

### 14. Вертикальное и горизонтальное

**Ответ:** вертикальное — более мощный сервер; просто, но у одного сервера есть предел, и мощное железо дорого. Горизонтальное — больше серверов с распределением данных и нагрузки; предел отодвигается, но система становится распределённой и сложнее в обслуживании.

**Подробнее:** [Конспект §4.2](8_1-nosql-konspekt.md#s4-2) · [← вопрос](8_1-nosql-voprosy.md#q-14)

<a id="a-15"></a>

### 15. Репликация и шардирование

**Ответ:** репликация хранит **копии** одних данных на нескольких серверах — для доступности и сохранности. Шардирование делит данные на **части** по шардам — для объёма и нагрузки. Ключ шардирования определяет, на какой шард попадёт запись. Неудачный ключ перегружает один шард, а запросы без ключа приходится рассылать на все шарды.

**Подробнее:** [Конспект §4.3](8_1-nosql-konspekt.md#s4-3) · [П-5](8_1-nosql-popravki.md#p-5) · [← вопрос](8_1-nosql-voprosy.md#q-15)

<a id="a-16"></a>

### 16. Медленный запрос

**Ответ:** сначала — план запроса (`explain`): нет ли перебора всей коллекции (`COLLSCAN`). Затем — индекс под фильтр и сортировку (например, `{ channelId: 1, sentAt: -1 }`), ограничение количества (`limit`), возвращаемые поля и ресурсы сервера. Шардирование — последняя мера.

**Подробнее:** [П-5, пример с explain](8_1-nosql-popravki.md#p-5) · [Пример 3, индекс](8_1-nosql-primery.md#ex-3) · [← вопрос](8_1-nosql-voprosy.md#q-16)

## E. MongoDB

<a id="a-17"></a>

### 17. Термины

**Ответ:** таблица → коллекция, строка → документ, столбец → поле, первичный ключ → `_id`, `JOIN` → встраивание данных или стадия агрегации `$lookup`.

**Подробнее:** [Конспект §5.1](8_1-nosql-konspekt.md#s5-1) · [← вопрос](8_1-nosql-voprosy.md#q-17)

<a id="a-18"></a>

### 18. BSON и `_id`

**Ответ:** BSON — двоичный формат, в котором MongoDB хранит документы. В отличие от JSON, в нём есть дополнительные типы: `ObjectId`, `Date`, разные виды чисел. Если вставить документ без `_id`, MongoDB сама добавит `_id` с новым `ObjectId`.

**Подробнее:** [Конспект §5.2](8_1-nosql-konspekt.md#s5-2) · [← вопрос](8_1-nosql-voprosy.md#q-18)

<a id="a-19"></a>

### 19. Валидация

**Ответ:**

1. запишется — все обязательные поля нужных типов;
2. отклонена с ошибкой `Document failed validation` — нет обязательного `sentAt`;
3. запишется — поле `pinned` не описано в правиле, а дополнительные поля разрешены (схема по-прежнему гибкая).

**Подробнее:** [Пример 2](8_1-nosql-primery.md#ex-2) · [Конспект §5.3](8_1-nosql-konspekt.md#s5-3) · [← вопрос](8_1-nosql-voprosy.md#q-19)

<a id="a-20"></a>

### 20. Нужна ли транзакция

**Ответ:**

- а) нет — меняется один документ группы, а операция над одним документом атомарна;
- б) да — меняются документы в двух коллекциях, и промежуточное состояние (канал удалён, а сообщения остались) недопустимо.

Для транзакций нужна replica set или шардированный кластер: на одиночном сервере их нет. Локально запускают replica set из одного узла.

**Подробнее:** [Конспект §5.4](8_1-nosql-konspekt.md#s5-4) · [Пример 4](8_1-nosql-primery.md#ex-4) · [← вопрос](8_1-nosql-voprosy.md#q-20)

<a id="a-21"></a>

### 21. Встраивать или ссылаться

**Ответ:**

- а) каналы группы — **встраивать**: их немного, читаются вместе с группой, принадлежат только ей;
- б) сообщения канала — **ссылаться** (отдельная коллекция с `channelId`): их неограниченно много, загружают порциями;
- в) автор сообщения — **ссылка** `authorId`: пользователь нужен отдельно и является автором многих сообщений; имя при выводе подтягивают через `$lookup` (или хранят копию имени, если оно почти не меняется).

**Подробнее:** [Конспект §6](8_1-nosql-konspekt.md#s6) · [Пример 3](8_1-nosql-primery.md#ex-3) · [← вопрос](8_1-nosql-voprosy.md#q-21)

<a id="a-22"></a>

### 22. Все сообщения в документе канала

**Ответ:**

1. размер документа ограничен 16 МБ, а сообщения растут без ограничений;
2. каждый раз, когда нужна группа, пришлось бы читать все сообщения, и каждое новое сообщение переписывало бы большой документ.

**Подробнее:** [Конспект §5.2](8_1-nosql-konspekt.md#s5-2) · [П-7](8_1-nosql-popravki.md#p-7) · [← вопрос](8_1-nosql-voprosy.md#q-22)

<a id="a-23"></a>

### 23. Объясни выбор

**Ответ (пример рассуждения):**

- главные запросы — «группы пользователя», «каналы группы», «последние сообщения канала» — это запросы по полям;
- данные удобно представлять документами: группа с каналами читается целиком, сообщение — вместе с автором;
- объём небольшой, огромной нагрузки нет — шардирование не нужно;
- нужная согласованность обеспечивается атомарностью одного документа и, где надо, транзакциями.

**Пояснение:** это аргументы из запросов и данных, а не «NoSQL быстрее» — такой аргумент ничего не доказывает.

**Подробнее:** [Конспект §4.4](8_1-nosql-konspekt.md#s4-4) · [Конспект §7](8_1-nosql-konspekt.md#s7) · [← вопрос](8_1-nosql-voprosy.md#q-23)
