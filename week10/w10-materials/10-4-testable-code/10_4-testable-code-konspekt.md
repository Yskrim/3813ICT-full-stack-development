## 1. Почему тестируемость зависит от устройства кода

В 10_2 и 10_3 мы писали тесты и несколько раз меняли **сам код**, чтобы его можно было протестировать: вынесли `app.js` отдельно от `server.js`, стали передавать коллекцию в роутер параметром, подменяли сервисы в Angular. Это не случайность: код, который трудно протестировать, обычно и устроен плохо — делает слишком много сразу и жёстко привязан к конкретным зависимостям.

Материал связывает тестируемость с пятью принципами проектирования **SOLID** — по первым буквам английских названий (Robert C. Martin):

| Буква | Принцип | Коротко |
|---|---|---|
| **S** | Single Responsibility | у модуля одна причина для изменения |
| **O** | Open/Closed | расширяем поведение, не переписывая работающий код |
| **L** | Liskov Substitution | подтип можно подставить вместо базового типа без сюрпризов |
| **I** | Interface Segregation | клиент не зависит от методов, которые не использует |
| **D** | Dependency Inversion | код зависит от абстракций, а не от конкретных реализаций |

## 2. S — принцип единственной ответственности

Материал формулирует так: объект должен делать одну вещь и только одну. Пример — функция или компонент, который загружает данные, фильтрует их, загружает ещё данные и показывает результат: такой код трудно тестировать. Лучше, если каждое действие выполняется отдельно, — тогда «у вас будет три отдельные функции», и каждую можно проверить.

Идея верная, но две детали стоит уточнить. У Роберта Мартина принцип звучит точнее: у модуля должна быть **одна причина для изменения** (один «хозяин» требований), а не «одно действие» — функция может выполнять несколько шагов одной задачи. И в примере перечислены **четыре** действия (загрузить, отфильтровать, загрузить ещё, показать), а не три. ⚠ [П-1](10_4-testable-code-popravki.md#p-1)

Для тестов принцип даёт главное: маленькую функцию с одной задачей проверяют без подготовки окружения. Функцию «отфильтровать» проверяют массивом в памяти — без сервера и без шаблона ([примеры, пример 1](10_4-testable-code-primery.md#ex-1)).

```ts
// ❌ Всё в одном методе: чтобы проверить фильтр, нужен HTTP и отрисовка
loadAndShow() {
  this.http.get<Product[]>('/api/products').subscribe((list) => {
    this.visible = list.filter((p) => p.units > 0 && p.price <= this.maxPrice);
  });
}

// ✅ Фильтр — отдельная чистая функция; её тест — одна строка
export const inStockUnder = (list: Product[], max: number) =>
  list.filter((p) => p.units > 0 && p.price <= max);
```

## 3. O — принцип открытости/закрытости

**Принцип открытости/закрытости** — модуль открыт для расширения и закрыт для изменения: новое поведение добавляют новым кодом, не переписывая уже работающий и протестированный.

Материал предлагает для этого добавлять в класс **новые методы** вместо изменения существующих: если список нужен по убыванию, а метод возвращает по возрастанию, написать отдельный метод, который принимает список и разворачивает его. Две функции остаются рабочими и протестированными.

Совет «не ломать работающий метод» полезен, но это ещё не сам принцип: добавление метода — тоже изменение класса. Смысл OCP — в том, чтобы точка расширения была **заранее**: код принимает стратегию (функцию, объект с интерфейсом), и новый вариант поведения — это новая реализация, а код, который её использует, не меняется. ⚠ [П-2](10_4-testable-code-popravki.md#p-2)

```ts
type SortStrategy = (a: Product, b: Product) => number;

export const byPriceAsc: SortStrategy = (a, b) => a.price - b.price;
export const byPriceDesc: SortStrategy = (a, b) => b.price - a.price;    // новое поведение — новая функция
export const byName: SortStrategy = (a, b) => a.name.localeCompare(b.name);

export function sortProducts(list: Product[], strategy: SortStrategy): Product[] {
  return [...list].sort(strategy);          // этот код не меняется при добавлении новых сортировок
}
```

Для тестов: `sortProducts` проверяют один раз, каждую стратегию — отдельно, и новая стратегия не требует перепроверять старые.

## 4. L — принцип подстановки Лисков

Материал описывает принцип так: класс, который использует другой класс, должен принимать и другой класс, не замечая разницы; нужна слабая связанность — как «чёрный ящик»: известный вход — известный выход. Это позволяет подменять внешние сервисы в тестах.

Описание смешивает два разных принципа. «Зависеть от абстракции и подменять реализацию» — это **инверсия зависимостей** ([§6](#s6)). **Принцип подстановки Лисков** (Barbara Liskov) — о правильном наследовании и реализации интерфейсов: **подтип можно использовать везде, где ожидается базовый тип, и программа остаётся корректной**. Подтип не должен требовать больше, обещать меньше или вести себя неожиданно. ⚠ [П-3](10_4-testable-code-popravki.md#p-3)

Связь с тестами при этом прямая: подмена в тесте — это тоже подтип. Если подмена ведёт себя не так, как настоящий сервис (возвращает массив вместо Observable, не бросает ошибок, которые бросает настоящий), тесты проходят, а приложение ломается ([10_3 П-4](10_3-vitest-popravki.md#p-4)).

```ts
interface ProductStore {
  save(p: ProductInput): Promise<Product>;      // обещание: сохраняет или отклоняет с ошибкой
}

// ❌ Нарушение LSP: реализация «удовлетворяет» интерфейсу по типам, но не по смыслу
class ReadonlyStore implements ProductStore {
  save(): Promise<Product> { throw new Error('read only'); }   // синхронно бросает вместо отклонённого Promise
}
// Код, который делает `await store.save(p)` внутри try/catch, переживёт это,
// а код `store.save(p).catch(...)` упадёт: ошибка вылетит до .catch
```

## 5. I — принцип разделения интерфейсов

**Принцип разделения интерфейсов** — ни один клиент не должен зависеть от методов, которые он не использует. Материал формулирует это верно и прямо связывает с тестами: если сервис большой, а компоненту нужен один метод, подмена всё равно должна «реализовать» всё остальное. Поэтому сервисы делают маленькими и разбивают на независимые части.

```ts
// ❌ Один большой сервис: подмене для страницы списка нужны все семь методов
// ProductService: list, get, add, update, remove, count, checkId

// ✅ Компонент зависит только от того, что использует
export abstract class ProductReader {
  abstract list(): Observable<Product[]>;
}

// Подмена в тесте списка — один метод
const reader: ProductReader = { list: () => of([{ _id: '1', id: 1, name: 'Pen', description: '', price: 1, units: 5 }]) };
```

## 6. D — принцип инверсии зависимостей

**Принцип инверсии зависимостей** — модули верхнего уровня не зависят от модулей нижнего уровня; и те и другие зависят от абстракций. Материал формулирует его верно: зависеть от интерфейсов и контрактов, а не от конкретных реализаций.

Именно этот принцип делает код тестируемым. В 10_2 роутер получал коллекцию **параметром** — тест подставил поддельную ([10_2, пример 2](10_2-mocha-primery.md#ex-2)). В Angular то же делает **внедрение зависимостей**: компонент просит абстракцию, а какая реализация придёт, решают провайдеры — рабочие в `app.config.ts` и поддельные в тесте.

```ts
// Абстракция — абстрактный класс служит и типом, и токеном для DI
export abstract class Clock {
  abstract now(): Date;
}

@Injectable()
export class SystemClock extends Clock {
  now() { return new Date(); }
}

// app.config.ts:  { provide: Clock, useClass: SystemClock }
// в тесте:        { provide: Clock, useValue: { now: () => new Date('2026-10-01T10:00:00Z') } }

@Component({ selector: 'app-message-time', template: `{{ label() }}` })
export class MessageTimeComponent {
  private clock = inject(Clock);                   // зависит от абстракции, не от new Date()
  readonly sentAt = input.required<Date>();
  protected label = computed(() => {
    const minutes = Math.round((this.clock.now().getTime() - this.sentAt().getTime()) / 60000);
    return minutes < 1 ? 'только что' : `${minutes} мин назад`;
  });
}
```

С настоящим `new Date()` внутри компонента результат теста зависел бы от того, когда он запущен. С абстракцией `Clock` время в тесте фиксировано ([примеры, пример 2](10_4-testable-code-primery.md#ex-2)).

## 7. Ключевые факты

- Трудно тестируемый код обычно плохо устроен: делает много сразу и жёстко привязан к зависимостям.
- **S:** одна причина для изменения; маленькие функции тестируются без окружения.
- **O:** новое поведение — новой реализацией через заранее заданную точку расширения (стратегию), не правкой рабочего кода.
- **L:** подтип подставляется вместо базового типа без нарушения ожиданий; подмена в тесте тоже должна вести себя как настоящая реализация.
- **I:** клиент зависит только от нужных методов; маленькие интерфейсы — маленькие подмены.
- **D:** зависимость от абстракций; в Angular — провайдеры DI, в Node.js — передача зависимостей параметром.
