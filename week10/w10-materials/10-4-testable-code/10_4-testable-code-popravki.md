## П-1. Единственная ответственность 🟡

### Как в материале

Слайд 3: объект должен делать одну вещь и только одну. Функция или компонент, который загружает данные, фильтрует, загружает ещё и показывает, выполняет несколько действий и трудно тестируется; лучше выполнять каждое действие отдельно — «(load data, apply filter, load data, display in UI) This means that you will have three separate functions».

### В чём несоответствие

1. **«Одна вещь»** — упрощение. Роберт Мартин формулирует принцип как «у модуля одна причина для изменения», то есть он отвечает перед одним источником требований. Функция может делать несколько шагов одной задачи и не нарушать принцип; нарушение — когда в одном месте смешаны, например, загрузка данных (меняется при смене API) и отображение (меняется при смене дизайна).
2. **Счёт в примере:** перечислены четыре действия, а вывод — «три отдельные функции».

### Как правильно

Разделять код по причинам изменения: данные, правила, отображение.

### Пример

```ts
// Причина 1: как получать данные (API)
list(): Observable<Product[]> { return this.http.get<Product[]>('/api/products'); }
// Причина 2: правило отбора (бизнес-требование)
export const inStockUnder = (l: Product[], max: number) => l.filter((p) => p.units > 0 && p.price <= max);
// Причина 3: как показывать (шаблон компонента)
```

**Источник:** [Robert C. Martin — The Single Responsibility Principle (2014)](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html)

## П-2. Открытость/закрытость 🟡

### Как в материале

Слайд 4: класс открыт для расширения и закрыт для изменения; если нужна новая функциональность, лучше создать новые методы, чем менять существующие. Пример — список отсортирован по возрастанию, а нужен по убыванию: вместо изменения метода создать новый, который принимает список и выводит его по убыванию; обе функции остаются протестированными.

### В чём несоответствие

Совет «не переписывать работающий метод» разумный, но добавление метода в класс — это тоже **изменение** класса: каждый новый вариант поведения снова требует его правки. Смысл принципа (Бертран Мейер, в современной трактовке — Роберт Мартин) — в заранее заданной **точке расширения**: код работает через абстракцию (интерфейс, стратегию, функцию-параметр), а новое поведение добавляется **новой реализацией** без правки кода, который её использует.

### Как правильно

Стратегия или полиморфизм: новое поведение — новый класс или функция, старый код не меняется.

### Пример

```ts
type SortStrategy = (a: Product, b: Product) => number;
export const sortProducts = (list: Product[], s: SortStrategy) => [...list].sort(s);

// Новое требование — новая стратегия; sortProducts и её тесты не меняются
export const byUnitsDesc: SortStrategy = (a, b) => b.units - a.units;
```

**Источник:** [Robert C. Martin — The Open Closed Principle (2014)](https://blog.cleancoder.com/uncle-bob/2014/05/12/TheOpenClosedPrinciple.html)

## П-3. Подстановка Лисков 🟡

### Как в материале

Слайд 5: класс, который использует другой класс, должен принимать и другой класс, не зная разницы; нужна слабая связанность — «чёрный ящик»: известный вход — известный выход, неважно как. Это важно для тестируемости, так как позволяет подменять внешние сервисы и подавать разные данные.

### В чём несоответствие

Описание относится к **инверсии зависимостей** и слабой связанности (слайд 7), а не к принципу Лисков. Принцип подстановки (Barbara Liskov, Jeannette Wing) — о **поведении подтипов**: если `S` — подтип `T`, то объекты `T` можно заменить объектами `S`, и все свойства программы, на которые она опирается, сохранятся. Подтип не должен усиливать требования к входу, ослаблять обещания о результате и бросать неожиданные ошибки.

Для тестов это важно по-своему: подмена в тесте — тоже подтип. Если она нарушает контракт настоящего сервиса (синхронный результат вместо Observable, нет ошибок, которые бывают у настоящего), тесты проходят, а приложение ломается.

### Как правильно

LSP — подтип сохраняет контракт базового типа; «зависеть от абстракции и подменять» — инверсия зависимостей.

### Пример

```ts
interface ProductStore { save(p: ProductInput): Promise<Product>; }   // контракт: результат или отклонённый Promise

// ✅ подмена соблюдает контракт — ошибку отдаёт через отклонённый Promise
const failingStore: ProductStore = { save: async () => { throw new Error('duplicate'); } };

// ❌ нарушает: бросает синхронно, код store.save(p).catch(...) не перехватит ошибку
const brokenStore: ProductStore = { save: () => { throw new Error('duplicate'); } };
```

**Источник:** [Barbara Liskov, Jeannette Wing — A Behavioral Notion of Subtyping (1994)](https://dl.acm.org/doi/10.1145/197320.197383) · [Robert C. Martin — The Liskov Substitution Principle (1996)](https://web.archive.org/web/20151128004108/http://www.objectmentor.com/resources/articles/lsp.pdf)
