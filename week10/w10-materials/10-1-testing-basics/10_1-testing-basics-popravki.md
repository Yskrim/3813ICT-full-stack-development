## П-1. Test Driven Development 🟡

### Как в материале

Слайд 4 «Test Driven Development»: тестирование стоит рассматривать на протяжении всего жизненного цикла; тесты проектируют и пишут каждый раз, когда пишется новый код; этап тестирования нужен для исправления оставшихся ошибок, а не для того, чтобы задним числом добавлять тесты.

### Пример из материала

Кода нет.

### В чём несоответствие

Мысль слайда верная, но это описание непрерывного тестирования, а не TDD. У TDD есть конкретное определение: тест пишут **до** кода, который он проверяет, и работают короткими циклами — написать падающий тест (Red), написать минимальный код, чтобы он прошёл (Green), улучшить код, сохраняя тесты зелёными (Refactor). Без этого цикла «TDD» остаётся просто названием.

### Как правильно

TDD — цикл Red → Green → Refactor с тестом перед кодом.

### Пример

```js
// 1. Red — теста для slugify ещё нет кода; тест падает
it('делает slug из названия', () => {
  assert.strictEqual(slugify('Study Group'), 'study-group');
});

// 2. Green — минимальный код
function slugify(s) { return s.toLowerCase().replace(/\s+/g, '-'); }

// 3. Refactor — улучшаем (например, обрезаем пробелы по краям), тест остаётся зелёным
function slugify(s) { return s.trim().toLowerCase().replace(/\s+/g, '-'); }
```

**Источник:** [Martin Fowler — Test Driven Development](https://martinfowler.com/bliki/TestDrivenDevelopment.html)

## П-2. «UI-тесты трудно или невозможно автоматизировать» 🔵

### Как в материале

Слайд 5 «Type of Testing»: UI-тесты состоят из сценариев и результатов, проверяют, выполняется ли действие, а не как устроен код; их трудно или невозможно автоматизировать, и выполняют их вручную.

### Пример из материала

Кода нет.

### В чём несоответствие

Так было давно. Сегодня сценарии через интерфейс автоматизируют сквозными тестами: инструмент открывает настоящий браузер, нажимает кнопки, заполняет поля и проверяет результат. Этому посвящена неделя 11 самого курса (Cypress). Angular поддерживает сквозные тесты через `ng e2e` с Cypress, Playwright, WebdriverIO и другими инструментами. Ручное тестирование интерфейса остаётся для того, что трудно формализовать (удобство, внешний вид), но не для повторяющихся сценариев.

### Как правильно

Повторяющиеся сценарии пользователя автоматизируют сквозными тестами; вручную проверяют удобство и то, что трудно выразить проверкой.

### Пример

```ts
// Cypress: сценарий входа — без ручных действий
it('после входа пользователь попадает на страницу аккаунта', () => {
  cy.visit('/login');
  cy.get('[data-cy=email]').type('anna@chat.com');
  cy.get('[data-cy=password]').type('123');
  cy.get('[data-cy=submit]').click();
  cy.url().should('include', '/account');
});
```

**Источник:** [Angular — End to End Testing](https://angular.dev/tools/cli/end-to-end) · [Cypress — Documentation](https://docs.cypress.io/)

## П-3. Таблица тест-кейсов для сложения 🟡

### Как в материале

Слайд 11: пример тест-кейсов для функции, которая складывает два числа. «Missing Input» — второй параметр отсутствует и по умолчанию равен 2, результат 24. «Bad input» — второй параметр строка `"2"`, она приводится к числу, результат 24. «File system not found» — те же 22 и `"2"`, файловую систему не удалось записать, выбрасывается ошибка. «Triggers validation» — те же 22 и `"2"`, выбрасывается ошибка «parameter 2 must be an int».

### Пример из материала

Кода нет (таблица).

### В чём несоответствие

1. **Один вход — три разных результата.** Для `(22, "2")` таблица ждёт одновременно `24`, ошибку файловой системы и ошибку проверки. Функция не может удовлетворить всем трём; по такой таблице нельзя написать тесты.
2. **Требования противоречат друг другу:** «строка приводится к числу» и «строка вызывает ошибку проверки» — взаимоисключающие правила. Сначала выбирают одно требование, потом пишут кейсы под него.
3. **У функции сложения нет файловой системы** — сценарий не относится к тестируемой функции. Если функция зависит от внешнего ресурса, этот ресурс подменяют в тесте, и кейс описывает, что должно произойти при его сбое.
4. Не хватает обычных кейсов: отрицательные и дробные числа.

### Как правильно

Сначала однозначные требования; каждый кейс — уникальный вход и один ожидаемый результат.

### Пример

```js
// Требование: только числа; второй параметр по умолчанию 2
function add(a, b = 2) {
  if (typeof a !== 'number' || typeof b !== 'number') throw new TypeError('arguments must be numbers');
  return a + b;
}

it('складывает два числа', () => assert.strictEqual(add(22, 3), 25));
it('использует 2 по умолчанию', () => assert.strictEqual(add(22), 24));
it('работает с отрицательными', () => assert.strictEqual(add(-5, 2), -3));
it('дробные — с допуском', () => assert.ok(Math.abs(add(0.1, 0.2) - 0.3) < 1e-9));
it('отклоняет строку', () => assert.throws(() => add(22, '2'), TypeError));
```

**Источник:** [Node.js — assert (strictEqual, throws)](https://nodejs.org/api/assert.html)

## П-4. Список фреймворков и «MEAN использует Mocha» 🔵

### Как в материале

Слайд 17: ручное тестирование долгое и дорогое, автоматизация ускоряет его и снижает ошибки; у Node.js много фреймворков — Expresso, Mocha, Intern, Vows, Node unit, Js Unit, Node Tap; стек MEAN использует Mocha как фреймворк модульного тестирования.

### Пример из материала

Кода нет.

### В чём несоответствие

1. **Список устарел.** Expresso, Vows, nodeunit и JsUnit давно не развиваются. Из списка активны Mocha, Intern и node-tap.
2. **Нет упоминания актуальных вариантов:** встроенного в Node.js модуля `node:test` (стабилен с Node.js 20), Jest и Vitest. В Angular 21 Vitest — стандартный инструмент модульных тестов (материал 10_3).
3. **«MEAN использует Mocha»** — у стека MEAN нет официального фреймворка тестирования; Mocha — выбор курса.

### Как правильно

Сервер: Mocha, `node:test` или Jest; Angular 21+: Vitest; браузер: Cypress или Playwright.

### Пример

```js
// node:test — без установки пакетов (node --test)
const test = require('node:test');
const assert = require('node:assert/strict');

test('add', () => {
  assert.equal(1 + 1, 2);        // в node:assert/strict equal — строгое сравнение
});
```

**Источник:** [Node.js — Test runner (node:test)](https://nodejs.org/api/test.html) · [Mocha](https://mochajs.org/) · [Angular — Testing](https://angular.dev/guide/testing)
