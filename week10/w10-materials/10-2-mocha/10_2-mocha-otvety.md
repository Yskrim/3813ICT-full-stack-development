## A. Mocha и проверки

<a id="a-1"></a>

### 1. Зачем `--save-dev`

**Ответ:** у каждого проекта своя зафиксированная версия фреймворка в `package.json`: обновление Mocha в одном проекте не сломает тесты в другом, а `npm install` у другого разработчика или в CI поставит ту же версию. В рабочую сборку сервера зависимости разработки не попадают.

**Подробнее:** [Конспект §1](10_2-mocha-konspekt.md#s1) · [← вопрос](10_2-mocha-voprosy.md#q-1)

<a id="a-2"></a>

### 2. Хуки

**Ответ:** `before` выполняется один раз перед всеми тестами группы, `beforeEach` — перед каждым тестом. `afterEach` очищает данные после каждого теста, чтобы следующий начинал с известного состояния и тесты не зависели от порядка.

**Подробнее:** [Конспект §2](10_2-mocha-konspekt.md#s2) · [← вопрос](10_2-mocha-voprosy.md#q-2)

<a id="a-3"></a>

### 3. Что покажет тест

**Ответ:** пройдёт: `assert.equal` сравнивает через `==`, и `'10' == 10`. Нужен строгий режим: `const assert = require('node:assert/strict')` — тогда `equal` сравнивает через `===`, и тест упадёт.

**Подробнее:** [Конспект §3](10_2-mocha-konspekt.md#s3) · [П-2](10_2-mocha-popravki.md#p-2) · [← вопрос](10_2-mocha-voprosy.md#q-3)

<a id="a-4"></a>

### 4. Ожидаемая ошибка

**Ответ:**

```js
assert.throws(() => add(1, '1'), TypeError);
await assert.rejects(loadUser(999));          // внутри async-теста
```

**Подробнее:** [Конспект §3](10_2-mocha-konspekt.md#s3) · [← вопрос](10_2-mocha-voprosy.md#q-4)

<a id="a-5"></a>

### 5. Слабый тест

**Ответ:** `2 × 2 = 2 + 2`, поэтому тест пройдёт и функция, которая складывает. Кейс должен различать поведение: `mul(3, 4) === 12` (сложение даст 7), плюс отрицательные и ноль.

## B. Асинхронные тесты

<a id="a-6"></a>

### 6. Что покажет Mocha

**Ответ:** тест будет **зелёным**: функция не возвращает Promise, не `async` и не принимает `done`, поэтому Mocha считает её синхронной и завершает тест до ответа. Провал проверки всплывёт позже — в другом тесте или хуке — или потеряется.

```js
it('...', async () => { const res = await fetch(url); assert.equal(res.status, 200); });   // 1
it('...', () => fetch(url).then((res) => assert.equal(res.status, 200)));                 // 2 — return
it('...', (done) => { fetch(url).then((res) => { assert.equal(res.status, 200); done(); }).catch(done); }); // 3
```

## C. Интеграционные тесты

<a id="a-7"></a>

### 7. `chai.request`

**Ответ:** в chai-http 5 API изменился: `chai.request` убрали, вместо него экспортируется `request` — `request.execute(app).get(...)` (Chai и chai-http теперь ES-модули). Второй способ — supertest: `await request(app).get('/api/products').expect(200)`.

**Подробнее:** [Конспект §6.2](10_2-mocha-konspekt.md#s6-2) · [П-5](10_2-mocha-popravki.md#p-5) · [← вопрос](10_2-mocha-voprosy.md#q-7)

<a id="a-8"></a>

### 8. `app.js` и `server.js`

**Ответ:** тест подключает `app.js` и отправляет запросы прямо в приложение — без `listen`, без занятого порта и без подключения к рабочей базе. `server.js` отвечает только за запуск: подключиться к рабочей базе и слушать порт.

**Подробнее:** [Конспект §6.3](10_2-mocha-konspekt.md#s6-3) · [Пример 1](10_2-mocha-primery.md#ex-1) · [← вопрос](10_2-mocha-voprosy.md#q-8)

<a id="a-9"></a>

### 9. Тестовые данные

**Ответ:** каждый запуск оставляет в рабочей базе новый тестовый товар: данные портятся, а тесты, которые считают товары, начинают падать. Правильно: отдельная тестовая база, `before` готовит нужные данные, `afterEach` или `after` удаляет всё, что создал тест; проверять и ответ, и базу.

**Подробнее:** [Конспект §6.2](10_2-mocha-konspekt.md#s6-2) · [П-6](10_2-mocha-popravki.md#p-6) · [← вопрос](10_2-mocha-voprosy.md#q-9)

<a id="a-10"></a>

### 10. Тест без базы

**Ответ:** передавать коллекцию в роутер параметром (фабрика `createProductsRouter(col)`), а в тесте подставить поддельный объект, у которого `insertOne` бросает ошибку с `code: 11000`. supertest отправляет `POST`, тест ждёт `409`.
