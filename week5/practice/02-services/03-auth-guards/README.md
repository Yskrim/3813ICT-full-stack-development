# 2.3 — AuthService и гарды ролей

**Тема:** сервисы и DI (5_2)
**Место в теме:** третье из трёх, рабочий кусок Phase 2
**Время:** 60–80 минут
**Опирается на:** [1.3 — Сессия пользователя без сервера](../../01-storage/03-user-session/README.md), [2.2 — Состояние каналов в сервисе](../02-channel-state/README.md)
**Дальше:** [3.1 — Поймать CORS](../../03-hosting/01-catch-cors/README.md). `AuthService` отсюда понадобится в [4.3](../../04-http/03-messages/README.md) и [6.2](../../06-login/02-angular-login/README.md)

## Задача

В 1.3 у тебя появилась сессия пользователя, но пока она только показывается в шапке — приложение никак не мешает зайти куда угодно. В чате Phase 2 так нельзя: гость не должен видеть каналы, а обычный пользователь — страницу администрирования.

Эту работу делят между собой два механизма. **`AuthService`** знает, кто вошёл и какая у него роль. **Гарды** — функции, которые роутер вызывает перед открытием маршрута, — спрашивают у сервиса и решают, пускать ли. Какая роль нужна для маршрута, записывается в самом маршруте, в поле `data`, поэтому один гард ролей обслуживает сколько угодно страниц.

Здесь `SessionService` из 1.3 вырастает в `AuthService`. Выбор пользователя кнопками переезжает на отдельную страницу входа — в 6.2 её заменит настоящая форма, а всё остальное останется как есть.

## Зачем это задание

Это центральный кусок Phase 2: без него невозможно реализовать роли super admin, group admin и user. А ещё здесь хорошо видно разделение обязанностей: хранение — в `StorageService`, знание о пользователе — в `AuthService`, решение «пускать ли» — в гардах, отображение — в компонентах.

## Что проверяет

1. Ты умеешь строить сервис поверх другого сервиса.
2. Ты пишешь функциональные гарды с `inject()` и возвращаешь `UrlTree` для перенаправления.
3. Ты передаёшь параметры гарду через `data` маршрута.
4. Ты понимаешь границу: роль на клиенте — для интерфейса, не для защиты данных.

## Старт

```bash
ng g s services/auth
ng g guard guards/auth --implements CanActivate
ng g guard guards/role --implements CanActivate
ng g c pages/login
ng g c pages/admin
```

CLI создаст функциональные гарды (в проектах Angular 20+ файлы будут называться `auth-guard.ts`, `role-guard.ts` — это нормально).

Перенеси `TEST_USERS` и интерфейс пользователя в `auth.service.ts`. `SessionService` после переноса логики удали.

Маршруты должны получиться такими (компоненты уже есть):

| Путь | Кто может открыть |
|---|---|
| `/login` | все |
| `/channels` | только вошедшие |
| `/admin` | только `superadmin` и `groupadmin` |
| `/playground`, `/services-lab` | все |
| `''` | перенаправление на `/channels` |

## Что сделать

**Часть А — `AuthService`**

1. Всё, что умел `SessionService`: пользователь в сигнале (снаружи — только чтение), восстановление после F5, синхронизация выхода между вкладками.
2. Производный `isLoggedIn`.
3. Метод `hasRole(...roles)` — есть ли у текущего пользователя одна из ролей.
4. `loginAs(user)` и `logout()`. После выхода — переход на `/login`.

**Часть Б — гарды**

1. `authGuard` пускает только вошедших, остальных отправляет на `/login`.
2. `roleGuard` читает список ролей из `data` маршрута и пускает только их; остальных отправляет на `/channels`.
3. Оба гарда перенаправляют через `UrlTree`, а не через `navigate` + `false`.

**Часть В — интерфейс**

1. `LoginComponent` — три кнопки «Войти как …»; после входа — переход на `/channels`.
2. В шапке ссылка «Администрирование» видна только ролям, которым открыт `/admin`.
3. `AdminComponent` — пока просто заголовок «Администрирование».

**Часть Г — проверка по таблице**

Заполни в `observations.md` таблицу: для каждого пользователя (гость, ben, anna, super) — что происходит при открытии `/channels` и `/admin`. Затем войди как ben, в Application поменяй роль в хранилище на `superadmin` и перезагрузи страницу. Что ты увидел и почему это не дыра в безопасности, если сервер проверяет права сам?

## Критерии готовности

- [ ] Таблица доступа совпадает с требованиями

- [ ] Ссылка «Администрирование» видна только нужным ролям

## Типичные ловушки

- Роли, прописанные прямо в `roleGuard`, — для каждой страницы придётся писать свой гард.
- `roleGuard` без `authGuard` на том же маршруте — у гостя нет роли, и поведение зависит от того, как написан `hasRole`.
- Шапка проверяет роль сравнением строк в шаблоне вместо вызова `hasRole` — правила дублируются.
- Переход в гарде через `navigate` и `return false` — возможна гонка двух навигаций.
