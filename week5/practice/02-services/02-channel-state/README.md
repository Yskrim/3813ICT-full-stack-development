# 2.2 — Состояние каналов в сервисе

**Тема:** сервисы и DI (5_2)
**Место в теме:** второе из трёх, связка концептов
**Время:** 50–70 минут
**Опирается на:** [2.1 — Один экземпляр на всех](../01-one-instance/README.md), [1.2 — StorageService и настройки](../../01-storage/02-storage-service/README.md)
**Дальше:** [2.3 — AuthService и гарды ролей](../03-auth-guards/README.md)

## Задача

В интерфейсе чата список каналов виден слева, а название выбранного канала — в шапке над сообщениями. Это два разных компонента, но показывают они одно и то же состояние: какие каналы есть и какой открыт. Если каждый хранит свою копию, они неизбежно разойдутся: добавил канал слева — шапка не знает, что их стало больше.

Решение ты уже знаешь из 2.1: общий сервис в одном экземпляре. Но теперь в нём настоящие данные, и компоненты должны обновляться сами, когда данные меняются. Для этого состояние сервиса хранится в сигналах, а наружу отдаётся только для чтения — менять его можно лишь через методы сервиса.

И ещё одна деталь из настоящего чата: при следующем открытии приложения должен открываться тот канал, где пользователь был в прошлый раз. Для этого сервис каналов попросит помощи у `PreferencesService` из 1.2 — так ты впервые увидишь, как один сервис использует другой.

Данные пока живут в памяти браузера. В 4.2 такой же сервис будет получать их с сервера.

## Зачем это задание

«Состояние в сервисе, компоненты только показывают и вызывают методы» — главный архитектурный приём Phase 2. Группы, каналы, сообщения, пользователи — всё будет устроено так же.

## Что проверяет

1. Ты умеешь хранить общее состояние в сервисе на сигналах и открывать его только для чтения.
2. Ты обновляешь сигналы с массивами и объектами так, чтобы подписчики узнали об изменении.
3. Ты используешь `computed` для производных значений.
4. Ты внедряешь один сервис в другой.

## Старт

```bash
ng g s services/channel-state
ng g c pages/channels
ng g c components/channel-sidebar
ng g c components/channel-header
```

Модель и начальные данные (положи в `channel-state.service.ts`):

```ts
export interface Channel {
  id: number;
  name: string;
}

const INITIAL_CHANNELS: Channel[] = [
  { id: 1, name: 'general' },
  { id: 2, name: 'random' },
  { id: 3, name: 'homework' },
];
```

Маршрут `{ path: 'channels', component: ChannelsComponent }` и ссылка в навигации. `ChannelsComponent` размещает боковую панель слева и шапку канала справа.

## Что сделать

**Часть А — сервис**

1. Сигналы: список каналов и id выбранного канала. Наружу — версии только для чтения.
2. Производные значения: выбранный канал целиком и количество каналов.
3. Методы:
   - `select(id)` — выбрать канал;
   - `add(name)` — добавить канал; пустое имя и повтор существующего имени не допускаются (подумай, как сообщить компоненту о причине отказа);
   - `remove(id)` — удалить канал; если удалён выбранный, выбор сбрасывается.
4. Выбранный канал запоминается через `PreferencesService` из 1.2 (`lastChannelId`) и восстанавливается при создании сервиса.

**Часть Б — компоненты**

1. `ChannelSidebarComponent` — список каналов с выделением выбранного, клик выбирает канал, у каждого кнопка «×», внизу форма «новый канал» с сообщением об ошибке.
2. `ChannelHeaderComponent` — имя выбранного канала или «Канал не выбран», а также «Каналов: N».
3. Ни один компонент не хранит свою копию списка.

**Часть В — проверка**

1. Добавь канал — счётчик в шапке меняется сразу.
2. Выбери канал, нажми F5 — выбран тот же.
3. Удали выбранный канал — шапка показывает «Канал не выбран».
4. Попробуй изменить список снаружи сервиса (например, из компонента вызвать `set` у сигнала) — компилятор должен не дать.

## Критерии готовности

- [ ] Оба компонента всегда показывают согласованные данные без ручных обновлений
- [ ] Выбранный канал восстанавливается после F5
- [ ] Список нельзя изменить в обход методов сервиса
- [ ] Ошибки добавления (пустое имя, повтор) видны пользователю
- [ ] Ты можешь ответить: почему `list.push(channel)` и повторный `set(list)` не обновит компоненты, а `update(l => [...l, channel])` — обновит?
- [ ] Ты можешь ответить: зачем `asReadonly()`, если можно просто договориться не менять сигнал снаружи?

## Наводящие вопросы (если застрял)

- Как сигнал понимает, что значение изменилось? Что будет, если положить в него тот же массив?
- Какой метод массива возвращает **новый** массив без элемента? А новый массив с элементом?
- Как `add` может сообщить о причине отказа, не бросая исключение? (Например, вернуть строку ошибки или `null`.)
- В каком порядке объявить поля сервиса, чтобы `PreferencesService` уже был доступен, когда читаешь `lastChannelId`?

## Типичные ловушки

- Изменение массива на месте (`push`, `splice`) внутри `update` с возвратом того же массива.
- Шаблон не видит сервис, потому что поле объявлено `private`.
- Генерация `id` через `list.length + 1` — после удаления появятся одинаковые `id`.
- Поле со значением из другого сервиса объявлено выше поля, в которое этот сервис внедряется.
