# 6.3 — Профиль и запись файла

**Тема:** соединяем Node и Angular (5_6)
**Место в теме:** третье из трёх, рабочий кусок Phase 2
**Время:** 70–90 минут
**Опирается на:** [6.2 — Вход из Angular](../02-angular-login/README.md), [4.3 — Сообщения: страницы и перехватчик](../../04-http/03-messages/README.md)
**Дальше:** неделя 5 закончена — пришли решения и переходим к неделе 6

## Задача

Читать данные из JSON-файла ты научился в 6.1. Записывать сложнее, и материал курса показывает это на примере с тремя проблемами: при каждом входе в файл дописывается копия пользователя, в ответ уходят данные всех пользователей, а сервер верит любым присланным данным.

Сделаем правильно на реальной задаче: пользователь редактирует свой профиль — дату рождения и возраст. Сервер находит **существующую** запись и меняет в ней только присланные поля. Проверяет, что значения разумные. Проверяет, что пользователь меняет **свой** профиль, а не чужой. И отвечает только обновлённым профилем.

Остаётся тонкий момент, о котором редко думают: два запроса могут прийти почти одновременно. Оба прочитают старый файл, каждый изменит своё, и второй при записи затрёт изменения первого. Здесь ты научишься выстраивать записи в очередь.

## Зачем это задание

До перехода на MongoDB (неделя 8) данные Phase 2 живут в JSON-файлах, и каждая операция изменения будет устроена так, как ты сделаешь здесь. Заодно это завершает поток: вошёл, увидел свой профиль, изменил, изменения пережили перезагрузку.

## Что проверяет

1. Ты обновляешь существующую запись в файле по схеме «прочитать → изменить → записать».
2. Ты проверяешь входные данные и права на сервере, а не только на клиенте.
3. Ты понимаешь гонку при одновременной записи и умеешь её предотвратить.
4. Ты обновляешь клиентское состояние ответом сервера.

## Старт

```bash
ng g c pages/account
```

Маршрут `/account` (только для вошедших) и ссылка в шапке.

На сервере создай `server/routes/users.js` на `express.Router()` и подключи его на `/api/users` (до `/api` 404).

## Новое в этом задании: очередь записи

Идея: хранить промис **последней** операции записи и запускать каждую следующую только после него — через `.then`. Тогда операции выполняются строго по одной, даже если запросы пришли одновременно. Важно, чтобы ошибка одной операции не «сломала» очередь для следующих. Как именно это записать, придумай сам — это часть задания.

## Что сделать

**Часть А — сервер**

`PATCH /api/users/:id/profile`, тело — любые из полей `birthdate` (строка вида `YYYY-MM-DD`) и `age` (целое от 0 до 130).

1. Нет заголовка `x-user-id` или такого пользователя нет — `401`.
2. `x-user-id` не совпадает с `:id` — `403`: менять можно только свой профиль.
3. Неверные значения — `400` с понятным сообщением.
4. Пользователь с `:id` не найден — `404`.
5. Меняются только присланные поля существующей записи; новых записей не появляется.
6. Файл записывается с отступами (удобно читать глазами).
7. Ответ — обновлённый профиль без пароля.
8. Все операции «прочитать → изменить → записать» идут через очередь.

**Часть Б — клиент**

1. `AuthService.updateProfile(changes)` отправляет `PATCH` на профиль текущего пользователя и после ответа сохраняет новый профиль так же, как после входа.
2. `AccountComponent` показывает имя, роль, дату рождения и возраст (пустые — «не указано»), форму с двумя полями, заполненными текущими значениями, и кнопку «Сохранить». После ответа — «Сохранено» или понятная ошибка.

**Часть В — проверка**

1. Измени профиль, нажми F5 — изменения на месте. Перезапусти сервер, войди заново — изменения в файле.
2. Открой `users.json` — нет ли дублей?
3. Введи возраст 200 — сообщение об ошибке, файл не изменился.
4. Войди как ben и в консоли браузера попробуй изменить профиль anna:

```js
await fetch('/api/users/2/profile', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json', 'x-user-id': '3' },
  body: JSON.stringify({ age: 99 }),
}).then((r) => r.status);
```

5. Проверь очередь: отправь из консоли два запроса **одновременно**, меняющих разные поля одного профиля, и убедись, что в файле сохранились оба изменения:

```js
const send = (body) => fetch('/api/users/2/profile', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json', 'x-user-id': '2' },
  body: JSON.stringify(body),
});
await Promise.all([send({ age: 30 }), send({ birthdate: '1996-01-01' })]);
```

Без очереди потеря одного изменения случается не всегда — это зависит от времени. Поэтому очередь делают не «когда увидели проблему», а сразу.

## Критерии готовности

- [ ] Профиль меняется только у своего пользователя, чужой — `403`
- [ ] Неверные значения — `400`, файл при этом не меняется
- [ ] В файле нет дублей, клиенту не уходят чужие данные и пароли
- [ ] Одновременные запросы не теряют изменения
- [ ] После сохранения интерфейс показывает данные из ответа сервера, и они переживают F5
- [ ] Ты можешь ответить: почему при одновременной записи без очереди одно изменение может пропасть?
- [ ] Ты можешь ответить: почему проверку «свой ли профиль» нельзя делать только на клиенте?
- [ ] Ты можешь ответить: чем твой `PATCH` отличается от `postLoginafter` из материала — назови три отличия

## Типичные ловушки

- `push` новой записи вместо изменения существующей.
- Сравнение `id` без приведения к одному типу: из заголовка и из адреса приходят строки, а в файле `id` — число, и `'2' === 2` ложно.
- Проверка значений после записи файла.
- Форма аккаунта, которая после сохранения показывает свои поля, а не ответ сервера.
