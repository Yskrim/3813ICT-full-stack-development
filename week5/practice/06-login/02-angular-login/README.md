# 6.2 — Вход из Angular

**Тема:** соединяем Node и Angular (5_6)
**Место в теме:** второе из трёх, связка концептов
**Время:** 50–70 минут
**Опирается на:** [6.1 — Вход на сервере](../01-login-route/README.md), [2.3 — AuthService и гарды ролей](../../02-services/03-auth-guards/README.md), [4.3 — Сообщения: страницы и перехватчик](../../04-http/03-messages/README.md)
**Дальше:** [6.3 — Профиль и запись файла](../03-profile/README.md)

## Задача

Сервер умеет проверять пароль — осталось, чтобы Angular им пользовался. Кнопки «Войти как …» из 2.3 уходят: вместо них форма с именем и паролем, а `AuthService` получает метод `login`, который отправляет их на сервер.

Здесь проявится то, ради чего в темах 1 и 2 всё раскладывалось по сервисам. Хранение пользователя, синхронизация вкладок, гарды, шапка, перехватчик — ничего из этого менять не придётся. Изменится только **источник** пользователя: раньше он брался из списка в коде, теперь — из ответа сервера. Если ты всё сделал правильно в прошлых заданиях, правок будет немного.

Важная деталь, на которой ошибается материал курса: профиль (роль, дата рождения, возраст) берётся **из ответа сервера**, а не из полей формы и не из констант в коде.

## Зачем это задание

Это готовый вход для Phase 2. А ещё проверка архитектуры: если для настоящего входа пришлось переписывать гарды или шапку, значит, где-то обязанности были перепутаны.

## Что проверяет

1. Ты отправляешь данные формы через сервис и берёшь профиль из ответа.
2. Ты различаешь ошибки входа по кодам и показываешь их пользователю.
3. Ты понимаешь, что пароль уходит на сервер один раз и нигде больше не хранится.
4. Ты видишь пользу разделения обязанностей из прошлых тем.

## Старт

1. Расширь интерфейс пользователя в `auth.service.ts` полями `birthdate: string | null` и `age: number | null` — такими, как их отдаёт сервер.
2. `FormsModule` понадобится в `imports` страницы входа.

## Что сделать

**Часть А — `AuthService.login`**

1. Метод `login(username, pwd)` отправляет запрос на `/api/login` и возвращает Observable с профилем.
2. После успешного ответа профиль сохраняется так же, как раньше сохранял `loginAs`.
3. `loginAs` и `TEST_USERS` удали.

**Часть Б — форма входа**

1. Поля «Имя» и «Пароль» (второе — `type="password"`), кнопка «Войти».
2. Отправка по кнопке и по Enter.
3. Кнопка неактивна, пока поле пустое.
4. Сообщения об ошибке: неверные данные (`401`), не заполнены поля (`400`), сервер недоступен или сломался (остальные случаи).
5. После успешного входа — переход на `/channels`.
6. Поля по умолчанию пустые — никаких учётных данных в коде.

**Часть В — проверка всего, что уже было**

1. Войди как anna — видна ссылка «Администрирование»; как ben — нет. Таблица доступа из 2.3 выполняется?
2. F5 на `/channels` — пользователь на месте.
3. Выход в одной вкладке разлогинивает другую.
4. Отправь сообщение в `general` — автор правильный (перехватчик берёт настоящий `id`).
5. Неверный пароль, пустое поле, остановленный сервер — понятные сообщения.
6. В Application посмотри, что лежит в хранилище: есть ли там пароль?

## Критерии готовности

- [ ] Вход работает только с верным паролем
- [ ] Всё из части В выполняется без изменений в гардах, шапке и перехватчике (или изменения минимальны, и ты можешь объяснить, почему они понадобились)
- [ ] Профиль в хранилище — из ответа сервера, без пароля
- [ ] В коде нет тестовых учётных данных
- [ ] Ты можешь ответить: какие файлы пришлось изменить при переходе с кнопок на настоящий вход и почему только они?
- [ ] Ты можешь ответить: почему профиль нельзя собирать из полей формы?
- [ ] Ты можешь ответить: зачем форме `ngSubmit`, если можно повесить `(click)` на кнопку?

- Какой оператор RxJS достаёт профиль из ответа `{ ok, user }`, чтобы компонент получил сразу профиль?

## Типичные ловушки

- Пароль сохранён в сервисе «на всякий случай».
- Компонент сам кладёт пользователя в хранилище — сервис и компонент расходятся.
- Проверка `data.ok` в `next` вместо обработки `401` в `error`.
- Кнопка без `<form>` — вход не срабатывает по Enter.
