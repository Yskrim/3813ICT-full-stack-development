# 1.3 — Сессия пользователя без сервера

**Тема:** хранилища браузера (5_1)
**Место в теме:** третье из трёх, рабочий кусок Phase 2
**Время:** 50–70 минут
**Опирается на:** [1.2 — StorageService и настройки](../02-storage-service/README.md)
**Дальше:** [2.1 — Один экземпляр на всех](../../02-services/01-one-instance/README.md), а сессия отсюда станет основой [2.3 — AuthService и гарды ролей](../../02-services/03-auth-guards/README.md)

## Задача

В чате пользователь входит один раз, и дальше приложение помнит, кто он: после F5, в соседней вкладке, завтра. А если он вышел в одной вкладке, остальные тоже должны это заметить, иначе там останется «призрачная» сессия.

Настоящего входа через сервер у нас пока нет — он появится в теме 6. Поэтому сейчас пользователь «входит», просто выбирая себя из списка. Зато всё остальное — как в настоящем приложении: пользователь сохраняется в хранилище, переживает перезагрузку, показывается в шапке, а выход синхронизируется между вкладками.

Заодно ты проведёшь эксперимент, который часто решают неосознанно: что будет, если хранить вход в sessionStorage, а не в localStorage.

## Зачем это задание

Это первая версия механизма, на котором держится весь чат Phase 2: кто вошёл и какая у него роль. В 2.3 ты превратишь его в `AuthService` с гардами, а в 6.2 заменишь выбор из списка на настоящий вход. Логику хранения, которую напишешь сейчас, менять уже не придётся.

## Что проверяет

1. Ты умеешь хранить в браузере объект пользователя и восстанавливать его при загрузке.
2. Ты понимаешь, что пароль и лишние данные в хранилище не кладут.
3. Ты умеешь реагировать на изменения localStorage в других вкладках через событие `storage`.
4. Ты осознанно выбираешь между localStorage и sessionStorage.

## Старт

```bash
ng g s services/session
ng g c components/header
```

Тестовые пользователи (положи в `session.service.ts`, пароли здесь не нужны):

```ts
export interface SessionUser {
  id: number;
  username: string;
  role: 'superadmin' | 'groupadmin' | 'user';
}

export const TEST_USERS: SessionUser[] = [
  { id: 1, username: 'super', role: 'superadmin' },
  { id: 2, username: 'anna', role: 'groupadmin' },
  { id: 3, username: 'ben', role: 'user' },
];
```

Подключи `<app-header />` в шаблон корневого компонента над `<router-outlet />`.

## Что сделать

**Часть А — `SessionService`**

1. Сервис использует `StorageService` из 1.2, а не `localStorage` напрямую.
2. Текущий пользователь хранится в сигнале. При создании сервиса он читается из хранилища — так вход переживает F5.
3. Методы: `loginAs(user)` — сохраняет пользователя, `logout()` — удаляет. Производный сигнал `isLoggedIn`.

**Часть Б — шапка**

1. Если пользователь не вошёл — три кнопки «Войти как super / anna / ben».
2. Если вошёл — «имя · роль» и кнопка «Выйти».
3. Шапка читает сервис, а не хранилище.

**Часть В — выход во всех вкладках**

1. Открой приложение в двух вкладках, войди в одной — во второй после F5 тоже вошёл.
2. Сделай так, чтобы выход в одной вкладке **сразу**, без F5, отражался во второй. Используй событие `storage`.
3. Проверь: во вкладке, где нажат «Выйти», событие не приходит — почему это не проблема?

**Часть Г — эксперимент с sessionStorage**

1. Временно переключи хранение сессии на sessionStorage (подумай, как сделать это одной строкой).
2. Проверь: F5, новая вкладка, дубликат вкладки. Запиши, что изменилось.
3. Верни localStorage и в комментарии в коде объясни, почему для чата выбран он.

## Критерии готовности

- [ ] После F5 пользователь остаётся вошедшим
- [ ] Выход в одной вкладке сразу отражается в другой
- [ ] В хранилище лежат только `id`, `username`, `role`, одной записью
- [ ] Ни компонент, ни `SessionService` не обращаются к `localStorage` напрямую
- [ ] Ты можешь ответить: почему событие `storage` не срабатывает во вкладке, которая сама изменила хранилище?
- [ ] Ты можешь ответить: что увидит пользователь в новой вкладке, если сессия хранится в sessionStorage?
- [ ] Ты можешь ответить: почему роль из хранилища годится для интерфейса, но не для проверки прав?

## Типичные ловушки

- Подписка на `storage` в компоненте шапки — при каждом создании компонента появляется новая подписка.
- Чтение хранилища в шаблоне на каждый кадр вместо сигнала в сервисе.
- Сравнение `event.key` с неправильным ключом — и событие «молча» игнорируется.
- Хранение пользователя несколькими ключами: при выходе один забыт, и вход «наполовину» остаётся.
