# 4.1 — Observable руками

**Тема:** HTTP-запросы (5_4)
**Место в теме:** первое из трёх, базовый концепт
**Время:** 40–50 минут
**Опирается на:** [3.2 — Прокси вместо CORS](../../03-hosting/02-proxy/README.md)
**Дальше:** [4.2 — Группы через HttpClient](../02-group-crud/README.md)

## Задача

`HttpClient` возвращает не данные, а Observable, и первое время это сбивает с толку: почему `const groups = http.get(...)` не список групп? Почему запрос не ушёл? Почему в консоли «конец» напечатался раньше данных?

Чтобы не разбираться с этим на живом коде чата, сначала поиграем с Observable отдельно. Ты создашь несколько потоков вручную, предскажешь порядок вывода, посмотришь, как поток заканчивается ошибкой, а потом отправишь первые запросы через `HttpClient` и проверишь во вкладке Network, когда они на самом деле уходят.

## Зачем это задание

Почти все ошибки с `HttpClient` — это неверные ожидания от Observable: подписка в сервисе вместо компонента, индикатор загрузки, который не гаснет при ошибке, два запроса вместо одного. Каждый из этих случаев ты воспроизведёшь здесь сам.

## Что проверяет

1. Ты понимаешь, когда вызываются `next`, `error`, `complete`.
2. Ты понимаешь, что Observable ленивый: без подписки ничего не происходит.
3. Ты различаешь синхронные и асинхронные потоки.
4. Ты знаешь, как ведёт себя HTTP-Observable: один ответ, каждая подписка — новый запрос, ошибки через `error`.

## Старт

1. Подключи `HttpClient`: в `app.config.ts` добавь `provideHttpClient()` в `providers`.
2. Все опыты — на странице `playground`: по кнопке на опыт, результат — в консоль. Наблюдения записывай в `observations.md`.

## Новое в этом задании: `finalize`

Оператор `finalize` из RxJS вызывает функцию, когда поток закончился — **неважно, успехом или ошибкой**. Он подключается через `pipe` перед подпиской:

```ts
import { of, finalize } from 'rxjs';

of(1, 2)
  .pipe(finalize(() => console.log('поток закончен')))
  .subscribe({ next: (x) => console.log(x) });
// 1, 2, поток закончен
```

## Что сделать

Перед каждым опытом **сначала запиши предсказание**, потом запусти.

**Часть А — порядок вывода**

1. Выведи `'start'`, подпишись на `of('a', 'b', 'c')` с объектом `{ next, complete }`, выведи `'end'`. В каком порядке появятся строки?
2. Повтори, но без `subscribe`. Что изменилось?

**Часть Б — поток во времени**

1. Подпишись на `interval(500)` из RxJS и выводи значения. Через 2 секунды отпишись. Сколько значений успело прийти? Вызвался ли `complete`?

**Часть В — ошибка**

1. Подпишись на `throwError(() => new Error('boom'))` с `next`, `error` и `complete`. Какие обработчики сработали?
2. Добавь `finalize` и сравни: какой из обработчиков годится для «выключить индикатор загрузки» — `complete` или `finalize`? Почему?

**Часть Г — первые HTTP-запросы**

Внедри `HttpClient` в компонент площадки.

1. Создай Observable `http.get('/api/health')`, но не подписывайся. Есть ли запрос в Network?
2. Подпишись один раз, потом подпишись на тот же Observable ещё раз. Сколько запросов в Network?
3. Выведи время: перед `subscribe`, в `next` и после `subscribe`. В каком порядке? Сравни с частью А.
4. Запроси `/api/unknown`. Какой `status` и что лежит в `error` у пришедшей ошибки?
5. Останови сервер и повтори запрос к `/api/health`. Какой статус? Почему он не `0`, хотя сервера нет? (Подсказка: кто сейчас отвечает на запрос вместо Express?)

## Критерии готовности

- [ ] В `observations.md` для каждого опыта есть предсказание и результат
- [ ] Подписки передают объект `{ next, error, complete }`, а не три функции подряд
- [ ] Ты можешь ответить: почему в части А `end` напечатался после значений, а в части Г — раньше ответа?
- [ ] Ты можешь ответить: что делает `unsubscribe` с HTTP-запросом, который ещё не получил ответ?
- [ ] Ты можешь ответить: почему для индикатора загрузки нужен `finalize`, а не `complete`?

## Наводящие вопросы (если застрял)

- Откуда импортировать `of`, `interval`, `throwError`, `finalize`?
- Что возвращает `subscribe()` и как с его помощью отписаться?
- Может ли поток после `error` выдать `complete`?
- Какой `status` ставит Angular, когда ответа нет вообще? А когда ответ есть, но с ошибкой?

## Типичные ловушки

- `subscribe(next, error)` с функциями отдельными аргументами — устаревший стиль.
- Ожидание, что `const x = http.get(...)` — это данные.
- Выключение индикатора в `complete` — при ошибке он не погаснет.
