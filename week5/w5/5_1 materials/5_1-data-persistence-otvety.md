## A. Общее

<a id="a-1"></a>

### 1. Что такое data persistence

**Ответ:** сохранение состояния приложения так, чтобы оно пережило перезагрузку страницы или повторный визит.

**Пояснение:** в SPA всё состояние (кто залогинен, что открыто, что набрано) живёт в памяти JavaScript. F5 очищает эту память: без хранилища пользователь окажется разлогинен, черновики пропадут.

**Подробнее:** [Конспект §1](5_1-data-persistence-konspekt.md#s1) · [← вопрос](5_1-data-persistence-voprosy.md#q-1)

<a id="a-2"></a>

### 2. Четыре хранилища

**Ответ:** localStorage, sessionStorage, cookies, IndexedDB. К Web Storage API относятся только localStorage и sessionStorage.

**Пояснение:** куки — механизм протокола HTTP, появившийся задолго до HTML5. IndexedDB — отдельный API. Материал ошибочно называет все четыре «Web Storage».

**Подробнее:** [Конспект §2.1](5_1-data-persistence-konspekt.md#s2-1) · [П-12](5_1-data-persistence-popravki.md#p-12) · [← вопрос](5_1-data-persistence-voprosy.md#q-2)

## B. localStorage и sessionStorage

<a id="a-3"></a>

### 3. Методы

**Ответ:** `setItem(key, value)`, `getItem(key)`, `removeItem(key)`, `clear()`, свойство `length` и метод `key(index)`. Для отсутствующего ключа `getItem` возвращает `null`.

**Пояснение:** имена в camelCase, с заглавной `I`. Написание `setitem` из материала падает с `TypeError: ... is not a function`. «Изменить» значение — это тот же `setItem`.

**Подробнее:** [Конспект §3.3](5_1-data-persistence-konspekt.md#s3-3) · [П-1](5_1-data-persistence-popravki.md#p-1) · [← вопрос](5_1-data-persistence-voprosy.md#q-3)

<a id="a-4"></a>

### 4. Объект в `setItem`

**Ответ:** в JavaScript выведется `[object Object]`. В TypeScript код не скомпилируется: `setItem` принимает только `string`.

**Пояснение:** в JS браузер молча приводит значение к строке через `String()`, и данные теряются без ошибки. Правильно: `localStorage.setItem('user', JSON.stringify(obj))`, а при чтении `JSON.parse`.

**Подробнее:** [Конспект §3.4](5_1-data-persistence-konspekt.md#s3-4) · [П-2](5_1-data-persistence-popravki.md#p-2) · [← вопрос](5_1-data-persistence-voprosy.md#q-4)

<a id="a-5"></a>

### 5. `false` в хранилище

**Ответ:** выведется «звук выключен».

**Пояснение:** `false` сохранилось как строка `"false"`. Непустая строка в `if` считается истиной. Правильная проверка: `localStorage.getItem('muted') === 'true'`.

**Подробнее:** [Конспект §3.4](5_1-data-persistence-konspekt.md#s3-4) · [П-2](5_1-data-persistence-popravki.md#p-2) · [← вопрос](5_1-data-persistence-voprosy.md#q-5)

<a id="a-6"></a>

### 6. Безопасное сохранение и чтение объекта

**Ответ:**

```ts
const user = { id: 2, username: 'anna', role: 'groupadmin' };
localStorage.setItem('user', JSON.stringify(user));

function readUser(): User | null {
  const raw = localStorage.getItem('user');
  if (raw === null) return null;            // ключа нет
  try {
    return JSON.parse(raw) as User;
  } catch {
    localStorage.removeItem('user');        // испорченные данные удаляем
    return null;
  }
}
```

**Пояснение:** две защиты — от отсутствующего ключа (`null`) и от испорченной строки (`JSON.parse` бросает исключение). `as User` не проверяет форму данных, а только сообщает тип компилятору.

**Подробнее:** [П-2](5_1-data-persistence-popravki.md#p-2) · [Пример 1, метод readUser](5_1-data-persistence-primery.md#ex-1) · [← вопрос](5_1-data-persistence-voprosy.md#q-6)

<a id="a-7"></a>

### 7. Origin

**Ответ:** origin = протокол + хост + порт.

- а) разные — отличается порт;
- б) один — путь в origin не входит;
- в) разные — отличается протокол.

**Пояснение:** материал упускает порт, хотя файл 5_3 определяет origin правильно, с портом.

**Подробнее:** [Конспект §2.2](5_1-data-persistence-konspekt.md#s2-2) · [П-3](5_1-data-persistence-popravki.md#p-3) · [← вопрос](5_1-data-persistence-voprosy.md#q-7)

<a id="a-8"></a>

### 8. «Пропавший» логин

**Ответ:** `localhost:4200` и `localhost:3000` — разные origin из-за разных портов, и у каждого свой localStorage. Это не баг кода, а устройство браузера.

**Пояснение:** при разработке одновременно на двух портах данные нужно сохранять отдельно на каждом. Посмотреть оба хранилища можно в DevTools → Application → Local Storage: там отдельная строка для каждого origin.

**Подробнее:** [П-3](5_1-data-persistence-popravki.md#p-3) · [← вопрос](5_1-data-persistence-voprosy.md#q-8)

<a id="a-9"></a>

### 9. localStorage и sessionStorage

**Ответ:**

1. **Срок жизни:** localStorage бессрочен, sessionStorage удаляется при закрытии вкладки.
2. **Область видимости:** localStorage общий для всех вкладок одного origin, а у каждой вкладки свой sessionStorage.

**Пояснение:** материал называет только первое отличие и путается, говоря, что сессия живёт «пока открыт браузер».

**Подробнее:** [Конспект §4.3](5_1-data-persistence-konspekt.md#s4-3) · [П-6](5_1-data-persistence-popravki.md#p-6) · [← вопрос](5_1-data-persistence-voprosy.md#q-9)

<a id="a-10"></a>

### 10. Где будет значение

**Ответ:**

- а) `'1'` — перезагрузка сессию не прерывает;
- б) `null` — новая вкладка, открытая вручную, начинает свою пустую сессию;
- в) `'1'` — дублирование копирует sessionStorage на момент копии, дальше копии живут отдельно;
- г) `null` — sessionStorage вкладки A удалился вместе с ней.

**Подробнее:** [Конспект §4.2](5_1-data-persistence-konspekt.md#s4-2) · [П-6](5_1-data-persistence-popravki.md#p-6) · [Пример 2](5_1-data-persistence-primery.md#ex-2) · [← вопрос](5_1-data-persistence-voprosy.md#q-10)

<a id="a-11"></a>

### 11. Синхронность

**Ответ:** каждая операция блокирует выполнение JavaScript (и отрисовку страницы), пока не завершится. Следующая строка кода выполняется только после неё.

**Пояснение:** следствие — нельзя хранить в localStorage большие объёмы или делать тысячи операций подряд: страница подвиснет. Для больших данных есть асинхронная IndexedDB.

**Подробнее:** [Конспект §3.2](5_1-data-persistence-konspekt.md#s3-2) · [Конспект §6.2](5_1-data-persistence-konspekt.md#s6-2) · [← вопрос](5_1-data-persistence-voprosy.md#q-11)

<a id="a-12"></a>

### 12. Проверка поддержки

**Ответ:** Web Storage поддерживают все браузеры больше десяти лет, поэтому проверка ничего не даёт. Реальные проблемы:

- `QuotaExceededError` — место закончилось, `setItem` бросает исключение;
- `SecurityError` — пользователь запретил хранение данных сайтов;
- SSR — если проект создан с серверным рендерингом, на сервере localStorage нет.

**Пояснение:** решение — работать с хранилищем через один сервис с `try/catch`, а при SSR проверять платформу через `isPlatformBrowser`.

**Подробнее:** [П-5](5_1-data-persistence-popravki.md#p-5) · [← вопрос](5_1-data-persistence-voprosy.md#q-12)

## C. Хуки жизненного цикла Angular

<a id="a-13"></a>

### 13. `ngOnInit` и `$(document).ready`

**Ответ:** неверно. `$(document).ready` — событие всего документа. `ngOnInit` — хук конкретного компонента: Angular вызывает его один раз после установки входных свойств, **до** отрисовки шаблона.

**Пояснение:**

- с localStorage работают в `ngOnInit`: хранилище — API браузера, DOM ему не нужен;
- с элементами шаблона работают в `ngAfterViewInit`, когда шаблон уже отрисован.

**Подробнее:** [Конспект §3.5](5_1-data-persistence-konspekt.md#s3-5) · [П-4](5_1-data-persistence-popravki.md#p-4) · [← вопрос](5_1-data-persistence-voprosy.md#q-13)

<a id="a-14"></a>

### 14. Фокус в `ngOnInit`

**Ответ:** в `ngOnInit` шаблон ещё не отрисован, поэтому `this.box` равно `undefined`. Будет ошибка `TypeError: Cannot read properties of undefined (reading 'nativeElement')`. Исправление — перенести фокус в `ngAfterViewInit`:

```ts
export class ChatInputComponent implements AfterViewInit {
  @ViewChild('box') box!: ElementRef<HTMLInputElement>;

  ngAfterViewInit(): void {
    this.box.nativeElement.focus();
  }
}
```

**Подробнее:** [П-4](5_1-data-persistence-popravki.md#p-4) · [Пример 2, порядок хуков](5_1-data-persistence-primery.md#ex-2) · [← вопрос](5_1-data-persistence-voprosy.md#q-14)

## D. Cookies

<a id="a-15"></a>

### 15. Зачем нужны куки

**Ответ:** HTTP не хранит состояние (stateless): после ответа сервер «забывает» клиента, и следующий запрос для него — от незнакомца. Куки хранят данные у клиента и возвращают их серверу с каждым запросом, поэтому сервер «узнаёт» пользователя.

**Подробнее:** [Конспект §5.1](5_1-data-persistence-konspekt.md#s5-1) · [← вопрос](5_1-data-persistence-voprosy.md#q-15)

<a id="a-16"></a>

### 16. Путь куки

**Ответ:**

1. Браузер отправляет запрос.
2. Сервер отвечает с заголовком `Set-Cookie`.
3. Браузер сохраняет куку.
4. Во всех следующих подходящих запросах браузер сам отправляет её в заголовке `Cookie`.

Куку может создать и JavaScript на странице через `document.cookie`, если только это не `HttpOnly`-кука.

**Подробнее:** [Конспект §5.3](5_1-data-persistence-konspekt.md#s5-3) · [Пример 3](5_1-data-persistence-primery.md#ex-3) · [← вопрос](5_1-data-persistence-voprosy.md#q-16)

<a id="a-17"></a>

### 17. Размер

**Ответ:** около 4 КБ (4096 байт) на одну куку, считая имя, значение и атрибуты. В материале ошибочно указано 2 КБ.

**Пояснение:** куки прикладываются к каждому подходящему запросу, включая картинки и API, поэтому лишние байты умножаются на каждый запрос. Большие данные хранят в localStorage или IndexedDB. Слишком большую куку браузер молча не сохранит.

**Подробнее:** [Конспект §5.2](5_1-data-persistence-konspekt.md#s5-2) · [П-8](5_1-data-persistence-popravki.md#p-8) · [← вопрос](5_1-data-persistence-voprosy.md#q-17)

<a id="a-18"></a>

### 18. Применение

**Ответ:**

- **управление сессией** — вход в аккаунт, корзина;
- **персонализация** — язык, тема;
- **трекинг** — аналитика, реклама.

**Подробнее:** [Конспект §5.4](5_1-data-persistence-konspekt.md#s5-4) · [← вопрос](5_1-data-persistence-voprosy.md#q-18)

<a id="a-19"></a>

### 19. Сессионная и постоянная кука

**Ответ:**

- **Сессионная** — без `Expires` и `Max-Age`. Удаляется при закрытии **браузера** (конце сеанса браузера), а не вкладки. При восстановлении сессии браузер может её сохранить.
- **Постоянная** — с `Expires` или `Max-Age`, живёт до указанного срока.

**Пояснение:** у sessionStorage «сессия» — это жизнь вкладки, у сессионной куки — сеанс браузера. Сессионная кука переживает закрытие вкладки и видна всем вкладкам. В материале здесь ошибка: там написано «до закрытия вкладки».

**Подробнее:** [Конспект §5.6](5_1-data-persistence-konspekt.md#s5-6) · [П-7](5_1-data-persistence-popravki.md#p-7) · [← вопрос](5_1-data-persistence-voprosy.md#q-19)

<a id="a-20"></a>

### 20. Атрибуты

**Ответ:**

- `Expires` — дата, после которой кука удаляется.
- `Max-Age` — срок жизни в секундах; важнее `Expires`, если указаны оба.
- `Secure` — кука передаётся только по HTTPS.
- `HttpOnly` — кука не видна JavaScript; ставит её только сервер.
- `Domain` — расширяет область на домен и все поддомены; без него кука уходит только на хост, который её поставил.
- `Path` — кука уходит только на URL, путь которых начинается с указанного.
- `SameSite` — уходит ли кука с запросами, которые инициировал другой сайт (`Strict`, `Lax`, `None`); защита от CSRF.

**Пояснение:** в материале нет `Max-Age` и `SameSite`, а про `Domain` сказано, что он сужает область, хотя он её расширяет.

**Подробнее:** [Конспект §5.5](5_1-data-persistence-konspekt.md#s5-5) · [П-10](5_1-data-persistence-popravki.md#p-10) · [← вопрос](5_1-data-persistence-voprosy.md#q-20)

<a id="a-21"></a>

### 21. Кука с датой 2020 года

**Ответ:** кука не создастся, а если кука `fruit` уже была — удалится. Дата истечения в прошлом, поэтому браузер считает куку истёкшей.

**Пояснение:** это пример «постоянной» куки из материала, который со временем превратился в пример удаления. Постоянную куку лучше задавать через `max-age` или вычисленную дату.

**Подробнее:** [П-9](5_1-data-persistence-popravki.md#p-9) · [← вопрос](5_1-data-persistence-voprosy.md#q-21)

<a id="a-22"></a>

### 22. Удаление

**Ответ:**

```js
document.cookie = 'theme=; max-age=0; path=/';
```

**Пояснение:** удаление не сработает, если:

- `path` (или `domain`) не совпадает с тем, с которым кука создавалась: браузер сочтёт это другой кукой;
- кука с `HttpOnly`: из JS её не удалить, только сервер (`res.clearCookie`).

**Подробнее:** [Конспект §5.7](5_1-data-persistence-konspekt.md#s5-7) · [П-9](5_1-data-persistence-popravki.md#p-9) · [← вопрос](5_1-data-persistence-voprosy.md#q-22)

<a id="a-23"></a>

### 23. Чтение

**Ответ:** одну строку со всеми доступными куками вида `"lang=ru; theme=dark"` — только имена и значения, без атрибутов. Кук с `HttpOnly` там нет.

**Пояснение:** строку нужно разбирать самому (`split('; ')`) или через библиотеку. Присваивание `document.cookie = ...` при этом добавляет или обновляет только одну куку.

**Подробнее:** [Конспект §5.7](5_1-data-persistence-konspekt.md#s5-7) · [П-9](5_1-data-persistence-popravki.md#p-9) · [← вопрос](5_1-data-persistence-voprosy.md#q-23)

<a id="a-24"></a>

### 24. Куки и порты

**Ответ:** куку `lang=ru` страница на 4200 увидит, значение из localStorage — нет.

**Пояснение:** куки привязаны к домену и пути, но не к порту, поэтому кука с `localhost` видна на любом порту `localhost`. localStorage привязан к origin, а в origin входит порт.

**Подробнее:** [П-3](5_1-data-persistence-popravki.md#p-3) · [← вопрос](5_1-data-persistence-voprosy.md#q-24)

<a id="a-25"></a>

### 25. Express `maxAge`

**Ответ:** 3,6 секунды. В Express опция `maxAge` задаётся в **миллисекундах**.

**Пояснение:** для часа нужно `maxAge: 60 * 60 * 1000`. Путаница возникает потому, что в самом заголовке `Set-Cookie` атрибут `Max-Age` — в секундах; Express переводит одно в другое сам.

**Подробнее:** [П-10](5_1-data-persistence-popravki.md#p-10) · [← вопрос](5_1-data-persistence-voprosy.md#q-25)

<a id="a-26"></a>

### 26. `CookieService`

**Ответ:** нет, это сторонняя библиотека `ngx-cookie-service` (`npm install ngx-cookie-service`). Своего сервиса для кук в Angular нет.

**Пояснение:** без `path` браузер привяжет куку к «папке» текущего пути. На вложенном маршруте вроде `/groups/5` кука привяжется к `/groups` и не будет видна на `/home`, а `delete` с другой страницы молча её не найдёт. Поэтому `path: '/'` передают и при записи, и при удалении.

**Подробнее:** [Пример 4](5_1-data-persistence-primery.md#ex-4) · [Конспект §5.5, атрибут Path](5_1-data-persistence-konspekt.md#s5-5) · [← вопрос](5_1-data-persistence-voprosy.md#q-26)

## E. IndexedDB

<a id="a-27"></a>

### 27. Отличия от localStorage

**Ответ:**

1. Хранит **объекты как есть** (массивы, даты, файлы) — без `JSON.stringify`.
2. **Асинхронная** — не блокирует страницу, результат приходит через событие или промис.
3. **Большой объём** (сотни мегабайт и больше), плюс транзакции и индексы для поиска.

**Подробнее:** [Конспект §6.2](5_1-data-persistence-konspekt.md#s6-2) · [П-12](5_1-data-persistence-popravki.md#p-12) · [← вопрос](5_1-data-persistence-voprosy.md#q-27)

<a id="a-28"></a>

### 28. `upgrade`

**Ответ:** `upgrade` вызывается при первом создании базы и при каждом повышении версии. Только в нём можно создавать и удалять хранилища (object stores) и индексы. Чтобы добавить новое хранилище, нужно повысить номер версии в `openDB` (например, 1 → 2) и создать хранилище в `upgrade`.

**Подробнее:** [Пример 5, схема upgrade](5_1-data-persistence-primery.md#ex-5) · [← вопрос](5_1-data-persistence-voprosy.md#q-28)

## F. Безопасность

<a id="a-29"></a>

### 29. Чужие сайты

**Ответ:** нет, это запрещает same-origin policy. Реальная угроза — **XSS**: чужой скрипт, выполнившийся **внутри твоего** origin, видит localStorage, sessionStorage и все куки без `HttpOnly`.

**Пояснение:** типичные пути XSS — пользовательский текст, вставленный на страницу как HTML (например, сообщение в чате), или скомпрометированная сторонняя библиотека. Защита в Angular — выводить текст через интерполяцию `{{ }}`, которая экранирует HTML.

**Подробнее:** [Конспект §7.2](5_1-data-persistence-konspekt.md#s7-2) · [П-11](5_1-data-persistence-popravki.md#p-11) · [← вопрос](5_1-data-persistence-voprosy.md#q-29)

<a id="a-30"></a>

### 30. CSRF

**Ответ:** CSRF — чужой сайт заставляет браузер отправить запрос на твой сервер, а браузер сам прикладывает к нему куки. Сервер принимает запрос за действие пользователя. Защита — атрибут `SameSite` (`Lax` или `Strict`) и CSRF-токены.

**Пояснение:** localStorage браузер никогда не отправляет сам, его значение уходит на сервер только если твой код явно его приложит. Поэтому CSRF касается только кук.

**Подробнее:** [Конспект §7.2](5_1-data-persistence-konspekt.md#s7-2) · [П-10](5_1-data-persistence-popravki.md#p-10) · [П-11](5_1-data-persistence-popravki.md#p-11) · [← вопрос](5_1-data-persistence-voprosy.md#q-30)

<a id="a-31"></a>

### 31. Самое защищённое место

**Ответ:** кука с `HttpOnly` (плюс `Secure` и `SameSite`). JavaScript её не видит, поэтому XSS-скрипт не может её прочитать.

**Пояснение:** IndexedDB читает любой JS на этом origin — у неё та же уязвимость к XSS, что у localStorage, и данные в ней не шифруются.

**Подробнее:** [Конспект §7.2](5_1-data-persistence-konspekt.md#s7-2) · [П-11](5_1-data-persistence-popravki.md#p-11) · [Пример 3](5_1-data-persistence-primery.md#ex-3) · [← вопрос](5_1-data-persistence-voprosy.md#q-31)

<a id="a-32"></a>

### 32. Подмена роли

**Ответ:**

- **Может произойти:** интерфейс покажет админские кнопки, потому что роль в браузере используется только для отображения.
- **Не должно произойти:** реальных прав пользователь не получает. На каждый запрос с админским действием сервер определяет пользователя по тому, чему он доверяет (своей сессии, а не присланной клиентом роли), берёт роль из своих данных и отвечает 403.

**Подробнее:** [Конспект §7.3](5_1-data-persistence-konspekt.md#s7-3) · [П-11](5_1-data-persistence-popravki.md#p-11) · [Пример 1, hasRole](5_1-data-persistence-primery.md#ex-1) · [← вопрос](5_1-data-persistence-voprosy.md#q-32)

### 33. Где хранить

**Ответ:**

**Подробнее:** [Конспект §8.2](5_1-data-persistence-konspekt.md#s8-2) · [Схема выбора хранилища](5_1-data-persistence-primery.md#ex-0) · [← вопрос](5_1-data-persistence-voprosy.md#q-33)

<a id="a-34"></a>

### 34. Сигнал и кука

**Ответ:** интерфейс продолжит показывать, что пользователь залогинен, пока страницу не перезагрузят. После F5 сигнал прочитает куку заново и станет `false`.

**Пояснение:** `signal(this.cookieService.check('username'))` читает куку **один раз**, при создании сервиса. Куки не реактивны, и сигнал не узнаёт об их изменениях: ни об истечении срока, ни об удалении в DevTools или в другой вкладке.

**Подробнее:** [Пример 4, комментарий к сигналу и диаграмма](5_1-data-persistence-primery.md#ex-4) · [← вопрос](5_1-data-persistence-voprosy.md#q-34)

<a id="a-35"></a>

### 35. Выкидывает после F5

**Ответ:** после F5 память JS очищена, сигнал снова `false`, а HttpOnly-куку JavaScript прочитать не может. Гард видит `false` и отправляет на логин, хотя сессия на сервере жива.

**Пояснение:** решение — при открытии защищённой страницы спросить сервер, например `GET /api/me`. Браузер сам приложит куку, сервер ответит пользователем или 401, и гард решит по ответу.

**Подробнее:** [Пример 3, ensureSession и sessionGuard](5_1-data-persistence-primery.md#ex-3) · [← вопрос](5_1-data-persistence-voprosy.md#q-35)
