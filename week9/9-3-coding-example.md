# MongoDB with Node and Angular — coding example

Разбор приложения-примера целиком: семь маршрутов на сервере, четыре компонента и сервис на клиенте. Лекция даёт хорошее описание того, **что** должен делать каждый маршрут, но код снова на скриншотах, а в самой архитектуре примера есть две настоящие проблемы: гонка при генерации собственного `id` и небезопасное обновление документа. Разбираю по порядку.

### Что делает приложение (слайды 2–9)

CRUD над товарами. Форма товара: `id: number`, `name: string`, `description: string`, `price: number`, `units: number`.

Семь маршрутов из лекции и что каждый должен делать:

| Маршрут в лекции | Задача |
| --- | --- |
| `POST /api/add` | прочитать тело, проверить, что товара с таким `id` нет, вставить, ответить успехом или отказом |
| `GET /api/getlist` | найти все товары и вернуть массив |
| `POST /api/getitem` | по идентификатору из тела найти один товар и вернуть его |
| `POST /api/update` | по идентификатору обновить поля товара, ответить успехом |
| `POST /api/delete` | удалить товар и вернуть клиенту **обновлённый список** |
| `POST /api/checkvalidid` | посчитать товары с таким `id` и подсказать, свободен ли он и какой брать следующий |
| `GET /api/prodcount` | вернуть количество товаров для главной страницы |

Правильную REST-схему для этих же операций я расписал в заметках 9.2 — там таблица соответствия. Здесь важнее содержательные проблемы.

### Проблема 1: свой числовой `id` и гонка

Логика лекции такая: перед вставкой посчитать, сколько документов с таким `id` уже есть, и если ноль — вставлять. А для подсказки следующего номера отсортировать по `id` по убыванию, взять один документ и прибавить единицу.

Работать это будет, пока ты один. Но между «посчитали, что свободен» и «вставили» проходит время, и если два клиента проверят один и тот же номер одновременно, оба получат «свободно» и оба вставят — в базе окажутся дубликаты. Это классическая гонка (race condition), и проверкой перед записью она не лечится **никогда**, потому что проверка и запись — две отдельные операции.

Правильное решение — заставить базу гарантировать уникальность:

```js
// один раз при старте приложения
await products.createIndex({ id: 1 }, { unique: true });
```

Дальше просто пытаешься вставить и обрабатываешь отказ базы:

```js
try {
    await products.insertOne(data);
    res.status(201).json({ ok: true });
} catch (err) {
    if (err.code === 11000) {                 // duplicate key
        return res.status(409).json({ error: 'товар с таким id уже существует' });
    }
    throw err;
}
```

Уникальный индекс — это гарантия на уровне базы, её невозможно обойти гонкой. Проверку через `checkvalidid` при этом можно оставить, но только как подсказку в интерфейсе, а не как защиту.

И более общий вопрос: а нужен ли свой числовой `id`? MongoDB уже даёт `_id`, уникальный без всяких усилий. Своё числовое поле оправдано, когда номер видит пользователь (номер заказа, артикул). Если такого требования нет — не заводи вторую систему идентификаторов, это лишний источник ошибок. В лекции, кстати, оба идентификатора и используются одновременно: `id` для проверки уникальности, `_id` для правки и удаления.

### Проблема 2: `$set` от тела запроса

Слайд 22 описывает обновление так: взять новые данные из тела запроса и передать их в `updateOne` через `$set`. В таком виде клиент может дописать в документ любые поля, какие захочет, в том числе служебные. Поэтому поля надо просеивать белым списком — как в примере `pickFields` из заметок 9.2.

Там же в слайде верно сказано главное про `_id`: он создаётся Mongo автоматически, и чтобы искать по нему, строку из запроса надо превратить в `ObjectId`. Добавлю то, чего нет: обязательно проверяй `ObjectId.isValid(id)` до создания, иначе на мусорной строке драйвер бросит исключение и маршрут упадёт с 500 вместо честного 400.

### Проблема 3: удаление возвращает список

Слайд 23: после удаления сервер заново запрашивает базу и возвращает клиенту свежий список товаров. Это удобно и экономит один запрос, но смешивает ответственности: маршрут `DELETE` начинает отвечать данными другого ресурса. Лучше вернуть результат операции, а список запросить отдельно — тем более что клиенту всё равно нужен способ обновлять список. Как оптимизация приём допустим, но понимай, что ты обменял чистоту API на один сэкономленный запрос.

### Сервер: как я бы разложил файлы

Лекция предлагает вынести каждый маршрут в свой модуль в папке `routes/` — идея хорошая, структура остаётся читаемой. Готовый рабочий вариант роутера с валидацией, статусами и `ObjectId` лежит в заметках 9.2, его достаточно скопировать и разбить по файлам, если нужна структура «один эндпоинт — один модуль».

Что стоит держать в голове про `server.js` из слайда 19: подключение к базе делается **один раз** при старте, и только после успешного подключения запускается Express. Клиент базы (`client`) и объект `db` передаются в маршруты, а не создаются внутри каждого маршрута заново. Почему именно так — подробно в заметках 9.1.

Отдельно про два маршрута со счётом:

```js
// GET /api/products/count
res.json({ count: await products.countDocuments() });

// подсказка следующего id
const [last] = await products.find({}).sort({ id: -1 }).limit(1).toArray();
res.json({ nextId: (last?.id ?? 0) + 1 });
```

Приём из лекции (сортировка по убыванию плюс `limit(1)`) — правильный способ получить максимум. Только помни про `countDocuments()` вместо устаревшего `count()`, об этом было в заметках 8.2.

### Клиент (слайды 10–17, 26–29)

Состав: компоненты Home (показывает количество товаров), Add Product, List Products, Edit Product; сервис `Proddata` для запросов; класс `Product` для описания формы объекта. Bootstrap ставится через npm и подключается в `angular.json`, иконки Font Awesome — через CDN в `index.html`. Имена компонентов лекция оставляет на твой выбор.

Ключевая фраза со слайда 26 стоит того, чтобы её осознать: HTTP-запрос возвращает Observable, на который компонент подписывается, и данные приходят в колбэк подписки. Это ровно то, что разбиралось в week6, и здесь оно наконец работает на настоящих данных. Код сервиса и компонента со списком — в заметках 9.2.

Что помнить по клиентской части:

- **Форма и `[(ngModel)]`** требуют `FormsModule` в `imports` (в компоненте, если он standalone, или в модуле).
- **`*ngFor` по списку** и ссылки на правку и удаление строятся по `product._id` — именно он уникален, а не индекс в массиве.
- **`id` не редактируется** на странице правки (слайд 14) — правильное решение, потому что смена идентификатора это не правка, а создание другой записи.
- **Проверка `id` на ходу** (слайд 29): каждый ввод значения дёргает сервер. В рабочем коде это место просят обвесить `debounceTime`, чтобы не отправлять запрос на каждую нажатую клавишу, но операторов из RxJS в наших конспектах пока не было — просто держи в голове, что запрос на каждый символ это дорого.
- **Анимации** (слайды 28–29) к теме недели отношения не имеют, это косметика. Если время поджимает, делай их последними.

### Порядок, в котором это удобно собирать

Сначала сервер целиком, и проверить его без Angular — через Compass видно данные, а маршруты удобно дёргать из браузера (`GET`) и через `curl` или Postman (остальные). Когда сервер отвечает правильными статусами, подключать клиент: сначала список, потом добавление, потом правка и удаление. Так у тебя на каждом шаге работающее приложение, а не сорок файлов, которые «должны заработать вместе».

### Проверь себя

1. Почему проверка «есть ли уже такой `id`» перед вставкой не защищает от дубликатов?
2. Как заставить базу саму гарантировать уникальность и как поймать нарушение?
3. Чем опасно `updateOne({ _id }, { $set: req.body })`?
4. Зачем проверять `ObjectId.isValid` до создания `ObjectId`?
5. Почему в списке товаров ссылки строятся по `_id`, а не по индексу элемента массива?
6. Что не так с тем, что маршрут удаления возвращает список товаров?

Ответы: потому что между проверкой и вставкой проходит время, и два одновременных запроса оба увидят «свободно» — это гонка. Создать уникальный индекс `createIndex({ id: 1 }, { unique: true })` и обрабатывать ошибку с кодом 11000, отвечая 409. Клиент сможет записать в документ произвольные поля, поэтому тело запроса надо просеивать белым списком. Иначе на некорректной строке драйвер бросит исключение, и вместо честного 400 клиент получит 500. Потому что индекс меняется при любой пересортировке или фильтрации списка, а `_id` привязан к конкретному документу навсегда. Маршрут `DELETE` начинает отдавать данные другого ресурса — это смешение ответственностей, обмен чистоты API на один сэкономленный запрос.
