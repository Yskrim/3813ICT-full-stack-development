Практика идёт снизу вверх по пирамиде тестов: сначала чтение тестов, которые «врут», потом тесты сервера, потом тесты клиента и сквозные сценарии. ## Задание 1. Найди тесты, которые врут

Самый опасный тест — тот, что проходит, когда код сломан. Для каждого фрагмента **предскажи**, что покажет запуск, назови причину одной фразой и перепиши правильно.

```js
// 1 — Mocha
it('получает товары', () => {
  fetch('http://localhost:3000/api/products').then((r) => assert.equal(r.status, 404));
});

// 2 — Mocha
const assert = require('assert');
it('цена — число', () => assert.equal(getPrice(), 10));     // getPrice() возвращает '10'

// 3 — Mocha
it('умножает', () => assert.equal(mul(2, 2), 4));

// 4 — chai-http 5
chai.request(app).get('/api/products').end((err, res) => { res.should.have.status(200); done(); });
```

```ts
// 5 — Angular 21 + Vitest
beforeEach(async(() => {
  TestBed.configureTestingModule({ declarations: [UserComponent] }).compileComponents();
}));

// 6 — Vitest
spyOn(comp, 'onSubmit');

// 7 — Vitest (jsdom)
expect(fixture.nativeElement.querySelector('p').innerText).toContain('user1');

// 8 — Cypress
cy.get('button').click();
cy.on('window:alert', (str) => expect(str).to.equal('correct'));

// 9 — Cypress
cy.get('input').first().type('anna');
```

**Готово, если:** для всех девяти фрагментов есть предсказание, причина и исправление. Отдельно отмечены фрагменты, где тест **зелёный при сломанном коде** (их минимум четыре), и для каждого ты можешь объяснить, почему.

Опора: [асинхронные тесты](../week10-11/10_2-mocha-konspekt.md#s5) · [строгий assert](../week10-11/10_2-mocha-konspekt.md#s3) · [слабые кейсы](../week10-11/10_2-mocha-konspekt.md#s4) · [chai-http 5](../week10-11/10_2-mocha-popravki.md#p-5) · [Jasmine → Vitest](../week10-11/10_3-vitest-primery.md#ex-0) · [innerText в jsdom](../week10-11/10_3-vitest-popravki.md#p-4) · [проверка alert](../week10-11/11_3-cypress-popravki.md#p-3) · [селекторы](../week10-11/11_3-cypress-popravki.md#p-4)

## Задание 2. Тесты сервера

Теперь — тесты для сервера магазина.

**Подготовка**

1. `npm i -D mocha supertest`; скрипты `test`, `test:unit`, `test:integration`; `.mocharc.json` с увеличенным таймаутом.
2. Раздели `app.js` (приложение без `listen`) и `server.js` (запуск). В `db.js` — имя базы параметром и защита: при `NODE_ENV=test` работать только с базой, имя которой заканчивается на `_test`.

**Модульные тесты**

1. Для функции проверки товара сначала напиши **таблицу тест-кейсов** (не меньше шести: верные данные, лишние поля, нет имени, отрицательная цена, дробный остаток, не объект), потом тесты, потом — если функции ещё нет — саму функцию.
2. Перепиши роутер товаров как фабрику, которая получает коллекцию параметром. Проверь без MongoDB: `400` при неверных данных (и что в базу ничего не записано), `409` на ошибку с кодом `11000`, `500` при сбое базы.

**Интеграционные тесты** (тестовая база)

1. `POST` — `201`, и товар действительно есть в базе.
2. Повторный `POST` с тем же `id` — `409`, и в базе по-прежнему один товар.
3. `DELETE` несуществующего — `404`.

Каждый тест начинается с пустой коллекции, а после тестов соединение закрывается.

**Проверка:** временно сломай маршрут создания (например, отвечай `200` вместо `201`) и **предскажи**, какие тесты упадут. Проверь и верни.

**Готово, если:** `npm test` запускает всё; тесты не зависят от порядка запуска (запусти интеграционные дважды подряд — результат тот же); рабочая база не тронута; поломка из проверки ловится.

Опора: [план интеграционного теста](../week10-11/10_1-testing-basics-primery.md#ex-2) · [таблица кейсов → тесты](../week10-11/10_1-testing-basics-primery.md#ex-1) · [настройка проекта](../week10-11/10_2-mocha-primery.md#ex-1) · [роутер с поддельной коллекцией](../week10-11/10_2-mocha-primery.md#ex-2) · [интеграционный тест с тестовой базой](../week10-11/10_2-mocha-konspekt.md#s6-3)

## Задание 3. Тесты клиента и сквозные сценарии

**Модульные тесты Angular (`ng test`)**

1. Сервис товаров с `HttpTestingController`: `list()` отправляет `GET` на нужный адрес и отдаёт массив; `add()` передаёт ошибку `409` подписчику; после каждого теста — `verify()`.
2. Компонент списка с **подменой** сервиса (`useValue`, данные через `of(...)`): строки отрисованы, при пустом массиве — сообщение «нет товаров». Проверки — через `textContent`.
3. Если компонент сам вызывает `new Date()` или делает HTTP-запрос — вынеси зависимость (10_4) и объясни в двух фразах, что это дало тесту.

**Сквозные тесты (Cypress)**

1. `ng add @cypress/schematic`; в тестовом сервере — маршрут сброса данных, доступный только при `NODE_ENV=test`.
2. Добавь атрибуты `data-cy` в форму входа и список.
3. Сценарии входа: неверный пароль — сообщение об ошибке и остаёмся на `/login`; верный — переход и имя на странице; гость на защищённой странице — перенаправление на вход. Если компонент использует `alert`, проверяй его заглушкой `cy.stub`.
4. Страница списка с `cy.intercept`: ответ `500` — сообщение об ошибке, пустой ответ — «нет товаров».
5. Своя команда `cy.login` через API и `cy.session`; используй её в тесте гарда ролей.

**Проверка:** в сценарии «неверный пароль» временно убери показ ошибки в компоненте и **предскажи**, упадёт ли тест. Проверь — и сравни с тестом из фрагмента 8 задания 1.

**Готово, если:**

- `ng test` и `ng e2e` проходят;
- в тестах нет `innerText`, `spyOn` без `vi.`, селекторов по порядку и классам оформления;
- сквозные тесты начинаются с известных данных и не зависят друг от друга;
- тест «неверный пароль» падает, если ошибку перестают показывать.
